# Режим 2/3 в широкой раскладке — план

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** когда в широкой раскладке (`^F`) на экране нарисованы ровно колонки 1 и 3, первая занимает 2/3 ширины, третья — 1/3.

**Architecture:** правило — одна чистая функция `wideColumnGrow` в `frontend-src/picker-sections.js`: номера нарисованных колонок → вес `flex-grow` каждой. `renderWide` в `sessions.html` при пересборке каркаса вешает колонке с весом 2 класс `grow-2`, CSS даёт ему `flex-grow: 2`. Остальное как было: `flex: 1 1 0`, поровну.

**Tech Stack:** ванильный JS (UMD-модуль, тот же, что грузится и `<script>`-ом, и `require` в тестах), CSS flex, `node --test` через `npm test`.

**Spec:** слова Стаса (12.11, через head-сессию): «сейчас заняты колонки default + 3, в этом случае default должна быть на 2/3 ширины, а колонка 3 на 1/3». Отдельного спека нет.

Толкование, на котором стоит план (вопрос head отправлен, ответ меняет только тело `wideColumnGrow` и тесты Task 1):

- «default» — не номер колонки, а значение выпадашки `column` на вкладке Layout panels: «колонку назначает смысл секции». Своя живая панель (`live`) и `zellij` по смыслу стоят в колонке 1, чужие (`remote`) — в 2. У Стаса в колонку 3 назначены `projects`, `snapshots`, `past`, остальное — default; без чужих машин на экране колонки 1 и 3.
- `renderWide` видит только `section.column`, а не то, откуда номер взялся. Поэтому правило сформулировано по нарисованным колонкам: ровно `{1, 3}` → 2:1, иначе поровну.
- Это автоматика, не переключатель в настройках. С тремя колонками (пришли чужие машины) всё поровну по 1/3: у колонки 3 та же треть, что и в режиме 2/3, первая просто отдаёт треть второй.

## Review Focus

1. **`/p` и `/s` — одна колонка.** Ожидание: единственная колонка во весь экран, как сейчас. `wideColumnGrow([3])` → `[1]`; тест в Task 1.
2. **Чужие машины приходят и уходят** (колонка 2 появляется и пропадает между опросами). Ожидание: 1/3+1/3+1/3, затем снова 2/3+1/3, без застрявшего класса. Класс ставится только при пересборке каркаса, а набор колонок уже входит в `blocksShape` — тест в Task 2 сверяет, что вес считается внутри ветки `shape !== blocksShape`.
3. **Непустой запрос убирает все секции колонки 1** (своя живая панель на запросе не дорисовывается). Ожидание: остаётся одна колонка 3 во весь экран, 2/3 не применяется. `wideColumnGrow([3])` → `[1]`; тот же тест, что в п. 1.
4. **Перетаскивание.** Под перетаскиванием `addDropZones` вставляет пустую узкую колонку 2. Ожидание: 2/3 у первой остаётся, ширина не прыгает сильнее, чем сейчас. Ручная проверка в Task 3.
5. **WebKit (мак).** Вёрстку широкого режима надо мерить в обоих движках (`docs/rules/layouts.md`, «Вёрстку широкого режима мало померить в Chromium»). Ожидание: в WKWebView 2/3 так же, как в WebView2. Проверка в Task 3.

**Interfaces:**
- Produces: `PickerSections.wideColumnGrow(columns: number[]) -> number[]` — на входе номера нарисованных колонок по возрастанию, на выходе веса `flex-grow` той же длины. Ровно `[COLUMN_LIVE, COLUMN_PAST]` → `[2, 1]`, всё остальное → единицы.

- [ ] **Step 1: Write the failing tests** в `test/picker-sections.test.js`

test('колонки 1 и 3 без второй — первая на 2/3, третья на 1/3', () => {

});

test('при трёх колонках ширина поровну — у третьей та же треть', () => {

  assert.deepStrictEqual(wideColumnGrow([1, 4]), [1, 1]);
