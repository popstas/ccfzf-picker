# Иконки у пунктов меню `^K`

Дата: 2026-08-13.

## Задача

Меню действий (`^K`, правая кнопка) — список подписей одной высоты и одного
цвета. Пункты в нём разной природы: четыре открывают папку сессии внешним
приложением, остальные делают что-то внутри пикера. Отличить их взглядом
нельзя, а выбирают в этом меню чаще всего именно приложение — «открыть в
Cursor», «открыть в проводнике».

Иконка приложения отличает такой пункт мгновенно и без чтения: узнаётся
логотип, а не подпись. Взять её неоткуда, кроме самого приложения: пикер не
знает про Cursor ничего, кроме `argv` в конфиге, и знать не должен —
соответствие «чем открыть папку» принадлежит машине, а не программе
(`config-shape.js:63-66`).

## Что должно получиться

У каждой строки меню слева значок одной ширины. У пунктов, за которыми стоит
приложение, — иконка этого приложения, вытащенная из его `.exe`. У остальных —
символ шрифта. Пустых слотов нет: строка без значка в списке со значками
читается как недоделанная.

На маке значков-иконок не бывает — там всё меню глифовое, и это не отказ, а
отсутствие ветки: извлечение из `.app` — другой API и другая задача.

## Разведка: что проверено на месте

Проверено на самой Windows-машине (`ExtractAssociatedIcon`, картинки
просмотрены глазами), потому что три из четырёх ответов оказались не те, что
ожидались:

| exe | результат |
|---|---|
| `%SystemRoot%\explorer.exe` | папка ✓ |
| `%LOCALAPPDATA%\Programs\cursor\Cursor.exe` | логотип Cursor ✓ |
| `%LOCALAPPDATA%\Programs\Microsoft VS Code\Code.exe` | логотип VS Code ✓ |
| `%LOCALAPPDATA%\Microsoft\WindowsApps\wt.exe` — это `argv[0]` действия | **чужая иконка** |
| `%ProgramFiles%\WindowsApps\Microsoft.WindowsTerminal_…\WindowsTerminal.exe` | `>_` ✓ |
| `claude.exe` | **не существует на машине** |

Отсюда три правила ниже, каждое куплено этой проверкой.

### `wt.exe` — не файл, а alias

`%LOCALAPPDATA%\Microsoft\WindowsApps\wt.exe` — reparse point с тегом
`IO_REPARSE_TAG_APPEXECLINK` (`0x8000001B`) и нулевой длиной. Иконку с него
система отдаёт дежурную. Настоящий путь лежит внутри самого буфера reparse
третьей UTF-16 строкой (первые две — имя пакета и AppUserModelID):

```
03 00 00 00 | Microsoft.WindowsTerminal_8wekyb3d8bbwe \0
            | Microsoft.WindowsTerminal_8wekyb3d8bbwe!App \0
            | <диск>:\Program Files\WindowsApps\Microsoft.WindowsTerminal_…\WindowsTerminal.exe \0
```

Каталог пакета на чтение открывается (проверено), иконка из него достаётся.
Прописать этот путь в конфиг руками нельзя: в нём стоит версия, и после
обновления Terminal он протухнет молча — иконка просто исчезнет, а почему —
непонятно ниоткуда. Поэтому alias раскрывается на месте, из буфера.

### `claude.exe` нет и не будет

Сессии живут на удалённой машине, агента на Windows-машине не стоит. Пункт `new`
пробует найти `claude.exe` в `PATH` — на этой машине не найдёт и покажет глиф.
Ветка нужна не ради сегодняшнего дня, а ради того, что искать всё равно
придётся: поставят — появится.

### `argv[0]` у Explorer — это `cmd`

Действие `explorer` запускается через `cmd /c start`, потому что прямой
`explorer.exe` папку не открывал (правило записано в `CLAUDE.md`). Значит
угадывание по `argv[0]` дало бы иконку командной строки — и именно у самого
частого пункта. Отсюда ключ `icon` в конфиге.

## Конфиг: ключ `icon`

Необязательный ключ у действия:

```yaml
actions:
  - id: explorer
    label: Open in Explorer
    argv: ['cmd', '/c', 'start', '', '{localPathSlash}']
    icon: '%SystemRoot%\explorer.exe'   # ← новое
  - id: cursor
    label: Open in Cursor
    argv: ['…\Programs\cursor\Cursor.exe', '{localPath}']
                                        # icon не нужен: argv[0] и есть приложение
                                        # (в живом конфиге тут полный путь)
```

Пусто — берётся `argv[0]`. Путь берётся как есть; голое имя ищется в `PATH` с
дописанным `.exe`. Так Cursor, VS Code и Terminal получают иконку без единой
правки конфига, а `icon` остаётся тем, чем должен быть, — исключением.

Переменные окружения в пути раскрываются (`ExpandEnvironmentStringsW`) — один
вызов, и путь в конфиге перестаёт зависеть от буквы диска и имени пользователя.
Раскрытие живёт только в этой ветке: `argv` запускается без шелла
(`spawn_detached`, правило в `CLAUDE.md`), и раскрывать переменные там значило
бы завести второй разбор команды.

`normalizeActions` (`frontend-src/config-shape.js`): `icon` — необязательная
строка, не строка или пустая → `''`. Мусор в ключе действие **не выбрасывает**
— то же правило, что у `hotkey`: опечатка в иконке не повод прятать пункт, до
которого человек дойдёт через `^K`.

Окно настроек про `icon` не знает и знать не должно: патч сливается по ключам
(`config_file::merge_patch`), незнакомый ключ переживает сохранение — тем же
способом, что и `actions` целиком.

## Rust: `src-tauri/src/icons.rs`

Команда:

```rust
#[tauri::command]
async fn action_icons(specs: Vec<IconSpec>) -> HashMap<String, String>
// IconSpec { id: String, path: String }  →  { id: "data:image/png;base64,…" }
```

Чего не нашлось или не извлеклось — просто нет в карте. Отказ здесь не
событие: иконки нет, и страница ставит глиф. Городить сообщение об ошибке
не из чего — человек и так видит, что значка нет.

Внутри, по шагам:

1. **Разрешение пути.** Сначала `ExpandEnvironmentStringsW`; дальше есть
   разделитель — путь как есть, нет — поиск по `PATH` с `.exe`.
2. **Alias.** Файл — reparse point с тегом `AppExecLink`?
   `DeviceIoControl(FSCTL_GET_REPARSE_POINT)`, из буфера берётся третья
   UTF-16 строка. Иначе путь остаётся прежним.
3. **Извлечение.** `SHGetFileInfoW(SHGFI_ICON | SHGFI_LARGEICON)` → `HICON` →
   `GetIconInfo` → `GetDIBits` в 32-битный top-down DIB → BGRA. Альфа во всём
   битмапе нулевая (старая иконка без альфа-канала) — собирается из маски
   `hbmMask`. `DestroyIcon`/`DeleteObject` в конце, иначе утечка GDI-хендлов
   на каждый перечит.
4. **Упаковка.** PNG крейтом `png` (уже в дереве: Tauri тянет его ради
   `image-png` для иконки трея), base64 — в `data:image/png;base64,…`.

**Размер — 32×32.** Показывается в 16–18 CSS-пикселей; при масштабе 150% на
этой машине это 24–27 устройственных точек, то есть 32 хватает с запасом.
Тянуться за jumbo-иконками (256×256 через `IImageList`) значило бы взять
второй COM-интерфейс ради картинки, которую всё равно ужмут.

**Кеш** — `Mutex<HashMap<(PathBuf, SystemTime), Option<String>>>`, ключ путь
плюс mtime. Обновился Cursor — сменился mtime, иконка перечиталась сама.
Кеш по одному пути протух бы незаметно и держался бы до перезапуска пикера, а
перезапускают его только при выкатке. `Option` в значении кеширует и неудачу:
иначе несуществующий exe перепроверялся бы на каждый показ меню.

**Вне Windows** — `#[cfg(not(windows))]` возвращает пустую карту.

**Что тестируется без Windows.** Разбор буфера reparse (байты → путь) и сборка
RGBA из BGRA с маской — чистые функции, они живут вне `cfg(windows)` и
проверяются `cargo test` на любой машине. Под `cfg(windows)` остаётся только
обвязка над WinAPI, у которой своей логики нет.

## Страница

**Когда зовём.** Один раз при старте, после загрузки конфига, и ещё раз на
`config-changed`. Не при первом `^K`: извлечение четырёх иконок — единицы
миллисекунд, но меню обязано открываться уже с картинками, а не дорисовывать
их на глазах. Результат живёт в карте `id → dataUri` рядом с `CONFIG`.

Список запросов собирает страница, а не Rust: `CONFIG.actions` даёт пару
`{id, icon || argv[0]}` на каждое настроенное действие, плюс постоянная пара
`{id: 'new', path: 'claude.exe'}`. Rust про меню не знает ничего и знать не
должен — он умеет ровно «дай иконку этого файла».

**Разметка.** Первым элементом `.action-row` встаёт слот фиксированной ширины:

```html
<span class="action-icon"><img src="data:image/png;base64,…" alt=""></span>
<span class="action-icon">ⓘ</span>          <!-- когда иконки нет -->
```

Слот — 16×16 плюс отступ 10 px до подписи; картинка растягивается на весь слот
(`width/height: 16px`), глиф центрируется в нём. Ширина одна у всех строк,
подписи в одну линию. `alt=""` намеренно пуст: иконка дублирует подпись, а не
добавляет к ней.

**Глифы:**

| id | глиф | почему этот |
|---|---|---|
| `new` | `+` | иконка `claude.exe`, если он найдётся |
| `info` | `ⓘ` | общепринятый знак справки |
| `pr` | `↗` | тем же помечен PR в строке списка |
| `unread` | `●` оранжевым (`#db6d28`) | тем же горит непросмотренная сессия |
| `attach` | `⧉` | копирование |
| `open-remote` | `▣` | тем же помечено окно в строке списка |
| настроенное действие без иконки | `▸` | нейтральное «запустить» |

Три глифа взяты из строки списка не для красоты: один и тот же знак в списке и
в меню читается как одно и то же дело, а разные знаки заставили бы догадываться,
что `↗` в строке и «Open PR» в меню — про один и тот же PR.

## Тесты

Фронтенд (`npm test`):

- каждый встроенный `id`, который может вернуть `availableActions`, есть в
  таблице глифов — иначе новый пункт молча приедет без значка;
- строка меню рисует слот первым, подпись после, слот есть у каждой строки;
- `normalizeActions`: `icon` доезжает; мусорный `icon` обнуляется, а действие
  остаётся в списке.

Rust (`cargo test`):

- разбор буфера `AppExecLink`: третья строка, а не первая; обрезанный буфер
  даёт `None`, а не панику;
- сборка RGBA: битмап с альфой берётся как есть, битмап без альфы —
  собирается по маске;
- разрешение пути: путь с разделителем не трогается, голое имя ищется в `PATH`.

## Чего в дизайне нет намеренно

- **Иконок на маке.** `.app` — другой API (`NSWorkspace`), и на маке из четырёх
  действий настроены два. Глифы там честнее пустых слотов.
- **Таблицы «id → приложение» в коде.** Пикер не знает ни одного приложения по
  имени; единственное исключение — `claude.exe` у пункта `new`, и оно названо
  явно, потому что это агент, а не «какое-то приложение».
- **Иконок в строках списка сессий.** Речь про меню; в списке значков своя
  система (кружок состояния, `▣`, `↗`), и подмешивать к ней логотипы
  приложений незачем.
- **Настройки «показывать иконки».** Галка, которую никто не выключит, стоит
  дороже, чем весит.
