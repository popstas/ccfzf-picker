# Сессии из git worktree наследуют проект — дизайн

Три репозитория: ccfzf (агрегатор — основная работа), windows11-manager
(иконка, значок, профиль по владельцу), ccfzf-picker (значок worktree у имени).

## Зачем

Запрос Стаса 25.11: worktree «не определяются как home проекты, отображаются
как untyped. Как можно сделать для них наследование типа? Цель: чтобы они
получали иконку проекта, тип профиля, присоединялись к дереву сессий в
пикере». И: «в пикере worktree должны отмечаться иконкой возле заголовка».

Исполнители head работают в worktree рядом с основным клоном
(`~/projects/js/ccfzf-picker.bell-children`). Такой каталог не потомок
проекта, и сегодня:

- ccfzf: `project_owner` (`ccfzf:547`) и `owners_of` (`ccfzf:531`) ищут
  проект среди **предков** `cwd` — сосед не находится, владелец = сам
  worktree, тип пуст, секция `untyped`. Head стоит в `home`, ребёнок в
  `untyped` — дерево head/дети в пикере рвётся между секциями.
- windows11-manager: иконка, значок `badges` и профиль терминала — по
  **точному** `cwd` (`projectFor` в `src/claude-wt/window-icons-helpers.js:66`,
  `profileForCwd`). Worktree не получает ничего.
- Обход, который Стас уже сделал руками: тип, поставленный из `^K` на
  сессию worktree, менеджер дописал отдельной записью worktree в
  `claudeWt.projects` (сейчас так `ccfzf-picker.bell-children`,
  `windows11-manager.bell-children` → `home`). После выкатки — вычистить.

## Цели

- Сессия из worktree принадлежит основному проекту: его тип (секция пикера,
  место в дереве head), его иконка окна и значки `badges`, его профиль
  терминала.
- У worktree нет своей строки проекта в пикере: его сессии видны под
  основным проектом (решение Стаса 1a, 25.11).
- Строка сессии из worktree помечена значком у имени; в подсказке — ветка и
  путь worktree.
- Работает для любого расположения worktree: сосед `<репо>.<суть>`,
  `.worktrees/`, `.claude/worktrees/`.

## Не цели

- Не трогается, где head/coord создают worktree.
- Хоткеи проектов, `/p`, снимки — без изменений.
- Мак: макосовский трекер не трогается; мак недоступен.

## Анти-цели

- Подмодуль (`vendor/ccfzf`, у него тоже файл `.git` с `gitdir:`), принятый за
  worktree, — его сессии уехали бы в чужой проект.
- Опрос `.git` по сети в такте менеджера (бюджет опроса, `mtime` по SMB врёт).
- Сессии удалённого worktree, всплывшие отдельными проектами после
  `git worktree remove`.

## Подходы (решение Стаса 25.11: «да» на рекомендованный)

1. **Выбран — владельца считает ccfzf, остальные берут готовое.** ccfzf
   живёт на машине агрегатора, рядом с каталогами, и читает `.git` локально;
   владелец едет в `--state` (пикер) и в дамп `~/.ccfzf.sessions.json`
   (менеджер).
2. Отвергнут — менеджер читает `.git` сам через сетевой диск: сетевой опрос в такте.
3. Отвергнут — по имени `<репо>.<суть>`: угадывание, ломается на точке в имени
   репо и на других местах worktree.
4. Отвергнут — владелец пишется при `session-spawn`: покрывает только детей
   head, не worktree, открытый руками.

## Как

### ccfzf

- **Распознать worktree.** От `cwd` вверх до первого `.git`. Это файл с
  `gitdir: <путь>` **и** в `<путь>` есть файл `commondir` → worktree; основной
  репо = родитель каталога, на который указывает `commondir` (относительно
  `<путь>`), т. е. `<main>/.git` → `<main>`. Файл `.git` без `commondir` в
  gitdir — подмодуль, не worktree. Каталог `.git` — обычный клон.
  Ветка — из `<путь>/HEAD` (`ref: refs/heads/<ветка>`; отделённый HEAD — без
  ветки).
- **Своя запись важнее наследства** (решение head): если `cwd` worktree сам
  стоит в `projects[]` трекера (точное совпадение) — владелец он, как
  сегодня. Так долгоживущему worktree можно дать свой тип и иконку. Отсюда:
  чистка ручных записей worktree из конфига (раздел «После выкатки») —
  обязательная часть выкатки, без неё эти два worktree наследовать не начнут.
- **Владелец.** `project_owner` и `owners_of` для сессии из worktree считают
  от пути внутри основного репо (`<main>` + относительный путь `cwd` от
  корня worktree), а не от `cwd`: тогда тип, проект-владелец и список сессий
  проекта совпадают с основным. `projectCwd` выставляется (он и так пишется,
  когда владелец ≠ `cwd`).
- **Строки проектов.** `project_rows` не заводит строку для каталога
  worktree: его сессии идут в строку основного проекта (1a).
- **Новое поле сессии** `worktree: {path, branch}` (`branch` пустой у
  отделённого HEAD; поля нет у сессий не из worktree) — в `--state` и в
  дампе.
- **Дамп.** К записи сессии добавить `projectCwd` (только когда ≠ `cwd`) —
  его читает менеджер.
- **Удалённый worktree.** Каталога нет → `.git` не прочитать. Чтобы сессии
  из истории не всплыли отдельными проектами, ccfzf помнит найденное:
  `cwd worktree → {main, branch}` в файле под `~/.ccfzf/` (решение head,
  можно иначе — см. «строителю»), и берёт оттуда, когда каталога уже нет.
  Память копится с выкатки; worktree, удалённые раньше, не восстанавливаются
  (только угадыванием по имени, а оно отвергнуто) — их старые сессии остаются
  как сегодня (решение head). Разового засева не нужно: живые worktree
  попадут в память на первом же такте.
- **Только машина агрегатора** (решение head): распознавание — для POSIX-путей. Местный
  источник пикера (`vendor/ccfzf` через `local_ccfzf.rs` на Windows/маке)
  worktree не распознаёт и ведёт себя как сегодня; Windows-пути в `gitdir:` не
  разбираются.
- Стоимость: `.git` читается на каждый уникальный `cwd` такта; кэшировать по
  `cwd` в процессе (у `--state` раз в секунду их десятки).

### windows11-manager

- Сессия из дампа несёт `projectCwd`; иконка, `badges` и профиль терминала
  ищутся по `projectCwd || cwd` (`projectFor`, `projectIconFor`, `iconFor`,
  `profileForCwd` там, где известен id сессии: подъём `resumeClaudeSession`,
  restore). Точное совпадение остаётся правилом — меняется только ключ.
  Ключ — `projectCwd` для **всех** сессий, не только worktree (решение head):
  `projectCwd` ccfzf уже пишет и подкаталогам проекта, тип они уже
  наследуют, и иконка с профилем, не унаследованные следом, расходились бы с
  типом. Следствие: сессия в подкаталоге или подмодуле без своей записи
  (`ccfzf-picker/vendor/ccfzf`) получит иконку и профиль ccfzf-picker — так же,
  как сегодня получает его тип.
- Явная иконка/значок от агента (`session-icons.json`) по-прежнему важнее.
- `claude-project-type` не трогается: пикер и так шлёт `projectCwd`
  (`projectTypeTarget`) — после правки это основной репо.

### ccfzf-picker

- Значок worktree у имени сессии — подписью в строке имени, тем же родом,
  что `head:<имя>` (`headNameHtml`) и задача (`taskNameHtml`) в
  `frontend-src/session-glyph.js`; `title` — `Git worktree: <branch> — <path>`
  (по-английски). Без поля `worktree` — пусто, строка как сегодня.
- Тип, секция и дерево берутся из `projectType`/`projectCwd`, как сейчас, —
  отдельной логики не нужно; проверить, что сессия ребёнка в worktree встаёт
  под head в его секции.

- Подпись каталога (`projectLine`) у сессии из worktree — имя **основного**
  проекта, а не basename worktree (решение head): сессия принадлежит ему
  (1a), а что это worktree, говорит значок; ветка — только в подсказке
  значка. Правка — в общей `projectLine`, по наличию `worktree`.

Эскиз строки (узкий список):

```
● .bell-children-picker ⎇  head:co-picker-toggles   ccfzf-picker   12m
● hide-dimmed-windows-head                           ccfzf-picker    3m
```

Подсказка на `⎇`: `Git worktree: feat/bell-children — /home/…/ccfzf-picker.bell-children`.

`⎇` — U+2387 «alternative key», общепринятый знак ветки; если в системных
шрифтах Windows (Segoe UI Symbol) он не рисуется — inline SVG в духе
`action-icons.js`, обе темы (токены `theme.css`).

### После выкатки (head, по оку Стаса)

- Вычистить из живого `claudeWt.projects` на nb
  (`%APPDATA%\windows-mqtt\windows11-manager.config.yaml`) записи, чей `cwd` —
  worktree (сейчас `…/ccfzf-picker.bell-children`,
  `…/windows11-manager.bell-children` и что найдётся): `scp`, бэкап
  `.bak-<дата>-worktree-types`, правка, `cmp`.

## Порядок и выкатка

1. ccfzf (поле в `--state` и дампе) — мерж в main = выкатка на машину агрегатора (основной
   каталог ccfzf = живой агрегатор). Бамп `vendor/ccfzf` в пикере.
2. windows11-manager — `deploy-pc.sh --no-build` (только node) на nb.
3. ccfzf-picker — `deploy-win.sh` на nb. Мак пропущен.

Старые читатели нового поля не видят и ведут себя как сегодня.

## Проверка вживую

- `ccfzf --state`: сессия в `ccfzf-picker.bell-children` — `projectCwd` =
  `…/ccfzf-picker`, `projectType` = тип основного, `worktree.branch` =
  `feat/bell-children`; строки проекта `ccfzf-picker.bell-children` нет.
  Подмодуль `vendor/ccfzf` — без `worktree`.
- nb: окно исполнителя в worktree — иконка проекта ccfzf-picker и профиль wt
  проекта (до чистки конфига — проверять на worktree, которого в конфиге нет:
  у двух вписанных руками своя запись важнее наследства).
- Пикер: значок `⎇` у имени, подсказка с веткой; ребёнок под head в его
  секции.
