# Просьбы к менеджеру по HTTP: связка работает без MQTT

2026-08-23

## Задача

Связка claude-wt не работает без брокера MQTT. Пять просьб пикера к оконному
менеджеру — подъём окна, отметка «непросмотрено», открытие сессии,
восстановление снимка, раскладка — уходят публикацией в MQTT и только ею.
Нет брокера — Enter на строке сессии Windows-машины тихо откатывается на
локальный запуск терминала (`chooseOpenTransport` в
`frontend-src/open-transport.js`), и это не ошибка, а другое поведение,
которое легко принять за «доехало».

Второе, менее заметное: **у публикации в MQTT нет ответа**. Рефрен повторён в
коде windows11-manager четыре раза (`src/commands/claude-commands.js:141, 189,
275, 289`) и в комментариях пикера столько же. Отсюда главное свойство всех
поломок связки: рассогласовали базу топика, имя команды или формат id — человек
видит одно и то же, «нажал, ничего не произошло». Различить причину можно
только по логу трея на той машине.

## Что уже есть, а чего нет

Разведано 2026-08-23 по коду трёх репозиториев.

| Факт | Где |
|---|---|
| HTTP-сервер в windows11-manager **написан**: порт 9722, маршруты `/claude-wt/focus`, `/session-open`, `/session-unread`, `/snapshot-restore`, `/restore`, тот же `createRouter(buildCommandMap(...))`, что у MQTT | `windows11-manager/src/http-server.js` |
| Его никто не поднимает: трей спавнит только `claude-wt watch` и `mqtt` | `tauri-app/src-tauri/src/lib.rs:1533` |
| Пикер в MQTT **только публикует**, никогда не подписывается | `src-tauri/src/mqtt.rs`, публичных функций пять |
| `startMqttService` без `W11M_MQTT_HOST`/`W11M_MQTT_BASE` **не поднимается вовсе** — вместе с ним не заводятся автопостановщик, сторож демона и HA-экспорт | `src/mqtt/service.js:29-32` |
| Маковский трекер HTTP-сервера не имеет: в зависимостях только `rumqttc` | `macos-windows-manager/src-tauri/Cargo.toml` |
| HTTP-клиента в пикере нет ни одного | `src-tauri/Cargo.toml` |
| Агрегатор строит `windowHosts[]` с полями `host`, `pid`, `canFocus`, `openSession`, `mqttBase` | `vendor/ccfzf/ccfzf:887` |

## Решение и его граница

**Меняется только направление пикер→менеджер.** Пять просьб получают второй
транспорт — HTTP, — и он становится основным там, где адрес известен.

**Направление менеджер→Home Assistant→панель остаётся на MQTT целиком**, и это
не компромисс: MQTT Discovery, retained-топики слотов и сводки, LWT-доступность
и соседние модули дома (`power`, `keys`, `filewatch` в windows-mqtt)
воспроизвести по HTTP нечем. Retained-состояние и завещание брокеру — свойства
транспорта, а не протокола поверх него.

Отсюда ответ на вопрос «есть ли у MQTT преимущества перед HTTP»: **есть, но в
другой половине связки.** В половине пикер→менеджер HTTP строго лучше —
появляется ответ на просьбу, исчезает согласование баз топиков, и связка
перестаёт зависеть от брокера в той работе, где брокер не нужен.

Маковский трекер остаётся на MQTT. Отдельного условия про macOS для этого не
понадобится — см. «Выбор транспорта».

## Как адрес доезжает до пикера

Той же дорогой, что `mqttBase` и `projects`, — файлом трекера через агрегатор.
Новых каналов не заводится.

```
windows11-manager: buildWindowsFile → http: { port }
        ↓ файл трекера
ccfzf: read_windows → windowHosts[].http
        ↓ ccfzf --state по ssh
ccfzf-picker: trackerHosts(state) → выбор транспорта
```

Три правки, каждая — одно поле:

1. **windows11-manager**, `src/claude-wt/windows-file-helpers.js`: ключ `http`
   в корне файла, рядом с `host`/`pid`/`generated`. Внутри только `port`: хост
   читатель уже знает, это поле `host` той же записи. Значение берётся из
   `config.httpPort`.

   Ключ этот — **объявление о намерении, а не доказательство**, и обманчиво
   выглядит местом, где нужна проверка живости. Файл трекера пишет демон
   (`claude-wt watch`), а http-слушатель живёт в служебном процессе: демон о
   его состоянии не знает и узнавать не должен — это лишний опрос в цикле, за
   который в этом проекте уже заплачено правилом «бюджет опроса».

   Проверять и нечего. Mqtt-клиент живёт в **том же самом** служебном
   процессе, что и http-слушатель: лежит служба — мертвы оба транспорта, и
   откат на MQTT спасал бы ровно ноль случаев. Единственная разница видна
   человеку и она в пользу HTTP: отказ соединения пикер покажет, а публикация
   в лежащий брокер до 2026-08-23 просто молчала.
2. **ccfzf** — свой репозиторий, в пикер приезжает сабмодулем `vendor/ccfzf`:
   переложить поле в запись `windowHosts` рядом с `mqttBase`,
   `openSession`, `canFocus`. В запись *окна* оно не кладётся: адрес — свойство
   машины, а не окна. `mqttBase` дублируется в записи окна по историческим
   причинам, и повторять эту ошибку незачем.
3. **ccfzf-picker**: `trackerHosts()` уже возвращает эти записи целиком;
   появляется чтение поля `http` и сиблинги у `place_order::tracker_base` и
   `session-windows.js:mqttBaseFor`.

**Старая версия любого из трёх звеньев означает отсутствие поля, то есть откат
на MQTT.** Это не отдельно придуманный запасной ход, а то же правило, по
которому уже живёт `mqttBase`: пустое значит «спроси свой конфиг». Согласовывать
руками нечего — ни портов в конфигах, ни списка машин. Ровно на таком
согласовании ломается сегодня база топика: она задана дважды, в двух проектах,
и автосогласования между ними нет.

## Служебный процесс в windows11-manager

`startMqttService` расщепляется по признаку «нужен ли брокер», и процесс
перестаёт быть mqtt-процессом.

| Заводится | Всегда | Только при настроенном брокере |
|---|---|---|
| роутер команд (`buildCommandMap`) | да | |
| http-слушатель | да | |
| автопостановщик, сторож демона | да | |
| mqtt-клиент, LWT, `publishDone` | | да |
| HA-экспорт, статистика, `notify` | | да |

Автопостановщик и сторож демона переезжают в графу «всегда» не за компанию: в
коде уже написано, что брокер этим двоим не нужен и ждать подключения они не
должны (`src/mqtt/service.js:55-57`). Сегодня они всё равно не заводятся без
`W11M_MQTT_HOST` — потому что вся функция выходит раньше.

Без брокера `haExport` остаётся заглушкой той же формы, что стоит сегодня в
`http-server.js` (`{ slots: () => [], slotOff: () => {}, refresh: () => {} }`).
**Это не дыра.** Слоты нужны ровно одной команде — `claude-focus-slot`
(`sessionIdForSlot(slots())`, `src/commands/claude-commands.js:245`), — а
приходит она с панели openHASP, то есть по тому самому транспорту, которого в
этом случае нет. `claude-focus` ищет сессию по id и слотов не спрашивает.

Отсюда — почему объединение обязательно, а третий процесс исключён. В
отдельном процессе `http-server` заглушка слотов стояла бы **при живом
брокере**, и `claude-focus-slot` ломался бы молча. Плюс два процесса,
разбирающих одни и те же команды, — ровно тот класс поломок, что уже стоил
здесь отладки: `restore` запускает каждое приложение дважды, а два издателя
`…/claude/slot/N` дёргают строку на панели между двумя сессиями.

Три следствия, каждое надо сделать явно:

- **Трей спавнит ребёнка безусловно.** Проверка настроек перед запуском
  («без хоста, темы или пути проекта поднимать нечего», `lib.rs:1526`)
  снимается. Переменные `W11M_MQTT_*` продолжают передаваться, но становятся
  необязательными.
- **Подпись в трее переименовывается.** `MQTT: running/stopped` и тумблер
  `Start/Stop MQTT` называют процесс, который теперь больше, чем MQTT.
  Становятся `Service`. Строки человеку — английские.
- **CLI-подкоманда `http-server` удаляется** из `src/index.js`. Модуль
  `src/http-server.js` остаётся — он и есть слушатель, — уходит только точка
  входа, поднимающая его отдельным процессом со своими слотами. Порт переезжает
  в конфиг ключом `httpPort` верхнего уровня, умолчание 9722.

Про «верхнего уровня» отдельно, потому что это уже ловилось: ключи
`placeWindowOnOpen`, `notifyPlaced`, `publishStats`, `homeassistant` читаются
как `config.<ключ>`, и вложенные внутрь `claudeWt` они молча ничего не делают.
`httpPort` — из той же семьи.

## Выбор транспорта в пикере

По наличию адреса, одна попытка, без ретраев:

```
есть windowHosts[host].http  →  POST http://<host>:<port>/claude-wt/<route>
нет                          →  публикация в MQTT, как сейчас
```

Мак попадает во вторую ветку сам, без единого условия про macOS: у маковского
трекера http-сервера нет, поля он не пишет.

**Ретраев по второму транспорту нет намеренно.** Таймаут на задумавшемся
сервере неотличим от падения, а `claude-session-open` не идемпотентна: повтор
открыл бы человеку второй терминал. Лучше сказать «не вышло», чем сделать
дважды, — то же правило, по которому публикация в MQTT ждёт PubAck пять секунд
вместо того, чтобы уходить и забывать.

Отказ HTTP (соединение, таймаут, не-2xx) уходит в тот же показ ошибки в
статуслайне, каким пикер уже отвечает на «mqtt не настроен» и на неудачную
публикацию. Тело ответа не разбирается: HTTP даёт возможность рассказать
человеку, что именно не так, но это отдельная задача, и брать её вместе с
транспортом значит смешать две правки в одной.

Правки в пикере:

- **`src-tauri/src/manager_http.rs`** — новый сосед `mqtt.rs` с теми же пятью
  функциями (`focus`, `unread`, `open`, `restore`, `place`) и тем же потолком
  5 секунд. Тела просьб не меняются вовсе.

  Маршруты приёмника покрывают **четыре просьбы из пяти**: в таблице `ROUTES`
  (`src/http-server.js`) стоят `/claude-wt/focus`, `/session-open`,
  `/session-unread`, `/snapshot-restore` — и нет пути для `claude-place`.
  Сосед `/place` там есть, но это команда окон windows11-manager, а не
  claude-wt, и уводить в неё раскладку пикера нельзя. Пятый маршрут заводится
  этой правкой.
- **Клиент — `ureq` с `default-features = false`.** TLS не нужен: сеть
  локальная, адрес приезжает от своего же трекера. Порядок десятка крейтов к
  323 имеющимся; ни `tokio`, ни `rustls`. Своего разбора HTTP не заводим —
  сервер свой и форма фиксирована, но собственный HTTP всегда выглядит меньше,
  чем оказывается.
- **Развилка на каждый вызов** — рядом с `mqtt::resolve_base(...)` в шести
  местах `main.rs`. Адрес приезжает из фронтенда тем же способом, каким уже
  приезжает `base`. Существующая дорога `base` не трогается: она и есть откат.
- **`mqttConfigured` перестаёт быть правдой.** `chooseOpenTransport` и
  `canOpenRemote` в `frontend-src/open-transport.js` спрашивают «есть ли
  транспорт до менеджера», а не «настроен ли брокер». Без переименования
  параметра в `managerReachable` и правки самого условия пункт «Open on
  \<host\>» не появился бы на машине, где MQTT не настроен вовсе, — то есть
  ровно в том случае, ради которого всё и делается.
- Порядок «погасить пикер → выдать `ASFW_ANY` → послать просьбу» не меняется:
  он про пикер, а не про транспорт. Сторож `test/hide-before-request.test.js`
  расширяется на новую ветку.

## Безопасность: сознательно принятый риск

**HTTP-сервер остаётся без защиты и слушает все интерфейсы.**

`claude-session-open` принимает произвольный `cwd` и запускает по нему терминал
(`openClaudeProject`), то есть любое устройство в домашней сети может выполнить
команду на рабочей машине. У MQTT в этой установке есть хотя бы пароль брокера;
у HTTP не будет ничего.

Решение принято владельцем 2026-08-23 сознательно: сеть доверенная. Записано
здесь этими словами, чтобы при следующем чтении это не выглядело недосмотром, и
чтобы вопрос «а почему тут нет токена» имел ответ. Дешёвый путь, если решение
переменится: менеджер генерит токен, кладёт его в файл трекера рядом с портом,
пикер шлёт заголовком — канал тот же ssh, и согласовывать руками по-прежнему
нечего.

**Абзац выше называет одну команду, а слушатель отдаёт весь `buildCommandMap` —
16 маршрутов.** `ROUTES` в `windows11-manager/src/http-server.js` разбирает не
только пятёрку, ради которой заводился этот транспорт (`/claude-wt/focus`,
`/claude-wt/session-open`, `/claude-wt/session-unread`,
`/claude-wt/snapshot-restore`, `/claude-wt/place`), но и одиннадцать оконных
команд MQTT-приёмника целиком: `/place`, `/placeAll`, `/store`, `/restore`,
`/clear`, `/open`, `/focus`, `/desktop`, `/reload`, `/autoplace`,
`/claude-wt/restore`. Роутер общий (`createRouter(buildCommandMap(...))`) — так
он и был написан для MQTT, и заводить второй, урезанный, значило бы держать
два списка команд, которые разойдутся при первой же правке.

Поверхность это не расширяет сверх уже принятого риска: до этой правки все
шестнадцать команд были доступны так же, публикацией в тот же роутер по MQTT
— разница только в том, что у брокера в этой установке есть пароль, а у http
нет ничего. Тот же размен, тем же словом принятый владельцем; отдельного
решения про остальные одиннадцать маршрутов не требовалось и не принималось.

## Что сломается молча и чем это ловится

Вся связка ломается молча по одной причине: у публикации в MQTT нет ответа.
HTTP эту причину убирает, но заводит четыре новых молчания.

| Молчание | Сторож |
|---|---|
| Поле `http` потерялось в агрегаторе: пикер тихо откатился на MQTT, и всё «работает», просто не тем транспортом | тест в ccfzf: поле доезжает из файла трекера в запись `windowHosts` |
| Маршруты `ROUTES` разошлись с хвостами топиков `mqtt.rs`. Сегодня совпадают один в один, общего источника правды нет — та же беда, что у имён команд и у `TERMINAL_NAMES` | тест в пикере, сверяющий свой список маршрутов с `ROUTES`; прецедент — `test/terminal-name.test.js`, уже сверяющий копию в Rust с чужим реестром |
| Служебный процесс не поднялся без брокера: задача не решена вовсе, а выглядит как «менеджер лежит» | тест `startService` без `W11M_MQTT_*`: роутер и http есть, mqtt-клиента нет |
| `claude-focus-slot` при живом брокере получил заглушку слотов: панель перестала работать, а пикер работает | тест: при настроенном брокере `slots()` настоящий |

Плюс один тест на само правило выбора: **при наличии `http` публикации в MQTT
не происходит.** Иначе однажды заведётся дублирование «на всякий случай», и
сессия начнёт открываться дважды.

Порт, положенный в конфиг внутрь `claudeWt` вместо верхнего уровня, тестом не
ловится — только строкой в документации, как уже сделано для соседних ключей.

## Выкатка

Порядок вынужденный, снизу вверх по потоку данных:

1. **ccfzf** — коммит и пуш в его собственном репозитории; на машине
   ssh-агрегатора он работает из рабочего каталога, деплоя у него нет. В пикере
   сдвигается указатель сабмодуля.
2. **windows11-manager** — `./data/scripts/deploy-pc.sh` (правится и Rust трея,
   и node). Первым: пикер без менеджера ничего не проверит.
3. **ccfzf-picker** — `deploy-win.sh` и `deploy-mac.sh --all` параллельно и в
   фоне, все три машины.

**Живая проверка, ради которой всё и делается.** Остановить брокер (или снять
`W11M_MQTT_HOST`) и нажать Enter на строке сессии Windows-машины. Сегодня это
молча откатывается на локальный терминал, то есть выглядит как «работает».
После правки сессия обязана открыться **на трекере, с профилем Windows Terminal
из `claudeWt.projects`**. Профиль и есть отличие: локальный запуск его теряет.

План работ заканчивается отдельной задачей «Деплой на Windows» — правило
связки: код лежит на машине разработки, а работает на Windows, и до выкатки
правка не проверена ничем, кроме тестов.

## Что в объём не входит

- **Вынос MQTT из связки целиком.** Требует переписать экспорт в Home Assistant
  на REST вместо Discovery и путь до openHASP; панель и Home Assistant живут на
  третьей машине. Это отдельный проект, и выигрыш от него неочевиден.
- **HTTP-сервер в macos-windows-manager.** Маки остаются на MQTT. Появится
  сервер — правило выбора транспорта подхватит его без единой правки в пикере:
  условие смотрит на поле, а не на систему.
- **Показ человеку причины отказа.** HTTP отвечает телом, и это можно
  показать в статуслайне. Отдельная задача.
- **Токен для http-сервера.** См. «Безопасность».
