# Снимки раскладки в ccfzf-picker

Дата: 2026-08-08. Задача из `docs/TODO.md`: «Скопировать функции snapshots из
windows-mqtt в ccfzf-picker, также взаимодействие с windows11-manager».

## Зачем

Демон windows11-manager запоминает раскладку открытых окон Claude Code —
снимок пишется, когда состав сессий на экране устоялся. У пикера в windows-mqtt
для них был режим `/s`: список снимков и Enter, поднимающий раскладку целиком.
Пикер windows-mqtt отдал свою роль ccfzf-picker, и режим уехал вместе с ним —
здесь его нет.

## Что мешает перенести напрямую

Список снимков в windows-mqtt не ездит по MQTT вовсе. `sendSnapshots()` в
`src/modules/windows.js` отвечает через `mqtt.sendEvent()`, а это запись в
stdout своему Tauri-процессу, который перевыпускает её событием в свой webview.
Стороннему читателю там взяться неоткуда.

Восстановление, наоборот, уже доступно: подписка на
`<base>/windows/claude-snapshot-restore` есть, и публикация в неё — законный
способ попросить.

## Устройство

### Дорога данных: снимки едут в файле оконного трекера

Той же дорогой, что уже везёт `window` и `focusedAt`. Пикер ни у кого не
спрашивает — всё приезжает в ответе агрегатора; своего http-клиента у него нет
и не должно появиться (`CLAUDE.md`).

```
демон windows11-manager → windowsFile (+snapshots) → ccfzf --state → пикер
```

**windows11-manager.** `snapshotTick` в `src/claude-wt/snapshotter.js` уже
держит снимки в модульном кэше: файл читается один раз за жизнь процесса,
дальше только пишется оттуда же. Новый экспорт `currentSnapshots()` отдаёт этот
кэш без ввода-вывода — `listSnapshots(cfg)` для тика не годится, он читает файл.
Кэш холодный (демон только поднялся, `snapshotTick` ещё не отработал) —
`currentSnapshots()` отдаёт пустой список, а не читает файл сам: первый же тик
его заполнит, а до тех пор поле в файле трекера просто пустое.

`buildWindowsFile` (`src/claude-wt/windows-file-helpers.js`) получает снимки
аргументом и кладёт в файл поле верхнего уровня, рядом с `windows`:

```json
{
  "host": "…", "pid": 123, "generated": 1754640000,
  "windows": { "…": {"title": "…", "desktop": 1, "lastSeen": 0, "focusedAt": 0} },
  "snapshots": [
    {"id": "…", "created": 1754640000,
     "sessions": [{"id": "…", "cwd": "/home/…/ccfzf-picker", "title": "…"}]}
  ]
}
```

Вид обрезанный: `bounds`, `desktop` и `monitor` остаются в файле снимков.
Читателю они не нужны — восстановление живёт на той же машине и читает свой
файл напрямую, — а ехали бы в каждом тике `--state`, раз в секунду.

`windowsFingerprint` учитывает состав снимков наравне с окнами. Без этого новый
снимок доезжал бы только сердцебиением — до тридцати секунд. Снимки редкие
(debounce 60 с), лишних записей это не даёт.

**ccfzf** (`~/projects/shell/ccfzf`, отдельный репозиторий). `read_windows`
возвращает снимки четвёртым значением. Отбраковка мусора — по тем же правилам,
что и всё остальное в этой функции: не тот тип, нет ключей — пустота, ни ошибки,
ни строчки в stderr. Список сессий обязан пережить любой мусор в добавке.

Правило TTL общее: протухший файл (`WINDOWS_TTL`) не даёт ни окон, ни снимков —
одна проверка на входе, отдельной ветки для снимков нет.

`--state` кладёт `snapshots` рядом с `windowHost` и `windowPid`.

**Пикер.** `frontend-src/state-shape.js` учит форму. Новый
`frontend-src/picker-snapshots.js` строит строки.

### Обратная дорога: восстановление

Просьба уходит публикацией, ответа у неё нет — как у фокуса и у отметки
«непрочитано».

**Пикер, Rust.** `src-tauri/src/mqtt.rs` сейчас умеет ровно одно тело:
`publish()` жёстко клеит `{"id": id}`. Обобщается до передачи готового payload;
поверх остаются три тонкие обёртки — `focus`, `unread`, `restore`. Хвост топика
`/windows/claude-snapshot-restore` — приёмник его уже слушает.

Тело:

```json
{"id": "<снимок>"}                        // весь снимок
{"id": "<снимок>", "sessionIds": ["…"]}   // одна сессия из снимка
```

Новая команда Tauri рядом с `focus_window_mqtt` и `unread_session_mqtt`.

**windows-mqtt.** `claudeSnapshotRestore` учится разбирать JSON рядом с сырой
строкой. Сейчас он делает `String(message ?? '').trim() || 'last'`, и объект от
пикера ушёл бы в `restoreSnapshot` литералом `{"id":"abc"}` вместо id снимка.
Прецедент рядом — `claudeFocusSlot` разбирает оба вида по той же причине.
Разобранный `sessionIds` уходит в `restoreSnapshot({id, sessionIds})`.

С панели openHASP по-прежнему прилетает пустота (кнопка Restore last) или сырой
id — эта ветка не меняется. Ограничитель на подписке остаётся: он про дребезг
физической кнопки платы, Enter в списке ему не мешает.

**windows11-manager** здесь не трогается: `restoreSnapshot({id, sessionIds})`
готов, `sessionIds` он уже принимает.

Пикер после публикации гасится, как и на фокусе. Итог восстановления не
показывается: за него пришлось бы заводить подписку в пикере, которой вся эта
схема и избегает. Не сработало — видно на экране, окна там же.

### Пикер: режим и раскладка

**Режим живёт в строке поиска**, как `/a`. `frontend-src/picker-mode.js`
расширяется до `/(all|a|s|snapshots)`, `parseQuery` возвращает третий режим —
`snapshots`. Хвост `(\s+|$)` уже на месте: `/src` в режим не проваливается.
Стирание префикса возвращает к сессиям само собой, отдельного выхода нет.

**Строки** — плоский список, без механики сворачивания:

```
10:31 · 2026-08-08 · 5 sessions · 3 не открыты     ← Enter: весь снимок
  ccfzf-picker    ~/projects/js/ccfzf-picker
  windows-mqtt    ~/projects/js/windows-mqtt       ← Enter: одна
  shome           ~/projects/smarthome  ▣ открыта  ← тусклая, Enter поднимает окно
```

Заголовок снимка — строка группы (ключ `g:snap:<id>`), сессии — обычные строки
(ключ `snap:<id>:<sid>`). Ключи разведены, чтобы `picker-list-sync.js` правил
только отличающиеся строки: список тикает раз в секунду и в этом режиме тоже.
`list.innerHTML` целиком здесь так же запрещён, как и в списке сессий.

«Уже открыта» считается пересечением с сессиями текущего ответа `--state`, у
которых есть поле `window`. Отдельного `openSessionIds` возить неоткуда и
незачем — в windows-mqtt он брался вторым вызовом `claudeWtSessions()`, здесь
всё уже в том же ответе.

Enter на открытой сессии уходит в существующую ветку фокуса, а не в
восстановление: окно есть, поднимать его — уже описанное действие, и
восстановление её всё равно пропустило бы (`skipped`).

**Поиск** фильтрует по строкам сессий: снимок остаётся в списке, пока в нём есть
хоть одна подошедшая; снимок без подошедших уходит из выдачи целиком вместе с
заголовком.

**Доступность** — `canFocus` (совпадение `windowHost` из конфига с `windowHost`
в ответе) и настроенный `mqtt`, оба сразу. Не выполнено — режима нет вовсе:
`/s` в строке поиска остаётся обычным поиском по сессиям, подсказки в
статуслайне нет. То же правило, по которому на маке не предлагается ветка
`focus`: поднимать раскладку на чужом экране бессмысленно, а Enter, который
молча ничего не делает, хуже отсутствующего режима.

## Что не делается

- **Хоткея «восстановить последний»** нет. Кнопка Restore last остаётся на
  панели openHASP, в пикере её эквивалента не заводится.
- **Ответа об итоге восстановления** нет — см. выше про обратный канал.
- **Своего чтения файла снимков** у пикера нет: файл лежит на Windows-машине, а
  ssh пикера ходит на pc-virt.

## Проверки

`npm test` (`node --test`, без зависимостей; `node --test test/` на этих
версиях Node не работает):

- разбор префикса `/s` и `/snapshots`, невлипание `/src`, возврат к сессиям по
  стиранию;
- сборка строк: пустой список снимков, снимок целиком открытый, пометки
  «открыта», счёт «не открыты» в заголовке;
- ключи строк — `g:snap:<id>` и `snap:<id>:<sid>`, разведены и стабильны;
- фильтр: снимок без подошедших сессий уходит вместе с заголовком;
- гейт доступности: нет `canFocus` или нет `mqtt` — режима нет;
- форма состояния (`state-shape.js`) на ответе со снимками и без них.

`cd src-tauri && cargo test`:

- топик и тело восстановления — тем же контрактным тестом, что сторожит
  `FOCUS_TOPIC` и `UNREAD_TOPIC`: опечатка в хвосте ничего не ломает на глаз,
  публикация проходит, а не слушает её никто.

В соседних репозиториях — их собственными тестами: `buildWindowsFile` и
`windowsFingerprint` в windows11-manager, `read_windows` в ccfzf, разбор тела
подписки в windows-mqtt.

Руками: `ccfzf --state | node scripts/check-state.js` на живом ответе, и полный
путь «`/s` → Enter → окна поднялись» на Windows-машине.

| Репозиторий | Что меняется |
|---|---|
| `windows11-manager` | `currentSnapshots()`, `buildWindowsFile`, `windowsFingerprint` |

через `schtasks`). Пикер — своими скриптами в `data/scripts/`.
