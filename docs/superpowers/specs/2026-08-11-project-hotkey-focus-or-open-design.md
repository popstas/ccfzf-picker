# Проектный хоткей поднимает окно, а не плодит сессии

Дата: 2026-08-11.

## Задача

Проектные хоткеи заработали (спека
[2026-08-11-project-hotkeys-through-aggregator](./2026-08-11-project-hotkeys-through-aggregator-design.md)),
но делают не то. `Ctrl+F11` на проекте, у которого сессия уже открыта, заводит
рядом вторую вместо того, чтобы поднять существующее окно.

Так было в windows-mqtt, и это правильное поведение: у проекта одно окно, и
хоткей — это «покажи мне проект», а не «дай ещё один терминал».

Причина прямая. Хоткей регистрирует Rust пикера
(`src-tauri/src/project_hotkeys.rs`), шлёт наверх событие `project-hotkey` с
каталогом, а страница (`sessions.html:1608`) безусловно зовёт `newSession(cwd)`.
Развилки «есть окно / нет окна» на этой дороге нет вовсе.

При этом сама развилка написана, работает и жива — в windows11-manager,
`openClaudeProject()` (`src/claude-wt/project.js:42`). Раньше её дёргал топик
`windows/claude-focus-project` из windows-mqtt; он вычищен вместе с остальным
claude-wt, но та же функция достижима живым топиком
`<base>/windows/claude-session-open` с телом `{action:'terminal', cwd}`
(`windows11-manager/src/commands/claude-commands.js:198`) — пикер этой дорогой
уже ходит для пункта меню «Open on \<host\>».

Значит задача не «написать логику», а «довести нажатие до неё».

## Что значит «у проекта есть сессия»

Открытое окно Windows Terminal с этим каталогом — ровно то, что уже считает
`pickOpenProjectSession`: среди сессий с `open === true` и точным совпадением
`cwd` берётся последняя по `focusedAt`, затем по `lastActivity`. Открытого окна
нет — новая сессия `claude -n <basename(cwd)>`.

Живая-но-без-окна сессия и давно закрытая сессия из истории новой не мешают:
для хоткея они значат «поднимать нечего». Это поведение windows-mqtt, и менять
его не за чем.

## Решение

Развилку принимает менеджер, а не пикер, и нажатие доводит до неё Rust, а не
страница.

```
Ctrl+F11 (RegisterHotKey)
   │
   ▼
on_shortcut → press(app, cwd)          project_hotkeys.rs
   │  дребезг ~1 с на комбинацию
   │  hide_window(app)
   │
   ├─ mqtt настроен ─→ allow_tracker_foreground(windowPid)
   │                   mqtt::open_project(broker, cwd)
   │                        │
   │                        ▼  <base>/windows/claude-session-open
   │                   {"action":"terminal","cwd":…}   без id
   │                        │
   │                        ▼  windows11-manager, правок нет
   │                   openProject → openClaudeProject
   │                        ├─ открытая сессия этого cwd → её стол + bringToTop
   │                        ├─ окно WT по заголовку        → тот же подъём
   │                        └─ ничего                      → claude -n <basename>
   │
   └─ mqtt не настроен ─→ emit("project-hotkey", cwd) → страница → newSession
```

### Почему решает менеджер, а не пикер

Пикер мог бы выбрать строку сам, по своему `lastState`, и позвать существующий
`focusSession`. Отвергнуто по двум причинам.

Первая: список у скрытого пикера устаревает. Такт фонового опроса растёт до
восьми минут (`BACKGROUND_MAX` в `poller.rs`), а при выключенном фоне скрытый
пикер не опрашивает вовсе. Хоткей нажимается ровно тогда, когда пикер скрыт, —
то есть решение принималось бы по самым старым данным, какие только бывают.

Вторая: правило «последняя сессия проекта» уже написано и покрыто тестами в
`pickOpenProjectSession`. Вторая его копия в JS разошлась бы с первой.

Заодно менеджер знает то, чего пикер не знает в принципе: профиль Windows
Terminal по каталогу (`claudeWt.projects` → `profileForCwd`) и виртуальный стол
окна. Сегодняшний `newSession` собирает `wt.exe` без `-p`, и профиль теряется —
это чинится тем же переходом, попутно.

### Почему зовёт Rust, а не страница

Хоткеи вешает Rust именно потому, что WebView2 у скрытого окна умеет усыплять
страницу целиком. Нажатие хоткея — это по определению момент, когда пикер
скрыт. Вести действие через страницу значило бы поставить ту же ловушку на шаг
дальше по дороге.

## Правки

### 1. `src-tauri/src/project_hotkeys.rs` — новая `press`

Замыкание `on_shortcut` вместо `emit("project-hotkey", cwd)` зовёт
`press(&handle, &cwd)`. Живёт она в этом же файле: она про нажатие хоткея, а не
про пикер вообще.

Порядок внутри `press`:

1. **Дребезг**, окно ~1 с, отметка на каждый каталог. `RegisterHotKey` на
   Windows повторяет `WM_HOTKEY`, пока клавиша удерживается, и все повторы
   приходят как `ShortcutState::Pressed` — сегодняшний фильтр по `Pressed` их не
   отсекает. Без окна удержанный `Ctrl+F11` даёт очередь просьб; а первые из них
   успевают отработать раньше, чем окно нового терминала появится на экране, то
   есть плодят терминалы вместо повторного подъёма одного.
   Решение самого дребезга — чистой функцией с явным временем, как
   `picker_toggle`: у неё есть тест, у пары `if`-ов внутри замыкания его не
   было бы.
2. **Погасить пикер**: `hide_window(app)`. Идемпотентна — уже скрытое окно не
   гасит повторно. До просьбы, а не после: показанный пикер оказался бы поверх
   поднятого окна, и это та же причина, по которой гасит до публикации
   `focusSession`.
3. **Просьба менеджеру**, если `mqtt` в конфиге настроен
   (`broker_from_config(&load_config()).is_configured()`): взять `windowPid` из
   кэша поллера (`Poller::snapshot()`), при `pid > 0` выдать
   `allow_tracker_foreground(pid)`, затем `mqtt::open_project(&broker, &cwd)` в
   `spawn_blocking`.

   Неизвестный `pid` отменяет грамоту, но **не** отменяет просьбу — в отличие от
   `canFocus` во фронтенде, где нулевой pid запрещает фокус целиком. Разница в
   цене ошибки: там альтернатива подъёму — открыть терминал у себя, здесь —
   молча завести второй терминал на проект, у которого окно уже есть. Поднятое
   без грамоты окно в худшем случае мигнёт кнопкой на таскбаре; лишний терминал
   человек будет закрывать руками.

   Отказ публикации — строкой в stderr. Ответа у просьбы нет по замыслу, как у
   фокуса и у восстановления снимка.
4. **Запасной путь**, если `mqtt` не настроен: прежний
   `emit("project-hotkey", cwd)`. Страница поднимает новую сессию — ровно
   сегодняшнее поведение, и единственное возможное без брокера. Подписка в
   `sessions.html` остаётся как есть.

### 2. `src-tauri/src/mqtt.rs` — новая `open_project`

Рядом с `open()`, тот же топик `OPEN_TOPIC`, тело собирает своя
`open_project_payload(cwd)`:

```json
{"action": "terminal", "cwd": "/p/site"}
```

Ключа `id` в теле **нет**, и звать `open()` с пустым id не надо. Сегодняшний
приёмник пустую строку и правда прочитал бы как «id нет»
(`found = id ? findSession(id) : null`, `claude-commands.js:205`), так что дело
не в поломке — дело в том, что тело перестало бы говорить правду. В этом файле
уже принято, что ключа без значения не бывает: ровно так сделан `cwd` в
`open_payload` («приёмник читает пустую строку как „каталога не знаем“, а
отсутствие ключа говорит то же самое честнее»). И приёмник, который завтра
станет проверять `id !== undefined`, на пустой строке сломался бы молча.

### 3. `windows11-manager` — правок нет

`claude-session-open` без `id` и с `cwd` уже уходит в `openProject(dir)` →
`openClaudeProject()`. Случай покрыт тестом
(`src/commands/claude-commands.test.js:180`).

Запасной поиск окна по заголовку внутри `openClaudeProject`
(`findOpenTerminalByTitle`) закрывает разрыв, пока дамп ccfzf не догнал только
что запущенную сессию: второе нажатие через секунду после первого поднимет
свежий терминал, а не заведёт ещё один.

## Тесты

- `mqtt.rs`: тело `open_project_payload` — есть `action` и `cwd`, ключа `id`
  нет. Ошибка здесь невидима глазом: лишний пустой `id` приёмник прочитал бы
  как «неизвестная сессия», и просьба ушла бы в ветку жалобы вместо открытия.
- `project_hotkeys.rs`: чистая функция дребезга — второе нажатие внутри окна
  отбрасывается, за его пределами проходит, разные каталоги друг друга не
  глушат.
- Фронтенд и `windows11-manager` — без новых тестов: подписка `project-hotkey`
  и приёмник просьбы не меняются.

## Чего в дизайне нет намеренно

- Выбора сессии на стороне пикера и второй копии правила «последняя сессия».
- Отметки «просмотрено» на нажатие: трекер поставит `focusedAt` сам, и она
  приедет обратно полем `window.focusedAt` внутри записи окна.
- Собственного клиента к windows11-manager: то же правило, которым уже запрещён
  http-клиент к оконному трекеру.
- Показа пикера перед грамотой (см. риск ниже) — это мигание на каждое нажатие,
  и заранее оно не оправдано.

## Риск, который проверяется только руками

`AllowSetForegroundWindow` разрешён процессу, который либо владеет передним
планом, либо получил последнее событие ввода. Пикер в момент нажатия хоткея не
на переднем плане и получил только `WM_HOTKEY` — засчитает ли это Windows,
из документации не следует.

Симптом отказа: строка `cannot grant foreground` в stderr пикера, а на экране
вместо поднятого окна мигает кнопка на таскбаре. Обход, если так и окажется, —
на миг показать окно пикера перед грамотой: тогда право есть по-честному.

Проверка: нажать хоткей на проекте с открытым окном, стоя в другом приложении и
на другом виртуальном столе.
