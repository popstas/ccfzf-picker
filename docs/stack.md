# Стек: что на чём написано и где граница

Пять частей, и у каждой свой расклад языков. Какую фичу какая часть даёт
человеку — в разделе «Stack» [README](../README.md); здесь — для того, кто
правит: в каком языке живёт поведение, где проходит шов и чем стороны
обмениваются. Шов почти везде — файл, процесс или сетевой запрос, а не общая
библиотека: части выкатываются порознь, и договор между ними — формат, а не
код.

| Часть | Rust | JS / Node | Python | shell |
|---|---|---|---|---|
| ccfzf-picker | оболочка Tauri: окно, трей, клавиши, опрос, транспорт | страница в webview; Node — только тесты и сборка | вшитый агрегатор исполняется; `make-icons.py` | — |
| ccfzf | — | — (Node только у чужого `ccstatusline`) | вся логика агрегатора | обёртка `ccfzf`, хуки агента |
| windows11-manager | трей Tauri и надзор за детьми | вся логика: демон, служба, http, MQTT, экспорт в HA | — | — |
| macos-windows-manager | всё | только страница настроек в webview | — | только скрипты выкатки |
| windows-mqtt | — | весь; в стек больше не входит | — | — |

## ccfzf-picker

**Rust (`src-tauri/`) — всё, что должно работать при скрытом окне или
трогает систему.** Окно и трей, глобальные хоткеи и проектные хоткеи
(`project_hotkeys.rs`), опрос источников (`poller.rs`, `state_source.rs`: ssh
или местный процесс), слияние ответов двух источников (`merge_state.rs`),
MQTT-клиент (`mqtt.rs`, rumqttc), прямой http до менеджера
(`manager_http.rs`), запуск терминалов, редактора и Claude Desktop, иконки
окон, чтение и запись `config.yaml`, `ui.json`, `seen.json`. Опрос живёт
здесь, а не на странице, по причине, которая записана в
[rules/state-sources.md](rules/state-sources.md): у скрытого окна webview
тормозит таймеры, а свёрнутое WebView2 усыпляет целиком.

**JS — страница в webview, а не Node.** `sessions.html`, `settings.html` и
`frontend-src/` исполняются браузерным движком окна: отрисовка, фильтры и
режимы, секции, сборка удалённой команды (`open-strategy.js`), выбор
транспорта (`open-transport.js`). Node в работающем пикере нет вовсе: он
нужен только `npm test` (`node --test`, без зависимостей) и скриптам сборки —
`prepare-frontend.js` раскладывает статику копированием, `check-version.js`
сверяет версию в трёх файлах. Отсюда UMD-шим у каждого файла
`frontend-src/`: один и тот же код грузится и `<script>`-ом, и `require` в
тестах.

**Граница — команды и события Tauri.** Страница зовёт `invoke(...)` (открыть,
поднять, сохранить настройки), Rust шлёт ей события (`state`,
`picker-shown`, `picker-hidden`, `config-changed`). Решения, которые можно
проверить без системы, лежат на стороне JS чистыми функциями; Rust у этих
решений только исполнитель.

**Python исполняется, но не пишется здесь.** Вшитая копия агрегатора
(`vendor/ccfzf`, `include_str!` в `local_ccfzf.rs`) — bash-обёртка вокруг
python-программы. На Linux и macOS пикер зовёт её через `bash`, на Windows
вырезает python-блок и запускает его напрямую: единственный `bash` там —
пускач WSL со своим `$HOME`. `scripts/make-icons.py` — разовый генератор
иконок, к работе не относится.

## ccfzf (агрегатор и хуки агента)

**Rust и Node здесь нет.** `ccfzf` — bash-обёртка с python-программой в
heredoc. Bash разбирает аргументы, ведёт fzf и делает `exec` в выбранную
сессию; python читает транскрипты, реестр сессий Claude Code, состояния
хуков и файлы трекеров и пишет JSON (`--state`, `--dump`). Тесты — pytest,
и вырезают тот же python-блок по тем же меткам `PYEOF`, что и пикер: метки —
часть договора, сломать их значит сломать местный источник пикера.

**Хуки — bash + jq, и с агрегатором у них один шов: файлы.** `wt-progress.sh`
пишет `<id>.state.json` на каждое событие агента, `claude-wt-agent-state.sh` —
`<id>.meta.json` на старте, `claude-wt-statusline.sh` — `<id>.status.json` из
входа статуслайна (иначе контекста и стоимости не достать: в stdin хука их
нет). Агрегатор только читает эти файлы; без них берёт состояние из хвоста
транскрипта. Хуки переезжают в репозиторий ccfzf; ставятся они записью в
настройки Claude Code руками.

Node в цепочке ровно один и чужой: `claude-wt-statusline.sh` после перехвата
отдаёт вход `ccstatusline`. К работе агрегатора он отношения не имеет.

## windows11-manager

**Rust (`tauri-app/src-tauri/`) — трей и надзор, логики claude-wt в нём
нет.** Меню трея, окно настроек, проверка обновлений, штамп версии, список
отслеживаемых окон в меню (читает тот же файл трекера, что и агрегатор) и
главное — запуск дочерних Node-процессов с автоподъёмом и бэкоффом
(`children.rs`): демона, службы и, если настроен интервал, периодического
автопостановщика. Своего MQTT-клиента у трея нет: состояние брокера он
узнаёт из служебных строк в stdout службы.

**Node (`src/`) — всё поведение.** Демон `claude-wt watch` (привязка окон к
сессиям, снимки, файл трекера, виртуальные столы) и служба `mqtt`
(http-слушатель `/claude-wt/*`, MQTT-клиент, экспорт в Home Assistant,
иконки окон и мигание на панели задач, расстановка новых окон, сторож
демона) — отдельные процессы. Служба поднимается и без брокера: тогда
работает по одному http, а MQTT-клиент и экспорт не заводятся.
Win32 они достают через нативный аддон `node-window-manager` (C++) и внешний
`VirtualDesktop11.exe`.

**Границ две.** Трей ↔ Node: процесс, настройки брокера переменными
окружения, обратно — stdout; разовые вопросы трей задаёт вызовом CLI
`node src/index.js …` и читает вывод. Демон ↔ служба: только файлы
(состояние, файл трекера), общей памяти у них нет. Пикер говорит со службой
по http или MQTT и с демоном не говорит вовсе — демона он видит только
через файл трекера, который приезжает в ответе агрегатора.

## macos-windows-manager

**Целиком Rust, хотя каталог проекта лежит среди JS.** `crates/mwm-core` —
чистая логика без macOS: сопоставление окон с сессиями, математика раскладок,
формат файла трекера, снимки; собирается и тестируется на любой системе.
`src-tauri` — всё, что требует macOS или сети: Accessibility (`ax.rs`),
доставка файла трекера по ssh, чтение дампа сессий, MQTT-клиент, трей.
Граница проходит по вводу-выводу: что можно проверить без мака, лежит в
`mwm-core`. JS — только страница настроек в webview.

С агрегатором он говорит тем же файлом трекера, что и windows11-manager, но
доставляет его сам, по ssh, а не через общий диск. MQTT только слушает —
поднять окно, отметить «непросмотрено», разложить; восстанавливать снимки не
умеет, поэтому снимки мака пикер поднимает сам (см.
[rules/snapshots.md](rules/snapshots.md)).

## windows-mqtt

Node, в стек не входит. Модуль `windows` вместе со всем claude-wt оттуда
удалён; осталось управление машиной по MQTT (звук, клавиши, питание, OBS и
соседи). Возвращать удалённое — не флаг, а откат из git с двух концов сразу,
иначе два процесса начнут разбирать одни и те же топики.

## Панель Home Assistant / openHASP

Своего кода в репозиториях стека у панели нет. Сущности сессий публикует
экспорт windows11-manager (MQTT Discovery), тексты на плату раскладывают
шаблоны Home Assistant, геометрию страницы — Node-RED; конфиг панели живёт
вместе с конфигом самого Home Assistant.
