# ccfzf-picker

Пикер сессий Claude Code на удалённой машине. Список берётся из `ccfzf --state`
по ssh, окно и хоткеи — Tauri 2. Начинать с [README.md](README.md).

## Сборка и тесты

```
npm test                      # фронтенд, node --test, без зависимостей
cd src-tauri && cargo test    # оболочка
```

`vendor/ccfzf` — сабмодуль: `local_ccfzf.rs` вшивает его `include_str!`-ом
в бинарь, и без `git clone --recurse-submodules` (или `git submodule update
--init` в уже склонированном каталоге) сборка не доходит до этой строчки —
падает весь крейт, а не только местный источник.

`node --test test/` на этих версиях Node не работает — только `npm test`.

## Выкатка

Собирает и перезапускает пикер на целевой машине `data/scripts/deploy-win.sh`
(Windows; соседний `deploy-mac.sh` — то же для маков). Каталог `data/` под
`.gitignore`: скрипты знают имена хостов и пути конкретной установки, а не
проекта, — и потому же остальное про них написано в них самих.

```
./data/scripts/deploy-win.sh              # обновить, собрать, перезапустить
./data/scripts/deploy-win.sh --no-build   # только перезапустить собранное
./data/scripts/deploy-win.sh --no-launch  # собрать, но не запускать
```

**Закончив задачу — выкатывать на все три машины, не дожидаясь просьбы.** Пикер
живёт значком в трее на каждой из них, и невыкаченная правка там просто не
видна; половина задач проекта и доказывается только живой проверкой — терминалы
на маке, перетаскивание секций, глифы в системных шрифтах, штамп сборки. Скрипта
два, машин три, и пускать их надо **параллельно и в фоне**: Windows собирается
около трёх с половиной минут, маки — около одной.

```
BRANCH=<ветка> ./data/scripts/deploy-win.sh
BRANCH=<ветка> ./data/scripts/deploy-mac.sh --all
```

Ветку называть явно: умолчание у скриптов `master`, и с ветки под ревью уехал бы
чужой код. Выкатывать **после пуша** — скрипт первым делом делает `git pull` на
целевой машине (правило ниже), то есть незапушенное не уедет вовсе. После
выкатки сказать, чего на машинах ещё нет: коммит, легший после запуска скрипта,
на экране не окажется.

Первым шагом скрипт делает `git pull` на целевой машине: выкатывается
запушенное, а не то, что лежит в рабочем каталоге. Собирает он `cargo build
--release`, а не `cargo tauri build` из README: `bundle.targets` в
`tauri.conf.json` — `["app"]`, это формат macOS, на Windows результат работы
сам `.exe`. Мимо tauri-cli не отрабатывает `beforeBuildCommand`, поэтому
`scripts/prepare-frontend.js` там зовётся отдельным шагом — без него в бинарь
вшилась бы прошлая статика.

Разложенную им статику cargo замечает сам: пути `frontend/` попадают в
dep-info крейта (`target/*/ccfzf-picker.d`, все 29 файлов), и правка страницы
крейт пересобирает. А вот сборочный скрипт про неё не знал: входы у него
объявлены явно, и каталог фронтенда лежит вне пакета. Отсюда штамп сборки в
трее показывал прошлую выкатку — сам `build.rs` не перезапускался. Чинит это
одна строка `cargo:rerun-if-changed=../frontend` в `src-tauri/build.rs`,
сторож — `build_script_watches_the_frontend`; поймать это поведением нельзя,
cargo решает про `build.rs` до того, как хоть что-то наше начнёт выполняться.

**Профиль `release` собран под выкатку, а не под витрину.** Стояли `lto = true`
и `codegen-units = 1`, и пересборка после правки одной строки занимала 208 с —
из них почти всё fat-LTO по дереву из 323 зависимостей в один поток. Правка
файла фронтенда стоила ровно столько же (214 с): статика вшивается на
компиляции, то есть обе дороги ведут в полную перекомпиляцию крейта. Замеры
(i5-12600K, 16 потоков) и цена в размере бинаря — таблицей в
`src-tauri/Cargo.toml` рядом с самим профилем; работу делает `incremental`,
итог — **37 с**. Оптимизации всей программы пикер не окупает: он спит и раз в
секунду правит различающиеся строки в DOM.

Три рычага проверены и отвергнуты, и каждый стоил бы настройки:

- **линкер `rust-lld` вместо `link.exe`** — 37,6 с против 37,2 с. Линковка
  узким местом не была; ради этого нуля пришлось бы завести
  `.cargo/config.toml` с путём внутрь каталога тулчейна, то есть привязать
  сборку к версии rustup;
- **`strip = "debuginfo"`** — 38,7 с. PDB на 7,6 МБ пишется при каждой
  линковке, но времени не стоит;
- **общий `target` на несколько соседних проектов** — ноль. Затея выглядела
  верной: у пикера с windows11-manager 224 крейта совпадают по имени, профили
  после этих правок одинаковы, и напрашивался вывод, что второй проект
  доберёт готовое. Замерено прямо: windows11-manager собран в пустой общий
  каталог (222,4 с, 518 юнитов), следом туда же пикер — **491 юнит**; он же в
  свой одноразовый каталог — **те же 491**. Переиспользован ноль юнитов,
  время совпало в пределах шума (321,9 с против 329,2 с), место сложилось
  ровно (1,8 + 1,4 = 3,2 ГБ). Совпадение имени и версии крейта ничего не
  значит: юнит опознаётся хэшем, а в него входит унификация фич, своя у
  каждого дерева зависимостей. Платой была бы сериализация — cargo берёт на
  каталог эксклюзивный лок, и две сборки перестали бы идти параллельно.

**`LNK1104` на `deps\ccfzf_picker.exe` — след стенда, а не беда деплоя.**
`release\ccfzf-picker.exe` и `release\deps\ccfzf_picker.exe` — жёсткие ссылки
на один образ (`fsutil hardlink list` показывает оба имени), и на этом легко
решить, что `deploy-win.sh` освобождает только одно имя и потому обязан падать.
Проверено воспроизведением всей последовательности деплоя на работающем
пикере: не падает. Удаление **не последнего** имени NTFS разрешает и для
отображённого образа — имён остаётся два (`*.old.exe` и `deps\`), cargo сносит
второе и кладёт своё. Отказ бывает ровно тогда, когда имя у образа осталось
одно; у деплоя такого не бывает, а у самодельного стенда — бывает.

## Язык

**Всё, что видит человек, — по-английски; всё, что видит разработчик, — по-русски.**
Подписи, кнопки, подсказки, сообщения об ошибках, пункты меню трея, заголовки
окон и шапка, которую окно настроек пишет человеку в `config.yaml`, — английские.
Комментарии, doc-комментарии, названия тестов и сообщения в `assert` —
русские: они объясняют «почему», и объяснение это писано на языке, на котором
о нём договаривались. Тест, сверяющийся с видимой строкой, правится вместе с
ней — иначе перевод ломает сторожа, а не проверяемое им правило.

## Правила, за которые уже заплачено

- **`;` в удалённой команде не ставить** — для Windows Terminal это разделитель
  панелей, и команда развалится на панели вместо выполнения. Стратегия
  `takeover` в `frontend-src/open-strategy.js` склеивает команду через `; `; она
  выключена (`caps.takeover: false`), но при включении это первое, что сломается.

- **`ssh host cmd` — неинтерактивный шелл.** zsh читает только `.zshenv`,
  `.zshrc` не читает. Форма `inDir` в `frontend-src/open-strategy.js`:
  `exec $SHELL -ic 'cd -- <cwd> && <cmd>'`. Через неё обязаны идти **все**
  удалённые запуски агента — и `resume`, и хвост `takeover`, и проектные хоткеи
  в `sessions.html`. Без неё не отрабатывает хук `chpwd`, который ставит
  `project=` в `OTEL_RESOURCE_ATTRIBUTES`, и агент пишет телеметрию без имени
  проекта.

- **`cd` стоит внутри интерактивного шелла**, после чтения rc: иначе rc, сам
  куда-то переходящий, увёл бы каталог обратно. Кавычки при этом навешиваются
  дважды (`q` внутри `q`) — разбирать будут два шелла подряд.

- **Список не перерисовывается целиком.** Подача тикает раз в секунду; запись в
  DOM идёт через `syncList()` и `frontend-src/picker-list-sync.js`, которые
  правят только отличающиеся строки. `list.innerHTML = html` на каждый тик
  ронял скролл и гасил hover.

- **Про окна пикер не спрашивает никого — они приезжают в ответе агрегатора.**
  `ccfzf --state` читает у себя файл, который кладёт рядом оконный трекер с той
  машины, где сессии видны на экране, и добавляет каждой сессии поле `window`
  (главное окно) и `windows` (список всех — сессию открывают и на нескольких
  машинах сразу), а ответу — `windowHost` и `windowPid`. Своего http-клиента у
  пикера нет и не должно появиться: сервер на той стороне вешал демона через
  две-три минуты после старта (разбор — в репозитории windows11-manager).
  Устаревший файл агрегатор отбрасывает сам, старше двух минут.

- **Имя терминала в строке приезжает той же дорогой, что и окно, — через
  четыре репозитория.** Пометка окна различает терминалы поимённо (буква на
  терминал, `TERMINAL_GLYPHS` в `frontend-src/session-glyph.js`), и вопрос у
  человека именно такой: «окно есть» видно и без неё, а на popstas-pc рядом
  живут Windows Terminal и WezTerm. Знания этого у пикера нет ниоткуда — окон
  он не видит, — поэтому цепочка целиком: трекер называет приложение
  (`terminalAppName` в windows11-manager — basename exe; `app_name` из `ax.rs`
  в macos-windows-manager — отображаемое имя), агрегатор пропускает поле
  насквозь (`read_windows` в `ccfzf` разбирает запись **белым списком**, и
  незнакомое поле там теряется молча), пикер узнаёт имя таблицей. Порвись
  цепочка в любом звене — глиф просто останется прежним, ▣, и отличить это от
  «терминал незнакомый» нечем: так и вышло с первой редакцией галки, работавшей
  ровно нигде.

  К общему виду имя не приводит никто, и это решение: на Windows приезжает файл
  (`WindowsTerminal.exe`), на маке — приложение (`kitty`), а таблица у
  читателя знает оба. Приводить пришлось бы на трёх сторонах сразу, и разошлись
  бы они на первой же правке.

- **Передний план на Windows выдаётся, а не берётся.** `SetForegroundWindow`
  система разрешает только тому, кто передним планом уже владеет либо получил
  последнее событие ввода. Никто из исполнителей наших просьб не таков: они
  слушают брокера. Право передаёт сам пикер, `allow_any_foreground` в
  `src-tauri/src/main.rs`, и **до** публикации, пока нажатие ещё наше.

  Право уходит всем (`ASFW_ANY`), а не названному pid, и это исправление.
  Названный pid был один — `windowPid` из ответа агрегатора, — но кладёт его в
  файл трекера демон `claude-wt watch`, а окна поднимает и терминал запускает
  служба MQTT: с переезда claude-wt из windows-mqtt в windows11-manager это два
  разных дочерних процесса трея, и грамота уходила не тому. Третьего исполнителя
  — только что запущенный `wt.exe` — по pid не назвать вовсе: в момент выдачи
  его ещё нет, а именно его отказ выглядел свернувшимся окном нового терминала.

  Гашение пикера — тоже ход за передний план, поэтому оно идёт **до** просьбы во
  всех четырёх ветках, кончающихся окном (`focusSession`, `openProjectRow`,
  `newSessionHere`, `openViaManager`); сторож — `test/hide-before-request.test.js`.
  Цена известна и уплачена: отказ публикации человек увидит не сразу, а когда
  откроет пикер снова.

  Чего грамота не решает: уже открытое окно менеджер поднимает и без неё —
  `bringToTop()` в node-window-manager подцепляет свой ввод к потоку переднего
  окна (`AttachThreadInput`), а такой подъём Windows не запрещает. Поэтому окно
  новой сессии на той стороне поднимают явно (`focusSpawnedWindow` в
  `windows11-manager/src/claude-wt/project.js`), выждав расстановку: грамота
  живёт до следующего ввода человека, а окно приезжает секундами позже.

- **Поднимать ли окно, решает совпадение имён машин — по каждой строке
  отдельно.** Трекеров теперь может быть несколько, и «чья это машина»
  перестало быть свойством всего ответа: `windowOf()` в
  `frontend-src/session-windows.js` берёт `host` из записи окна именно этой
  строки, а на старом агрегаторе (там окно одно на весь ответ) подставляет
  верхние поля `windowHost`/`windowPid`. `canFocusRow()` сравнивает этот
  `host` с `windowHost` конфига — тем же именем, что человек пишет в
  `config.yaml`. На маке агрегатор рассказывает и про окна Windows-машины:
  пометка ▣ там полезна, а ветка `focus` не включается — подъём окна на чужом
  экране ничего не дал бы человеку, а Enter лишился бы привычного открытия
  терминала. Пустое поле в конфиге значит «фокуса не бывает», и это
  умолчание.

- **Окон у сессии бывает несколько, и карточка — на окно.** Сессию открывают
  на нескольких машинах: работали на одной, продолжили с того же места на
  другой — id один, окон несколько. Агрегатор отдаёт их списком (`windows` у
  сессии), порядок — свежайший взгляд первым (`focusedAt`, дальше `lastSeen`,
  дальше имя машины ради устойчивости). Прежде запись с меньшим `lastSeen`
  выбрасывалась, и строка мигала между машинами: имя, пометка ▣, отметка
  «просмотрено» и адресат Enter менялись от опроса к опросу, потому что
  трекеры тикают с разной частотой.

  Одна строка на сессию тоже была написана и отвергнута на живом пикере: с
  двумя окнами она уезжала в блок чужой машины целиком, несла два глифа сразу
  и на вопрос «а здесь она где» не отвечала ничем. Теперь `buildSessionList`
  даёт по карточке на окно (`perCard`): у каждой своё окно, своя машина
  (`windowHost`) и своё `focusedAt` — взгляд именно на это окно. Работа агента
  (запрос, ответ, деньги, контекст) повторяется на обеих: агент один и ждёт
  человека через любое из окон.

  Поле `window` (первое из списка) осталось и не мёртвый груз: пикер и
  агрегатор выкатываются порознь, и пикер прошлой версии обязан продолжать
  работать. Читатель у него ровно один — сам пикер: в дамп поле не попадает
  (`DUMP_KEEP`), поэтому HA-экспорт и панель читают файл трекера сами.

  **`id` строки от этого перестал быть уникальным**, и мест, где на его
  уникальность опирались, нашлось пять — все ломались бы молча: ключ строки
  при перерисовке (`rowKey`, теперь `s:<id>@<host>` — тот же приём, что у
  `zellij:<name>` и `snap:<id>:<id>`), поиск строки под меню `^K`, тай-брейк
  сортировки, раскладка карточек по блокам и пометка сессий-тёзок. Пометка
  считается **по машине своей карточки**, а не по представителю сессии: с
  представителем местная карточка получала подпись с именем чужой машины.

  Два места, где список окон главнее своего. Enter ищет **своё** окно
  (`focusWindowOf`): подъём на чужом экране человеку ничего не даёт. И «Mark
  unread» отматывает у **каждого** трекера сессии (`sessionWindows` →
  `unreadBases`) — отмотай у одного, второй вернёт «просмотрено» следующим же
  опросом. Отметка «просмотрено», наоборот, у карточки своя: смотрели в
  конкретное окно, и вторая карточка обязана остаться непросмотренной.

- **У фонового форка бывает окно, и достаётся оно строке родителя.** Форк
  своей строки не получает — иначе он отобрал бы у родителя его же окно, — а
  его поля подставляются в родительскую (`activeAgent`). Поля эти не только
  агентские: фоновое задание Claude Code занимает собой тот самый терминал, из
  которого его завели, трекер привязывает окно к **его** id (id называют хуки,
  а пишет их с этого момента форк), а родитель перестаёт быть живым — процесс
  ушёл. Строка родителя от этого уезжала в историю, форка в списке не было
  вовсе, и живое отслеживаемое окно не показывал никто: сессия видна только в
  History, при том что трекер её окно видит.

  Поэтому `buildSessionList` берёт у работающего форка и окно, и живость.
  Окна **замещают**, а не складываются: у обычного `claude agents` окно
  остаётся за родителем, а одно и то же окно, привязанное разными трекерами к
  разным id, дало бы на одной машине две карточки. Живость, наоборот,
  складывается: форк кончился, родитель работает — строка обязана остаться
  живой.

- **Имён у сессии два, и второе — имя окна.** `title` строки приезжает из
  транскрипта (`custom-title`/`ai-title`), то есть от агента; `windowTitle` —
  то, чем сессию назвал человек, заводя окно (`claude -n tray-build-time`), и
  то, по чему её привязывает к окну трекер. У долгой сессии первое остаётся от
  работы, ради которой её когда-то завели, и с сегодняшней расходится:
  живой пример — строка `esm-migration` у сессии, которую человек знает как
  `tray-build-time`. Пока имя окна не показывалось и не искалось, найти её в
  списке было **нечем**: запрос по своему же имени давал ноль строк на всех
  трёх машинах, и выглядело это пропажей сессии, а не расхождением имён.

  Поэтому имя окна едет в строку полем (`windowTitle` в `session-list.js`),
  входит в стог поиска третьим (`picker-filter.js`) и рисуется подписью рядом
  с именем — но **только когда расходится** с ним (`windowNameHtml`). Мерка
  расхождения та же, что у второй строки с каталогом (`hidesProject`):
  множества слов, а не строки целиком, иначе `ccfzf_picker` рядом с
  `ccfzf-picker` был бы подписью ни о чём. Пустая строка, а не отсутствие
  поля: стог склеивается из полей, и недостающее уехало бы в него словом
  `undefined` — запрос из него нашёл бы разом всю историю.

  Имя окна главнее не сделано намеренно: окно закрывается, а строка остаётся,
  и в истории сессия молча вернулась бы к прежнему имени — то есть имя строки
  менялось бы само по себе.

- **Короткий id стоит в строке имени, а не в правой группе колонок.** Правая
  группа отвечает на вопрос «стоит ли сюда заходить» — деньги, контекст,
  возраст; id отвечает на другой, «та ли это строка», и спрашивают его глазами
  там же, где читают имя. Поэтому `sessionIdHtml` рисует `span`, а не `div`, и
  зовётся из `.name` — рядом с именем окна и меткой PR, той же тусклостью и по
  той же причине: это подсказка рядом. Галка `showId` осталась прежней, а вот
  её группа в `TOGGLE_CHECKS` сменилась на `left`: порядок галок повторяет
  порядок строки, а строка имени выше тела.

  Две строчки стилей держат это и ломаются молча — сторож
  «id прижат вправо, и правый край у всех строк общий» в
  `test/row-contract.test.js`. `margin-left: auto` у `.name .sid` и есть «прижат
  вправо». `flex: 1 1 auto` у `.row.session .text` — то, от чего правый край
  один на все строки: без него ширина текстового блока считается по
  содержимому, своя у каждой строки, и id встаёт лесенкой вместо колонки. Ни
  одну строку тела растяжение не удлиняет — они и так обрезались по доступной
  ширине.

  Имя при этом обёрнуто в `span.label`: строка имени стала flex, а обрезка
  многоточием на безымянном flex-элементе (голом тексте) идёт без многоточия.
  Flex включён у строк сессий, зелийных и проектов — у тех, у кого в строке
  имени есть подписи; у снимка и заголовка секции имя осталось голым текстом,
  и им бы это обрезку сломало. Замерено в обоих движках, Chromium и WebKit.

- **Хоткей проекта — подпись в строке имени, а не колонка справа.** Довод тот
  же, что у короткого id, и место то же: правая группа отвечает на «стоит ли
  сюда заходить», а хоткей — на «чем эту строку открыть», и спрашивают его
  там, где читают имя. Поэтому `hotkeyHtml` рисует `span`, а не `div`,
  зовётся из `.name`, а галка `showHotkey` переехала в группу `left` — порядок
  галок повторяет порядок строки.

  Колонкой он побывал между двумя правками, и колонка эта стояла у **всех**
  строк списка: у сессии `hotkey` не ставит никто (хоткей — признак каталога,
  а не разговора), то есть каждая строка носила пустой `div`, а у проектов
  колонка раздвигала соседей ради клавиши, которая есть у четырёх каталогов из
  сорока пяти. Из `sessionItem` вызов убран вовсе; пустой подписи не остаётся
  и у проекта без клавиши.

  Звезда отметки получила свой `margin-right`: пробел между flex-элементами
  схлопывается, и в разметке он больше ничего не значит — «★windows11-manager»
  слитно. Поймано глазами на снимке, сторожем — в `test/row-contract.test.js`.

- **Правая группа у строк проектов — табличная, и ширины ей считает JS.**
  Группа прижата вправо (`margin-left: auto` у `.meta`), поэтому левый край
  колонки задаётся шириной всех колонок правее неё: пока ширина считалась по
  содержимому, «172 · 4●» у одного проекта сдвигал счёт задач у него же, и
  левые края `todo` стояли лесенкой — читать колонку сверху вниз было нечем.

  Числа даёт `projectColumnWidths` (`session-glyph.js`) — самое длинное
  значение каждой колонки среди **видимых** строк, в знаках «0», — а
  `paintProjectColumns` в `sessions.html` кладёт их в переменные `--pcol-*` на
  `#list`. Переменные на контейнере, а не в разметке строк: список правится
  поэлементно (`planListSync`), и ширина, вшитая в строку, пересобирала бы их
  все при первой же смене самого длинного значения.

  Мерка — не замер DOM, а счёт знаков: под `font-variant-numeric: tabular-nums`
  цифра равна «0» ровно, буква уже, знаки вне ASCII (☑, ●, ·) считаются в
  полтора. Ошибка выходит в сторону запаса, и это верная сторона: колонка чуть
  шире содержимого никому не мешает, уже — режет счёт. Заодно правило остаётся
  обычной функцией с обычным сторожем — замер жил бы только в браузере.

  Три места, ломающиеся молча: общая ширина у всех трёх колонок, снятый
  `min-width` (базовые правила ставят пол в 48px и 34px — он держал бы колонку
  шире посчитанной) и сам вызов из `render()` — без него переменные не ставит
  никто и ширины схлопываются в ноль. Сторож — «колонки строки проекта одной
  ширины на все строки» там же. Левые края померены в обоих движках и в обеих
  раскладках: узкий список и блоки.

- **Отметок «просмотрено» две, и складываются они по максимуму.** Своя —
  `seen.json`, её ставит открытие сессии из списка; на маке она единственная.
  Чужая приезжает полем `focusedAt` внутри `window` (у сессии с несколькими
  окнами — максимум `focusedAt` по всем ним) — оконный трекер видит
  переход взгляда на окно, а пикер про это не знает ниоткуда. Отсюда и обратный
  ход: «Mark unread» отматывает обе, местную в `seen.json` и трекерную
  публикацией в `<base>/windows/claude-session-unread`. Только местная у сессии
  с открытым окном не значит ничего — следующий опрос вернёт «просмотрено».
  Шлётся она независимо от `canFocus`: тот про подъём окна, а отметка приезжает
  в список на любой машине.

- **Настроенный `mqtt` — условие выполнимости фокуса, а не второе решение.**
  Просьба о подъёме уходит единственным способом, публикацией в MQTT. Топик
  при этом не свой: адрес называет трекер строки (поле `mqttBase`), а
  `<config.base>/windows/claude-focus` — только запасной ход, на который
  `resolve_base` в `src-tauri/src/mqtt.rs` откатывается, когда трекер адреса
  не назвал (подробности — в правиле про адрес просьбы ниже). Без брокера
  ветку `focus` предлагать нельзя: Enter молча не сработал бы, а это хуже,
  чем открыть терминал.

- **Раскладку окон просят у трекера, и спрашивает её строка своей машины.**
  Плитку и каскад расставляет сам оконный трекер (на маке — с v0.4.0), пикер
  только просит: публикация в `<база машины>/claude-place` с телом
  `{"mode": …, "ids": [...]}`, протокол выписан в
  [docs/window-layouts.md](docs/window-layouts.md). Смысл `ids` — порядок, и
  знает его только пикер: `placeIds` в `frontend-src/session-windows.js` даёт
  id строк **видимого** списка, чьи окна на этой машине, без повторов —
  карточка на окно, а id у сессии с двумя окнами один.

  Пункты `^K` появляются по `rowCanFocus`, то есть по тому же правилу, каким
  Enter решает «поднимать ли окно»: брокер настроен, окно строки стоит здесь,
  трекер жив. Второго правила про то же самое заводить нельзя — оно разошлось
  бы с первым молча: пункты остались бы на экране, а просьба уходила бы в
  никуда, ответа у публикации нет. По той же причине незнакомую раскладку
  отвергает `place_payload` в `src-tauri/src/mqtt.rs`, а не приёмник: тот её
  отбрасывает молча, и опечатка выглядела бы сработавшей просьбой.

  Гашение пикера идёт до просьбы, как и на четырёх соседних ветках: трекер
  выводит разложенные окна на передний план, то есть ветка кончается окном.
  Отметки «просмотрено» здесь нет — окна встали по местам, но ни в одно из них
  человек не смотрел.

  Цена известна: пункты видны по `rowCanFocus`, но просьба может исчезнуть молча,
  если машина не объявила умение раскладок — объявление в задаче. Прятать пункты
  было бы правкой в трёх репозиториях сразу.

- **Хоткей плитки принадлежит пикеру, и порядок для него считает Rust.**
  Клавишу (`tileHotkey`, третья глобальная рядом с `hotkey` и `projectsHotkey`)
  забрали у обоих трекеров: `Ctrl+Win+F10`/`Ctrl+Win+F11` вешал
  windows11-manager, `Cmd+Alt+Ctrl+C` — macos-windows-manager, и оба нажатия
  уходили **без `ids`**, то есть каждая машина раскладывала окна своим
  порядком. Порядок знает только тот, кто показывает список.

  Считает его `place_order::tile_ids`, а не страница, и это та же причина, по
  какой в Rust живут опрос, проектный хоткей и имя терминала: клавишу жмут
  ровно тогда, когда пикер скрыт, а у скрытого окна WebView2 усыпляет страницу
  целиком. Значит в Rust лежит **вторая копия** `compareSessions`, `recentKey`,
  отбора своего окна и подстановки полей фонового форка. Прецедент такой копии
  один — `terminal_name`, — и держится она так же: общая фикстура
  `test/fixtures/place-order.json` и два сторожа над ней (`test/place-order.test.js`
  и тест в самом `place_order.rs`). Поведением расхождение не поймать вовсе:
  публикация проходит, брокер подтверждает, окна встают — просто не в том
  порядке, а ответа у просьбы нет.

  Живость — ключ **старше** выбранной сортировки, и это не отсебятина, а порт
  порядка секций: `placeIds` идёт по нарисованному списку, где закончившаяся
  сессия стоит в History, ниже всех живых, какой бы свежей ни была её запись.
  Плоская сортировка поставила бы её среди работающих.

  Пустой `ids` не шлётся никогда: у приёмника это значит «все ведомые окна,
  порядком той машины» — ровно то поведение, ради ухода от которого клавиша и
  забиралась. Не нашлось ни одного своего окна — пикер молчит и пишет причину
  в журнал.

  Три расхождения с пунктом `^K` известны и приняты: запроса с фильтрами Rust
  не видит вовсе (`^K` после `/l foo` раскладывает найденное, хоткей — все окна
  машины), под сортировкой `name` имя берётся голым `title` без пометки тёзки,
  а сравнение имён побайтовое вместо `localeCompare`.

  **Выкатывать обязательно в порядке «сперва трекеры, потом пикер».**
  Комбинацию держит один процесс: выкати пикер первым — `RegisterHotKey`
  ответит отказом, и клавиша молча перестанет работать у обоих. Отказ теперь
  виден — окно настроек называет не вставший хоткей поимённо (`HOTKEY_REPORTS`
  в `settings.html`), и ключи этой таблицы сверяются с ответом `save_config`
  текстовым сторожем: разойдись они, `undefined === false` не сработало бы, и
  окно печатало бы «saved» про мёртвую клавишу.

  Каскад глобальной клавиши не получил, хотя на Windows она у него была: вторая
  комбинация — это вторая занятая комбинация, а каскадом пользуются реже. Ему
  остались пункт `^K` и пункт трея самого трекера.

  **Пункт трея `Tile windows` зовёт ту же `tile_press`, что и хоткей.** Второй
  сбор просьбы разошёлся бы с первым молча — публикация прошла бы, брокер
  подтвердил бы, а окна встали бы не в том порядке. Пункт не в `MODE_MENU`:
  режимы открывают список, а этот трогает окна и списка не показывает вовсе, —
  поэтому у него своя ветка в `on_menu_event`, и её сторожит
  `every_active_tray_item_is_handled`. Пункт без ветки — самый тихий отказ из
  возможных: нажатие проходит, ветки не находит, ни ошибки, ни следа, а
  `build()` отвечает `Ok` в обоих случаях.

- **Развилку Enter решает `chooseEnterAction`, а не условия по месту.**
  `frontend-src/open-transport.js`, три проверки в одном порядке: уже открытое
  окно поднимает `focusSession` — подъём, а не открытие (гасят пикер до
  публикации и выдают право на передний план теперь все ветки одинаково);
  просьба к windows11-manager уходит лишь у
  строк с настоящим id сессии (`SESSION_ID_ROW_KINDS`) и только у тех, по
  которым менеджер сможет сработать — либо трекер знает сессию (поле `window`,
  то есть её id найдётся среди слотов), либо известен каталог проекта (поле
  `cwd`, и по нему открывается терминал с профилем из `claudeWt.projects`);
  всё остальное открывается локально, как до появления ветки менеджера.
  Каталог едет в теле просьбы (`open_session_mqtt` → ключ `cwd`) — без него
  менеджер на незнакомый id отвечает `unknown session` в свой лог, а пикеру
  про это не узнать ниоткуда: ответа у публикации нет.

- **Сессию Claude Desktop выдаёт одно поле, и другого признака нет.**
  Приложение пишет такой же транскрипт в `~/.claude/projects`: файл, каталог,
  формат и заголовок у него те же, что у терминальной сессии. Отличается
  только `entrypoint` в каждой записи — `claude-desktop` против `cli`, — и
  цепочка у него своя: агрегатор читает его **из хвоста обратным проходом**
  (сессию приложения продолжают `claude --resume` в терминале, и спрошено «где
  она сейчас», а не «где её завели»), кладёт полем в `--state`, а
  `session-list.js` несёт в строку. Ключа нет, когда поля нет в транскрипте: у
  прежних версий агента его не было, и «не сказано» обязано читаться как
  прежнее поведение, а не как выдуманный `cli`.

  **Окна у такой сессии не бывает, и добавлять её бандл в `terminals` трекера
  бесполезно.** Трекер привязывает окно к сессии сравнением заголовка с именем
  сессии, а заголовок окна приложения — просто `Claude` (снято живьём). Поэтому
  глиф `c` рисует `windowHtml` по `entrypoint`, а не `terminalOf` по записи
  окна, и глифов окон он не отменяет: сессия бывает и в приложении, и в
  терминале сразу.

  **Enter возвращает её в приложение, и маршрута для этого два.**
  `claude://resume?session=<id>` сессию не открывает, а **импортирует** —
  заводит в приложении новую поверх транскрипта; для сессии, которую приложение
  само и завело, это давало двойника рядом с настоящей, безымянную «General
  coding session» с тем же разговором. Открывает заведённую сессию
  `claude://claude.ai/epitaxy/<id>`, и `<id>` здесь **не наш**: имён у сессии два, наш —
  имя транскрипта, у приложения своё, `local_<uuid>`, и второй uuid другой.
  Связь записана только в хранилище приложения (`claude-code-sessions/<учётная
  запись>/<организация>/local_*.json`, поле `cliSessionId`), поэтому пикер его
  читает — `desktop_store.rs`.

  Двойника от настоящей записи отличает единственный признак: импорт называет
  сессию по транскрипту (`local_` плюс тот же uuid), а свою собственную
  приложение называет новым. Настоящая главнее — у неё имя и история; записи
  нет вовсе — сессия терминальная, и тогда `resume` верен, импорт для того и
  написан.

  **Хост у двух маршрутов разный, и сегмент пути угадать нельзя — только
  подсмотреть.** `resume` разбирается своей веткой целиком, а страницы окна
  живут под хостом `claude.ai`, где маршрут называет первый сегмент. Сегмент
  этот — `epitaxy`, внутреннее имя поверхности локальных сессий, и взят он
  оттуда же, куда уходит само приложение, закончив импорт (`vN(e) =
  "/epitaxy/" + e`, зовётся сразу за `importCliSession`).

  Две соседние формы проверены живьём и отвергнуты, обе тихо: `claude://cowork/<id>`
  приложение пишет в журнал как `unrecognized cowork path` — окно выходит
  вперёд, не сменив сессии (хост `cowork` принимает ровно `/new` и
  `/shared-artifact`), а `claude://claude.ai/cowork/<id>` уводит в чужую
  поверхность и открывает чат с окном новой задачи. Ответа у ссылки нет, и
  отличить верную форму от неверной можно только глазами или по журналу
  приложения — `~/Library/Logs/Claude/main.log` на маке,
  `%APPDATA%\Claude\logs\main.log` на Windows. Разбор терпимый, как у файла окон: нет каталога — пусто, а не отказ,
  иначе отсутствие приложения отменяло бы открытие.

  **На Windows ссылку открывают без своего окна.** `cmd /c start` мигал
  консолью при каждом переходе в сессию, поэтому запуск идёт через
  `hidden_command`, мимо `spawn_detached`: та сознательно идёт мимо гашения
  окна — у неё окно и есть цель, она открывает терминал.

  **Доли контекста у такой сессии не бывает вовсе** — считает её перехват
  статуслайна, а статуслайна у приложения нет. Правило «ноль честнее пустоты»
  тут оговорено, а не отменено: оно написано про терминальную строку, где два
  случая неразличимы, — здесь признак прямой, и показанный ноль был бы
  единственным числом строки, которое врёт. Правятся оба места сразу, строка и
  карточка: два места об одном факте расходиться не должны.

  Ветка стоит **ниже** фокуса — открытое окно поднимают, а не
  открывают заново, — и требует `source === 'local'`: ссылка импортирует
  транскрипт той машины, где её открыли, и строка с `sshHost` ушла бы в
  «transcript is not on disk» молча, ответа у ссылки нет. Прежняя дорога
  осталась пунктом `^K` «Resume in terminal»; он зовёт ту же `openSession` с
  флагом, а не копию её хвоста. Буква у пункта своя (`menuKey`), а не запись в
  `BUILTIN_ACTION_KEYS`: та даёт ещё и глобальный Ctrl-хоткей, а `Ctrl+E` уже
  занят настроенным действием человека — встроенная ветка съедала бы у него
  событие молча.

  **Процесс приложения на маке невидим разбору по двум причинам сразу**, и обе
  чинились в агрегаторе. Оно зовёт агента `--resume=<id>` одним токеном — форму
  с равенством `arg_value` не понимал вовсе; и живёт в
  `~/Library/Application Support/…`, а на маке argv приезжает из `ps` одной
  строкой и делится по пробелам, так что `is_claude` смотрел на
  `/Users/…/Library/Application`. Без обеих правок строка получала живость
  догадкой по каталогу (`fresh_ids`) — в каталоге с двумя сессиями не той, — и
  оставалась без pid.

  **На Windows это видно с тех пор, как местный источник заработал там** — см.
  правило про реестр сессий ниже. До него местного агрегатора на той машине не
  было вовсе (`ccfzf` — bash с python внутри, а единственный bash там пускач
  WSL), и Desktop-сессия, заведённая на самой Windows, в список не попадала:
  `--state` с `sshHost` знает только сессии той машины.

- **Снимки раскладки приезжают в ответе агрегатора, а не по запросу.** Список
  снимков в windows-mqtt отвечал через `mqtt.sendEvent()` — это запись в stdout
  своему Tauri-процессу, и стороннему читателю там взяться неоткуда. Дорога
  та же, что у окон: демон кладёт снимки в файл трекера, `ccfzf --state` их
  отдаёт. Заводить ради списка подписку в пикере значило бы держать
  соединение и ждать — ровно того, чего эта схема избегает.

  Трекеров, умеющих снимать раскладку, теперь два (windows11-manager и
  macos-windows-manager), и владельца снимку приписывает агрегатор, а не сам
  трекер: в своём файле трекер и так публикует только свои снимки, а вопрос
  «чей это снимок» встаёт лишь на слиянии, когда агрегатор складывает файлы
  разных машин в один список. Та же развилка уже решена для окон
  (`windowOf()`, правило про совпадение имён машин выше) — снимку она досталась
  тем же способом: `host` и `mqttBase` источника каждой записи проставляет
  `read_window_sources` в агрегаторе `ccfzf`, а пикер их только читает —
  `snapshotBase()` в `frontend-src/picker-snapshots.js` достаёт `mqttBase` из
  уже готовой записи.
  `^S` отбирает из ответа только снимки своей машины (`snapshotsHere`) — снимок
  соседней восстановить на своём экране всё равно нечего.

  **Снимки сгруппированы по дням, и свернуть можно только день.** Строк три
  вида — `snapshot-day`, `snapshot`, `snapshot-session`, — и складывает их
  `buildSnapshotRows`. Свежий день первым, внутри дня свежий снимок первым;
  развёрнут по умолчанию только первый день, остальные свёрнуты
  (за неделю снимков набирается столько, что вчерашние оттесняют сегодняшние с
  экрана, а восстанавливают почти всегда последний). Умолчание живёт в коде, а
  `collapsedDays` — только отступления человека: то же правило, что у
  `collapsed` в `buildSections`.

  Карта эта живёт **в памяти страницы, а не в `ui.json`**: ключи там — даты, по
  одной на каждый день, который хоть раз трогали, и копились бы в файле
  навсегда, а окно настроек показало бы их строками в списке панелей — оно
  берёт ключи именно из `ui.json` (та же болезнь, что у `remote:<host>`).
  Плата известна и принята: свёрнутость дней не переживает перезапуск.

  У снимка сворачивания нет и не заводилось: заголовок снимка и его сессии
  идут вместе, и второй способ навигации там, где хватает стрелок, пришлось бы
  объяснять. Меню `^K` на дне не открывается вовсе — `availableActions` отдаёт
  ему пустой список поимённой веткой, а не общей: «восстанови все снимки дня»
  никто не просил, а сессионные пункты нарисовали бы по нему пустоту.

  Три места, где день стоит дороже, чем кажется:

  - **Счёт секции считается по дням, а не по строкам** (`snapshotCount`,
    зовётся из `buildSections`). Строки свёрнутого дня в список не попадают
    вовсе, и `rows.length` менялся бы на каждое сворачивание: «Snapshots - 18»
    превращалось бы в «Snapshots - 2» без единого исчезнувшего снимка.
  - **Под непустым запросом заголовок дня — подпись, а не строка** (`foldable`,
    как у секции): свёрнутость там назначена сверху, и Enter молча затирал бы
    записанное.
  - **Сброс выбора пропускает оба вида заголовков** (`HEADER_KINDS` в
    `sessions.html`). В режиме `/s` день — первая строка списка, и проверка на
    один `section` оставляла бы выбор на нём: Enter сразу после `^S` сворачивал
    бы сегодняшний день вместо того, чтобы поднять свежую раскладку.

  Дату строка снимка больше не показывает — только час (`formatSnapshotTime`):
  снимок стоит под своим днём, и дата в каждой строке повторяла бы заголовок
  дословно.

  Восстановление ветвится не по `host` снимка, а по способности его
  машины `openSession` (`openManager` в `frontend-src/session-windows.js`,
  развилку решает `snapshotOwner` в `sessions.html`). Мак эту способность не
  объявляет: менеджера, который умел бы открыть терминал по MQTT-просьбе, там
  нет, и снимок с `host: mac-host` восстанавливается не просьбой, а тем же
  путём, каким пикер открывает сессию из списка сам — по одной, `resume` по
  id (место запомнено за идентификатором сессии, а не за именем окна), с
  паузой между поднятиями: два терминала, вставшие разом, ни один трекер не
  различит — заголовок у обоих ещё не устоялся, а привязка идёт по нему.
  Расставляет поднятые окна по местам сам трекер той машины, обычным
  механизмом расстановки — про восстановление как таковое он не знает и
  знать не обязан. Прямое сравнение `host` снимка с `windowHost` конфига эту
  развилку не заменит: так не отличить мак без менеджера от Windows-машины с
  ним, и Enter уехал бы в топик, который никто не слушает, молча, потому что у
  публикации нет ответа.

  На машине с менеджером просьба по-прежнему уходит ему — публикацией
  `claude-snapshot-restore`, но адрес называет уже не `managerBase()`, а сам
  снимок: у `mqttBase` в его записи то же происхождение, что у одноимённого
  поля записи окна, и то же правило — своя база у каждой машины.
  `managerBase()` жива и не тронута: ею по-прежнему пользуются три другие
  просьбы к менеджеру (открыть проект, завести сессию, открыть через пункт
  меню), у которых снимка нет и адрес неоткуда взять, кроме как у текущей
  машины-менеджера. `<config.base>/windows/claude-snapshot-restore` — запасной
  ход на случай пустого `mqttBase` у снимка (старый агрегатор его не
  проставляет), а не основной адрес.

- **Тело просьбы о восстановлении разбирается на той стороне двумя видами.**
  С панели openHASP прилетает сырая строка или пустота, от пикера — объект
  `{id, sessionIds}`. `parseRestorePayload` в windows-mqtt знает оба; без
  разбора JSON id снимка уезжал в `restoreSnapshot` литералом `{"id":"…"}`, и
  ошибки на такой вход нет — есть пустой результат.

- **Действия открытия папки запускаются без шелла — и это разница, а не
  мелочь.** `spawn_detached` зовёт `Command::new(file).args(args)`, элементы
  `argv` уходят аргументами процесса: кавычить и экранировать нечего, `q` из
  `open-strategy.js` тут не нужна и только испортила бы путь. Правило `q`
  действует ровно там, где команда идёт через `ssh` в чужой шелл.

- **Команда едет хвостом argv — кроме тех терминалов, которые её так не
  берут.** Обычный путь (`buildOpenCommand` в `frontend-src/open-strategy.js`)
  — `[terminal.file, ...terminal.args, 'ssh', '-t', host, remote]`: элементы
  уходят аргументами процесса, и кавычить нечего. kitty исполняет этот хвост
  как есть, Ghostty хочет его после `-e`, Windows Terminal берёт как есть,
  WezTerm — после `start --` (без `--` он принял бы `ssh` за свою подкоманду);
  всем четверым хватает пресета с верными аргументами (`terminal-presets.js`,
  выбор в настройках полем «Terminal preset»). Окно после конца сессии WezTerm
  закрывает, и держать его нечем: флага вроде kitty-шного `--hold` у
  `wezterm start` нет вовсе — это `exit_behavior` в `~/.wezterm.lua`, то есть
  настройка человека, а не пресета. На Windows он зовётся `wezterm-gui.exe`
  (обычный `wezterm.exe` привёл бы с собой консольное окно) и без каталога —
  как `wt.exe`, потому что абсолютный путь у msi, portable и scoop разный.

  **А на маке пресет зовёт `wezterm` из бандла, и это верно.** Догадка, что
  здесь та же беда, что на Windows, и звать надо `wezterm-gui`, проверена живьём
  (2026-08-17) и не подтвердилась: `wezterm` сам перезапускается в
  `wezterm-gui` — под настоящим argv пресета в `ps` стоит
  `…/MacOS/wezterm-gui start -- ssh -t …`, окно с сессией открывается, stderr
  пуст. Консольного окна на маке не бывает вовсе, ради чего развилка и заведена
  на Windows, — то есть переносить её сюда было бы правкой без причины.

  iTerm2 в argv команду не принимает вовсе: `open -a iTerm` аргументы до
  программы не доносит. Единственная дорога к нему — AppleScript, где команда
  обязана быть **одной строкой**. Отсюда подстановка `{command}`
  (`COMMAND_PLACEHOLDER`): аргумент, её содержащий, получает всю команду
  строкой, а хвостом argv она уже не едет. Приём и имя те же, что у
  `{localPath}` в настроенных человеком действиях, — второго способа не
  заводили.

  Две мины здесь уже обезврежены, и обе тихие. Подстановка идёт через
  `split/join`, а не `replace`: у строки замены в `replace` свои значения у
  `$&` и `$'`, а в команде стоит `exec $SHELL` и одинарные кавычки рядом — она
  молча съела бы кусок. И экранирование для двойных кавычек делает слэш
  **первым**, иначе он удвоил бы слэши, добавленные следом за кавычками.
  Кавычек в итоге три слоя (POSIX внутри POSIX внутри AppleScript), и
  собраны они без единого живого запуска — на Linux этих терминалов нет.
  Форму сторожит `test/terminal-presets.test.js`.

  **Кавычек iTerm2 не достаётся ни одной, и это не перестраховка.** Живая
  проверка на маке (2026-08-15): его токенизатор обрабатывает `\` и внутри
  одинарных кавычек — там, где POSIX-шелл считает его обычным знаком, — и
  идиома `'\''`, которой `q` закрывает кавычку, у него рассыпается. Один и
  тот же продуктовый вход, два разбора (замерено подставным `argv`-дампером
  вместо `ssh`):

      sh:     exec $SHELL -ic 'cd -- '\''/home/user/x'\'' && claude --resume …
      iTerm2: exec $SHELL -ic 'cd -- '\\\/home/user/x\''' && claude --resume …

  До ssh доезжала вторая, падала мгновенно, а профиль по умолчанию закрывает
  кончившуюся сессию — отсюда симптом «окно открылось и тут же исчезло», без
  единого слова о причине: ответа `osascript` мы не читаем.

  Поэтому команду iTerm2 не отдают вовсе. Он получает **два токена** —
  `{helper}` и `{commandBase64}`, — а разворачивает и кавычит уже шелл, в
  помощнике `~/.config/ccfzf-picker/open-terminal.sh` (пишет его
  `terminal_helper` в `main.rs`, на каждый спрос: файл — продолжение бинаря и
  расходиться с ним не должен). В алфавите base64 нет ни кавычки, ни пробела,
  ни обратного слэша, так что делить такой токен не на чем — что бы ни лежало
  в команде.

  Промежуточный ход — `write text`, печатавший команду в уже поднятую сессию, —
  тоже работал: разбирал строку шелл сессии, и argv совпадал с sh знак в знак.
  Отвергнут не за неверность, а за то, что напечатанное **видно**: первой
  строкой сессии человек читал простыню экранирования.

  Окно после сессии держит открытым сам помощник (`exec $SHELL -i` в хвосте):
  иначе профиль закрыл бы его вместе с агентом, и причину отказа снова стало бы
  не прочитать — та самая слепота, из-за которой поломку искали дольше, чем
  следовало. Забота та же, что у kitty с `--hold`, только платит здесь
  помощник, а не флаг терминала.

  Цена, видная человеку: у сохранившего iTerm2 до этих правок в `config.yaml`
  лежит одна из двух прежних форм, и выпадашка обязана показать ему «Custom», а
  не iTerm2, — иначе она обещала бы рабочий пресет тому, у кого окно
  по-прежнему закрывается. Лечится выбором пресета заново.

- **Терминал встречается с командой ровно в одном месте — `terminalArgv`.**
  Дорог у неё три, и терминал выбирает свою сам, содержимым аргументов: без
  подстановок — команда хвостом argv (kitty, Ghostty, Windows Terminal);
  `{command}` — одной строкой, для тех, кто хвост argv не берёт; `{helper}` —
  путь помощника и base64, для тех, кому нельзя отдать ни одной кавычки.

  Второй сборки быть не должно, и мина эта уже сработала: `newSession` в
  `sessions.html` складывал argv у себя — `[terminal.file, ...terminal.args,
  'ssh', …]` — и про подстановку не знал вовсе. На kitty это верно, а на iTerm2
  давало окно, в которое печатается литеральный `{command}`, тогда как `ssh` с
  аргументами уезжал osascript в никуда. То есть `^N` и «New session» на iTerm2
  не работали никогда, и заметить это можно было только на нём. Сторож —
  «страница не собирает argv терминала мимо terminalArgv» в
  `test/open-strategy.test.js`, и ловит он **текстом страницы**: поведением
  такое не поймать — argv тут собирается верным для большинства терминалов и
  молча неверным для того единственного, который живёт подстановкой.

  Путь помощника страница спрашивает у Rust (`terminal_helper`) и только когда
  терминал его назвал: домашнего каталога страница не знает, а у kitty с
  Ghostty ветка эта не включается вовсе. Пустой путь — отказ с сообщением, а не
  молчание: пустой токен превратил бы base64 в имя программы, и окно закрылось
  бы сразу после открытия — ровно тот симптом, из-за которого всё затевалось.

  У обоих kitty в аргументах стоит и `--hold` («remain open, at a shell
  prompt, after child process exits»): без него окно закрывается вместе с
  сессией агента. Флага `--hide` у kitty нет вовсе, а `--start-as=hidden`
  делает обратное — прячет окно; путать их легко. Оговорку kitty «only affects
  the first window» рядом с `--single-instance` живьём ещё не мерили.

  Пресет полей не заменяет, а заполняет: путь у всех разный, и один homebrew
  на arm и на intel даёт два разных префикса. Своего ключа в конфиге у пресета
  нет намеренно — что выбрано, считается обратно по содержимому полей
  (`matchPreset`). Второй источник правды разошёлся бы с тем, что человек
  правит руками, и выпадашка обещала бы iTerm2 там, где в поле стоит kitty;
  поэтому же `preset` исключён из `FIELDS` в `settings-form.js` — иначе патч
  унёс бы в `config.yaml` выдуманный ключ.

- **«Open terminal» — встроенный пункт, а не подстановка в настроенное
  действие.** Вопрос был «пусть моё действие открывает выбранный терминал», и
  напрашивался `{terminal}` в его `argv`. Так нельзя: у настроенного действия
  форма «программа плюс путь» (`['cursor', '{localPath}']`), а `terminalArgv`
  пути не подставляет — он **дописывает команду**, и дорог у него три. Первая
  же подстановка дала бы верный kitty и молча неверный iTerm2, которому argv не
  отдают вовсе, — ровно та мина, на которой уже подорвался `newSession`.

  Поэтому пункт свой: `terminal` в `availableActions`, у всех строк с
  каталогом (сессия, проект, строка внутри снимка) — тем же условием, что и
  `new`, и без `pathMap`: терминал уходит на машину источника через ssh, а не
  открывает путь на этой. Команду даёт `terminalCommand` в `open-strategy.js` —
  `inDir(cwd, 'exec $SHELL -i')`, и хвост тут обязателен: без него шелл,
  поднятый `-c`, кончится вместе с `cd`, и окно закроется мгновенно. Это то же
  дело, ради которого у kitty стоит `--hold`, только флаг есть не у всех, а
  команда одна на всех.

  Буква `t` — и вместе с ней `^T`: `BUILTIN_ACTION_KEYS` одна на подпись в меню
  и на прямую клавишу (из неё же считается `RESERVED_CODES`), взять половину
  нечем. Прежде в её докблоке стояло, что действия `terminal` здесь нет
  намеренно — «на маке открытие сессии и есть открытие терминала»; про Enter
  это по-прежнему верно, а пункт отвечает на другой вопрос: шелл в том же
  каталоге, **без** агента.

  Менеджера этот пункт не просит вовсе, в отличие от `newSessionHere`: все его
  просьбы кончаются агентом, голого шелла он не открывает. Цена известна и
  уплачена — на машине с менеджером теряется профиль Windows Terminal по
  каталогу (соответствие живёт в `claudeWt.projects`). И гашение здесь **после**
  запуска, а не до: окно поднимает сам пикер, права на передний план у него
  никто не отбирает — то же, что у местной `newSession`, и не то, что у
  четырёх веток, кончающихся чужим окном.

- **`{localPathSlash}` не для красоты.** `cmd /c start` съедает обратные слэши
  и папку не открывает — проверено ещё в windows-mqtt
  (`src/picker/session-open-helpers.js`). Прямой
  запуск `explorer.exe` там же не сработал вовсе. Единственная форма, которая
  открывает папку, — `cmd /c start "" <путь прямыми слэшами>`.

- **Счёт задач в колонке считает агрегатор, а файл ему называет
  `env.STATUSLINE_TODO`.** Поле `todo` приезжает в ответе `ccfzf --state`
  списком секций по заголовкам первого уровня — данными, а не готовой строкой,
  и рисует его `todoSections` в `frontend-src/session-glyph.js`. Файл при этом
  не `docs/TODO.md`: то лишь умолчание, а настоящее имя стоит в
  `env.STATUSLINE_TODO` проектного `.claude/settings.json` (`todo_path` в
  агрегаторе, `settings.local.json` перекрывает `settings.json`). Ключ этот
  ведёт статус-строку Claude Code, то есть названный там файл человек и видит
  перед собой: у вольта Obsidian это `tasks.md` в корне, у соседних рабочих
  каталогов — файл вовсе вне проекта. Считай пикер сам — счёт разошёлся бы со
  статуслайном, а разбор галочек лёг бы вторым рядом с портом
  `statusline-block.sh`, уже живущим в агрегаторе.

- **Имена машин в репозиторий не возвращать.** Хост берётся из
  `~/.config/ccfzf-picker/config.yaml`, умолчания у него нет.
  `test/no-private-data.test.js` это проверяет; список конкретных слов — в
  `data/private-patterns.txt`, каталог под `.gitignore`.

  Правило не безоговорочное: санкционированное исключение есть, и живёт оно в
  `BINARY_OK` того же теста — `assets/fullscreen.png`, снимок окна для
  README. Комментарий рядом называет цену: имена машин, домашний путь, полный
  список проектов и содержимое сессий текстом — всё это на снимке видно, и
  проверке нечем ни прочитать картинку, ни отредактировать её. Решение
  опубликовать снимок принято владельцем сознательно; второму такому файлу
  появляться в репозитории не следует, не замазав на нём те же классы данных.

- **Опрос живёт в Rust, а не на странице.** У скрытого окна webview тормозит
  таймеры, а WebView2 у свёрнутого умеет усыплять страницу целиком: фон на
  `setInterval` замолчал бы, и узнать об этом было бы неоткуда. Такт считает
  `next_delay` в `src-tauri/src/poller.rs` — секунда на показанном окне,
  1→2→4→8 минут на скрытом. Фон нужен не только ради тёплого списка:
  `ccfzf --state` переписывает свой дамп, а с того дампа живут экспорт в Home
  Assistant и панель openHASP — закрытый пикер, переставший спрашивать,
  останавливает и панель.

- **Отпечаток состояния считается без времени.** `generated` наверху ответа и
  `age` у каждой сессии считаются от «сейчас» и отличаются на каждом опросе:
  сравнивая ответ целиком, бэкофф не включился бы никогда, а выглядело бы это
  как работающая функция. `fingerprint` в `poller.rs` их выбрасывает.

- **`ui.json` — шесть полей верхнего уровня, и окно настроек обязано вернуть
  все, кроме своих.** `sort`, `toggles`, `fullscreen`, `collapsed`, `order`,
  `hidden`. Вкладка UI распоряжается только `toggles`, вкладка Panels — тремя
  осями панелей (`order`, `collapsed`, `hidden`); остальным
  распоряжается пикер, и `uiStateToSave` зовётся всеми шестью аргументами — и
  в `settings.html`, и в `sessions.html`. Мина известная и сработавшая уже дважды: окно звало её
  тремя, и первое же сохранение вкладки UI гасило запомненный `^F`; потом
  четырьмя — и гасило свёрнутость. Сторож — `test/settings-page.test.js`, и
  сверяет он список аргументов **дословно**: одна арность не ловит ничего,
  аргументы можно и переставить местами.

  Половинки `collapsed`, `hidden` и `order` — свои у каждой раскладки
  (`narrow`, `wide`), но формы у них разные, и это не оплошность. Свёрнутость — карта
  «ключ → булево», одинаковая в обеих раскладках. Порядок в узком списке —
  последовательность ключей, а в широком — **по последовательности на колонку**:
  секцию там можно перенести и в соседнюю колонку, и так колонка и
  место внутри неё записаны одной структурой. Сколько колонок — сказано ровно в
  одном месте, `WIDE_COLUMNS` в `frontend-src/ui-state.js`, и все прочие
  (`picker-panels.js`, `byColumn` и `addDropZones` в `sessions.html`, выпадашка
  в `settings.html`, стартовый `order.wide`) читают его оттуда. Число тут
  называть словом нельзя: раньше «три» стояло в шести местах сразу, и потолок
  не поднимали именно поэтому. Разбор — `normalizeOrder` в
  `frontend-src/ui-state.js`.

  **`hidden` — не третье состояние свёрнутости, а отдельная просьба.**
  Свёрнутая панель остаётся строкой: видно, что она есть и сколько в ней.
  Спрятанной на экране нет вовсе. Отсюда и разница в силе: непустой запрос
  разворачивает свёрнутое (искали не счёт), но прятанье не отменяет — «убери»
  сказано намеренно. Отменяет его только префикс, назвавший панель поимённо
  (`^H`, `^P`, `^S`): он спрашивает про неё прямо, и молчание в ответ было бы
  тем же, что молчащий Enter. Ставится `hidden` **только из окна настроек** и в
  обеих раскладках, а клавиши для этого нет намеренно: случайно нажатая убрала
  бы панель без следа, а вернуть её можно было бы только там же.

  Вкладка Panels правит ui.json, а не config.yaml, и потому у неё свой код и
  своё сохранение — как у вкладки UI, и с тем же приёмом: файл перечитывается
  в момент сохранения, а поверх свежего кладётся только то, чего человек
  касался здесь (`dirtyPanels`). Иначе сохранение откатывало бы
  перетаскивания, сделанные в пикере, пока окно настроек было открыто.
  Пометка в `dirtyPanels` называет раскладку (`«раскладка:ключ»`, режется по
  длине имени раскладки — в ключе своё двоеточие бывает): половинки у панели
  свои, и один ключ на обе переносил бы правку туда, где человек её не делал.
  Колонка в этой вкладке имеет значение «default» (ноль): оно означает
  «колонку назначает смысл секции», и без него выбор по умолчанию нечем было
  бы выразить — подставь окно единицу, и все панели съехали бы в первую
  колонку записью, которой человек не делал.

  **Таблиц во вкладке две, и различаются они не только осями.** У широкой три
  оси, у узкой две: колонок в узком списке нет вовсе, и показанный там выбор
  колонки был бы выбором без последствий — хуже, чем его отсутствие. Поэтому
  же у узкой строки поля `column` нет, а не ноль: ноль значит «колонка по
  умолчанию», то есть обещал бы выбор.

  Постоянные ключи у таблиц одни и те же — с тех пор, как чужие машины
  склеиваются в обеих раскладках (см. правило про склейку ниже), строка
  `remote` есть и в узкой. А набор панелей всё равно непостоянен: `past:<N>`
  приходят с рабочими столами, и ответа агрегатора окно настроек не видит
  вовсе. Ключи оно берёт из `ui.json` (`keysInUi`), поэтому рабочий стол
  появляется в списке только после того, как его хоть раз свернули или
  перетащили в пикере. Развилка тут была — научить пикер отдавать окну список
  своих секций, — и владелец выбрал дешёвый ход: вторая дорога для данных между
  окнами стоила бы дороже этой задержки.

  **Ключи `remote:<host>` из `ui.json` окно настроек выбрасывает** — фильтр
  `STALE_HOST_KEY` в `picker-panels.js`. Это остаток прежнего устройства узкого
  списка, и в файле он лежит у всех, кто те панели трогал: показанный, он стоял
  бы строкой «Remote: mac» рядом с настоящей «Remote sessions» и предлагал бы
  настраивать то, чего на экране нет. Из самого файла ключи не вычищаются:
  `buildSections` незнакомый ключ и так не находит, а чистка переписывала бы
  человеку файл ради того, чего он не видит.

  **Умолчание свёрнутости в узкой таблице спрашивается, а не считается
  пустым.** История, проекты и снимки приходят в узком списке свёрнутыми
  (`defaultCollapsed` в `picker-sections.js`), и галка «expanded», нарисованная
  без оглядки на это, показывала бы развёрнутыми три строки из пяти —
  противореча тому, что человек видит рядом в пикере. Считает это
  `defaultCollapsedFor` в `picker-panels.js`, и считает **от ключа**: секций
  окно настроек не видит. Второй источник правды тут неизбежен, поэтому он не
  молчаливый — тест «умолчание свёрнутости совпадает с тем, по которому живёт
  пикер» гоняет настоящий `buildSections` в обеих раскладках и сверяет с ним
  каждую секцию.

- **Галка в списке имеет две оси, и старую форму `ui.json` надо понимать.**
  `list` — показывать ли колонку (это и значила плоская галка), `statusline` —
  выносить ли галку в строку внизу. `normalizeUiState` поднимает булево
  значение в `list`: не поняв старый файл, первый же запуск после обновления
  сбросил бы человеку все колонки, и выглядело бы это потерей настроек.

- **`config.yaml` после первого сохранения из окна настроек ведёт окно.**
  Перезапись через `serde_yaml` теряет комментарии — а они и есть
  документация. Смягчение одно и разовое: `config.yaml.bak` перед первой
  перезаписью и шапка-предупреждение в новом файле. Патч сливается по ключам
  (`config_file::merge_patch`), иначе окно стирало бы `actions`, про которые не
  знает, и `mqtt.password`, который не показывает.

- **Окно создаётся только из `async`-команды.** Синхронную команду Tauri
  выполняет в потоке цикла событий, а webview на Windows дозревает через этот
  же цикл: `open_settings` без `async` возвращал Ok, окно появлялось, и
  страница в нём не загружалась никогда — белый прямоугольник с рамкой.
  Отладить это тяжелее, чем звучит: то же окно, открытое из `setup` (тоже
  главный поток, но до входа в цикл), рисуется правильно, и разница видна
  только в настоящем пути «пикер → шестерёнка». То же правило и у второго входа
  в настройки — пункта в меню трея: `on_menu_event` крутится в том же потоке,
  и вызов `open_settings` оттуда на месте вернул бы тот же белый прямоугольник.
  Поэтому он уходит в `tauri::async_runtime::spawn`; сторожит это тест
  `tray_opens_settings_off_the_event_loop`, сверяющийся с формой обработчика —
  поведением это не поймать, `build()` отвечает `Ok` в обоих случаях.

- **На маке окно настроек выносит вперёд приложение, а не окно.** Пикер
  объявлен `ActivationPolicy::Accessory` — ни значка в доке, ни очереди на
  передний план, — и созданное им окно остаётся за тем, из которого человек
  полез в трей: за терминалом. `set_focus` тут не при чём, он двигает окно
  внутри приложения, а какое приложение впереди, решает AppKit. Поднимает себя
  `activate_self` в `main.rs` — на Windows это пустая функция, ровно как
  `allow_any_foreground` пуста на маке: передний план пикер там уже отдал себе
  сам, погасив список. Набор параметров у активации пустой: с macOS 14
  `ActivateIgnoringOtherApps` объявлен ничего не делающим.

  Веток у открытия две — окно уже есть и окна ещё нет, — и объединены они
  ровно ради этого вызова: с прежним ранним `return` одна из двух дорог рано
  или поздно потеряла бы активацию, а вторая продолжала бы работать, то есть
  окно выходило бы вперёд через раз. Сторож —
  `opening_the_settings_window_brings_the_application_forward`, и он текстовый:
  вызов уходит в AppKit, на машине разработки этой ветки нет вовсе, а `build()`
  отвечает `Ok` и с активацией, и без неё. Тем же приёмом и по той же причине
  поднимает себя соседний macos-windows-manager (`ax::activate_self`).

- **Плагин хоткеев ходит через главный поток — звать его под мьютексом
  нельзя.** `unregister` и `on_shortcut` в `tauri-plugin-global-shortcut` идут
  через `run_main_thread!`: кладут задачу в цикл событий и блокируются на
  ответе. Пока регистрация жила только в `setup`/`apply_config`, это
  исполнялось inline и не стоило ничего; теперь список вешает поток поллера
  (`project_hotkeys::apply`), и переход настоящий. Держи он при этом свой
  мьютекс, приложение вставало бы насмерть двумя путями сразу: поллер ждёт
  главный поток, а тот ждёт мьютекс в команде `project_hotkeys_taken` — она
  поэтому `async`; и путь короче — `apply_config` зовёт `reapply` прямо с
  главного потока. Отсюда форма `apply_once`: под замком только обмен
  списками, работа с плагином — снаружи. Двух `apply` внахлёст разводит не
  второй мьютекс, а заявка (`claim`/`finish`): ждать опоздавшему нельзя ровно
  по той же причине, по какой нельзя держать замок.

- **Галка-фильтр в статуслайне зовёт `regroup`, а не `render`.** Отбор строк
  живёт в `regroup()`, `render()` рисует уже отобранное. С одним только
  `render` фильтр (`onlyWindow`, `showAll`) срабатывал бы к следующему ответу
  агрегатора — а тот может не прийти вовсе: на скрытом окне такт уходит в
  минуты, а неизменившееся состояние отсекается по отпечатку. Выглядит это
  мёртвым чекбоксом. Какая галка фильтр, решает `FILTER_KEYS`, считанный из
  `TOGGLE_CHECKS`: вторым списком он молча разошёлся бы с первым.

  По той же причине `regroup`, а не `render`, зовёт и **правка строки поиска**
  (`onSearchInput`): от запроса зависит теперь не только рисунок, но и состав
  списка — см. правило ниже. Сторож — «правка запроса пересчитывает состав
  списка, а не только рисунок» в `test/row-contract.test.js`, и он текстовый:
  на видимом окне список догонит сам через секунду, и ошибка видна только на
  скрытом.

- **Спрошенное перебивает отобранное: непустой запрос и любой префикс режима
  отменяют оба отсева.** Решает это `activeFilters` в
  `frontend-src/session-groups.js` — рядом с самими отсевами, а не по месту в
  `regroup`. Причина та же, по которой непустой запрос разворачивает свёрнутые
  секции: искали сессию, а не отбор, и отсев при поиске не сообщает о себе
  ничем — найденного просто нет в списке.

  Болеют этим оба отсева одинаково, поэтому и правило одно.
  `onlyLive` вычищает всё неживое, то есть историю целиком, — и с умолчанием
  конфига (`onlyLive: true`) `/h` показывал `Nothing in history.` всегда,
  сколько бы её ни было. Префикс отменяет отсевы и на пустом запросе именно
  поэтому: `/h` — просьба про историю, и пустой ответ на неё врал бы про
  причину.

  Оговорок по режимам нет намеренно: `/p` и `/s` сессий не касаются вовсе, а
  `/l` и `/r` живые по построению, так что отмена там ничего не меняет, — а
  таблица «какой режим что отменяет» была бы вторым списком рядом с `PREFIXES`
  и разошлась бы с ним на первой же правке. Галки при этом остаются нажатыми:
  отступление временное и кончается вместе с запросом — то же, что со
  свёрнутостью.

- **`onlyWindow` спрашивает про живые сессии, а истории не касается вовсе.**
  Отсев (`buildSessionsPayload`) оставляет `r.window || !r.live`: у закрытой
  сессии окна нет и быть не может, и вопрос «что сейчас на экране» получал от
  неё не ответ «нет», а молчание. Видно это было только вместе с `showAll` —
  и тогда история пропадала до заголовка, ни словом не объяснив причину.
  Живых оговорка не касается: живая сессия без окна уходит по-прежнему.
  Заодно это единственный отсев, у которого своё правило помимо `activeFilters`:
  там отступление кончается вместе с запросом, а здесь его нет вовсе.

- **Заголовок секции — подпись и счёт, и больше ничего.** У свёрнутой истории
  стоял хвост `· last Aug 12`, считался он от `lastActivity` самой свежей
  строки, и вместе с ним ушли поле `lastAt` у секции и таблица `MONTHS` из
  `picker-sections.js`. В истории сотни строк за все времена, и дата новейшей не отвечает ни на один
  вопрос, с которым в историю приходят, — а место в узком заголовке занимала.

- **`showAll` перекрывает `onlyLive`, а не заменяет его.** Конфиг задаёт, с чем
  пикер открывается, галка — отступление от настройки, и отступление
  запоминается в `ui.json`, как и все остальные. Обратной галки «только живые»
  нет намеренно: включённый `onlyLive` и есть умолчание, а вторая галка поверх
  настройки читалась бы как второй фильтр. Оба они при этом — «с чем пикер
  открывается»: непустой запрос отменяет их обоих (правило выше).

- **Пикер гасится перед открытием настроек.** Он `alwaysOnTop` и центрирован,
  окно настроек центрируется тоже и выходит меньше — то есть ложится ровно под
  него и закрывается целиком: не прочитать и не нажать крестик. К `hideOnBlur`
  это отношения не имеет, тот про потерю фокуса; здесь пикер уходит по своей же
  команде, и до создания окна, пока фокус ещё наш.

- **Клик по затемнению гасит пикер сам, а не через потерю фокуса.** Спека
  обещала обратное — «подложка примет клик, фокус уйдёт, `hideOnBlur` сделает
  работу, отдельного обработчика не нужно», — и это неверно на собственных
  флагах окна: на Windows подложка создана с `WS_EX_NOACTIVATE`, на macOS это
  borderless `NSWindow` без `canBecomeKeyWindow`; ни то, ни другое передний
  план по клику не берёт, значит `Focused(false)` не приходит вовсе. Живая
  проверка владельца это подтвердила: клик не делал ничего ни в одной
  раскладке. Теперь обработчик свой на каждой платформе (`WM_*BUTTONDOWN` в
  `wnd_proc`, `ScrimView::mouseDown:`), и оба зовут общую `dismiss` —
  расходиться им нельзя, а разойтись они могли бы только молча: ни одна ветка
  не собирается на машине разработки.

  Гасится пикер **не спрашивая `hideOnBlur`**: тот про уход в чужую программу,
  а включённая подложка делает список модальным на вид, и у клика по
  затемнению значение одно. `acceptsFirstMouse:` на маке обязателен —
  подложка ключевым окном не бывает, то есть каждый её клик для AppKit
  «первый», а первый клик в неактивное окно AppKit по умолчанию съедает.

- **Проектные хоткеи приезжают ответом агрегатора, а не из конфига.** Список
  живёт в `claudeWt.projects` у windows11-manager, демон кладёт его в файл
  трекера, `ccfzf --state` отдаёт полем `hotkey` у строки проекта. Признак
  свежести у них общий с окнами — `windowHost`: пуст (трекер лежит или файл
  протух) — регистрации не трогаем вовсе, непуст и совпал с конфигом — список
  полон и заменяет прежний, даже пустой. Своего таймера у хоткеев нет
  намеренно: второй признак свежести разошёлся бы с первым на первой же правке.
  Вешает клавиши `project_hotkeys.rs` из поллера, а не страница: у скрытого
  окна WebView2 умеет усыплять её целиком, и клавиши вставали бы только при
  открытом пикере. До первого ответа висит список из `hotkeys.json`.

- **Отказ регистрации проектного хоткея обязан быть виден.** Раньше он стоил
  строки в stderr, и `Ctrl+F11`, отобранный соседом по системе (им оказался
  windows-mqtt, регистрировавший те же клавиши из того же конфига менеджера),
  выглядел как сломанный конфиг: расследование заняло полдня. Теперь занятая
  комбинация уходит наверх событием `project-hotkeys`, гаснет в подписи `hk`
  строки проекта и называется в статуслайне.

- **Хоткей в настройках набирают клавишами, и записанное обязано разобраться в
  Rust.** Поля трёх глобальных хоткеев — не `text`, а тип `hotkey`
  (`settings-form.js`): кнопка ловит `keydown`, показывает комбинацию по мере
  набора и пишет её на `keyup`. Набирать туда текст нельзя вовсе — опечатка
  стоила бы молчащей клавиши, а форма записи (`Super` объединяет Cmd и Win, а
  слова `Win` разбор в Rust не знает) человеку теперь не нужна ни разу.

  Собирает строку `comboFromEvent` в `frontend-src/action-hotkey.js`, рядом с
  `parseHotkey` и `RESERVED_CODES`: там живёт весь разбор комбинаций, и второй
  разошёлся бы с первым. Порядок и слова — те же, что у `DEFAULT_*_ACCELERATOR`
  в `main.rs` (`Control+Alt+Super+Shift`), а имя клавиши — `e.code` без
  приставки `Key`/`Digit`. По `e.code`, а не `e.key`, и по той же причине, что
  у `matchesHotkey`: `key` — напечатанный знак, в русской раскладке та же
  клавиша пришла бы буквой «с».

  Словарь клавиш — **общая фикстура с Rust**, `test/fixtures/hotkey-codes.json`,
  и сторожей над ней два (в `action-hotkey.test.js` и `hotkey_codes_all_parse`
  в `main.rs`). Приём тот же, что у `terminal_name` и `place_order`, и по той
  же причине: расхождение поведением не поймать вовсе — окно ответит «saved»,
  строка ляжет в `config.yaml`, а `tile_hotkey` и соседи молча откатятся на
  встроенное умолчание, то есть клавиша просто не сработает.

  Три места, где это упирается в уже оплаченное. `preventDefault` на `keydown`
  обязателен — иначе набираемая комбинация срабатывает как хоткей самого окна.
  Кнопка «Clear» — не украшение: пустое поле значит «взять встроенное
  умолчание», и без неё записать пустоту стало бы нечем (`merge_patch` умеет
  только вставлять). И занятую окном комбинацию контрол показывает **той же**
  `validate`, что стоит на пути сохранения, — своя проверка разошлась бы с ней
  и разрешила бы то, что форма потом отвергнет.

  Отсюда же `GLOBAL_HOTKEYS` отбирается **по типу поля**, а не как «все поля
  вкладки Hotkeys»: рядом с клавишами на ней стоят выпадашки действий мыши, и
  попади они в этот список, форма проверяла бы `tile` на занятую комбинацию.

- **Умолчание второго глобального хоткея живёт в Rust, а в `config-shape.js`
  пусто.** Глобальных хоткея два: `hotkey` показывает пикер, `projectsHotkey`
  открывает его сразу в режиме проектов. У первого умолчание одно на обе
  системы — `SUPER` и есть Cmd на маке и Win на Windows. У второго объединять
  нечего: комбинации выбраны разные, `Win+Shift+F10` против
  `Option+Cmd+Shift+C`, — поэтому в `main.rs` развилка по `target_os`, а окно
  настроек умолчания не знает вовсе. Запиши оно комбинацию строкой —
  и, сохранившись на другой системе, увезло бы в `config.yaml` чужую клавишу.
  Отсюда правило: пустое поле (и отсутствие ключа) значит «взять встроенное»,
  а не «выключить», и `projects_hotkey` в `main.rs` глотает пустую строку без
  жалобы в stderr, в отличие от испорченной.

  Второй хоткей окно **переключает**, как и первый: повторное нажатие его
  гасит. Сначала он был сделан показывающим — рассуждение было, что нажатый на
  уже открытом пикере он должен сменить режим, а не погасить окно, — и это
  оказалось неверно на живом пикере: от любого хоткея пикера ждут переключения,
  и второй, ведущий себя иначе, читается как поломка. Отсюда общая
  `toggle_window` с режимом и общий дребезг `LastToggle`: два хоткея подряд не
  открывают окно дважды. Сам режим живёт префиксом `/p ` в строке поиска,
  поэтому Rust окно только показывает, а правку строки делает страница по
  событию `picker-mode` — `showMode()` в `sessions.html`, общая с `^P`.

- **Жестов мыши на иконке трея два, и что они делают — решает одна таблица.**
  `TRAY_CLICK_ACTIONS` в `src-tauri/src/main.rs` — значение конфига и подпись,
  и таблица эта одна на разбор конфига (`tray_action`), на развилку нажатия
  (`run_tray_action`) и на список в окне настроек. Второй список разошёлся бы
  с первым самым тихим отказом из возможных: клик проходит, ветки себе не
  находит, ни ошибки, ни следа. Сторожей два — `every_tray_click_action_is_handled`
  в самом `main.rs` и `test/tray-actions.test.js`, сверяющий таблицу с
  `TRAY_ACTIONS` в `settings-form.js` **вместе с подписями**: страница и Rust
  — два языка, общего кода между ними нет.

  Взять `MODE_MENU` целиком нельзя: `tile` — действие, а не режим, списка оно
  не показывает вовсе, — поэтому режимы и действия перечислены здесь вместе.
  Клик при этом **переключает** окно, а не показывает: жест делают не глядя в
  список, и повторный обязан погасить окно — то же правило, что у хоткея, и
  ровно так вёл себя клик до появления настройки.

  Ключей два (`trayClickAction`, `trayMiddleClickAction`), умолчания разные
  (`sessions` и `tile`) и живут они **у самого нажатия**, а не в таблице: та
  отвечает на вопрос «что бывает», а не «что по умолчанию у этой кнопки».
  Конфиг читается на каждом нажатии — иначе смена настройки требовала бы
  перезапуска; так же поступает и `tile_press`. Незнакомое значение
  откатывается на умолчание **со строкой в журнал**, а не молчит: мёртвая
  иконка выглядит сломанным приложением, а не опечаткой в конфиге.

  Третьего жеста нет, и это проверено, а не забыто. Правая кнопка занята меню
  трея — единственной дорогой к настройкам, выходу и режимам. Двойного клика
  не бывает на маке: `TrayIconEvent::DoubleClick` эмитится единственным местом
  — `platform_impl/windows/mod.rs` в крейте `tray-icon`, — а на Windows он
  приходит **после** обычного `Click(Up)` (`WM_LBUTTONUP` → `WM_LBUTTONDBLCLK`),
  то есть одиночное действие пришлось бы задерживать на интервал двойного
  клика. Долгого нажатия в API нет ни на одной системе. Средняя кнопка
  приходит на обеих, отдельным событием и без задержки — потому она и выбрана.

- **Пункты-режимы меню трея живут одной таблицей, а показывают — не
  переключают.** `MODE_MENU` в `src-tauri/src/main.rs` — id пункта, имя режима,
  подпись, — и таблица эта одна на сборку меню и на разбор нажатия
  (`mode_for_menu_id`). Два списка разошлись бы самым тихим отказом из
  возможных: пункт в меню есть, нажатие проходит через `on_menu_event`, ветки
  себе не находит — ни ошибки, ни следа, просто ничего не происходит.

  Имена режимов в таблице — те же, что в `PREFIXES` (`picker-mode.js`): они
  уезжают на страницу телом события `picker-mode` и ищутся там. Опечатка стоит
  молчащего пункта меню, и поймать её можно только сверкой двух файлов на двух
  языках — сторож `test/tray-modes.test.js`. Поведением не поймать вовсе: обе
  половинки по отдельности работают верно, а `withPrefix` незнакомого режима
  оставляет строку как есть, то есть окно открывается обычным списком.

  Событие одно на все режимы, с именем в теле, а не по событию на режим: четыре
  имени на одной стороне против четырёх подписок на другой — это опять два
  списка. Уходит оно **после** `picker-shown`, и порядок обязателен: по
  `picker-shown` страница чистит строку поиска (`beginShow`), и приди режим
  раньше, префикс стёрло бы тем же показом, ради которого его и ставили.

  Пункт меню **показывает**, а не переключает, — и это не противоречие
  правилу про хоткей выше, а его продолжение. Хоткей нажимают вслепую, поэтому
  он гасит окно повторным нажатием; в меню режим выбирают глазами, уже открыв
  трей, и выбравший `History` ждёт историю, а не гашения окна, которое ради
  этого и открыл. Тогглом в меню остаётся один `Sessions`.

  Слова `Show` в подписях нет: одинаковое у всех пяти пунктов, оно не различало
  бы ничего. Хоткей есть только у двух режимов, поэтому у остальных нет ни
  акселератора, ни подписи об отказе регистрации; рабочую подпись
  `projects_item_label` берёт из той же `MODE_MENU`, а не пишет вторично.

  **На Windows комбинация едет в подписи, а не в нативном слоте**, и слот там
  обязан остаться пустым. Причина — одно слово: muda пишет модификатор `SUPER`
  как `Windows`, это хардкод в его `Display`
  (`platform_impl/windows/accelerator.rs`), а клавиша подписана `Win`, и
  `Windows+Shift+C` длиннее самого пункта меню. Подменить рендер в muda нечем,
  поэтому `menu_item_parts` в `main.rs` собирает подпись сама — через `\t`,
  ровно тем приёмом, каким её кладёт туда и сам muda
  (`format!("{text}\t{}", accelerator)`): выравнивание по табуляции делает
  Win32, и колонка выходит та же. Отдай мы при этом ещё и слот, muda приписал
  бы к нашей табуляции свою вторую — две колонки в одной строке.

  Цена — запись в таблице акселераторов меню, но она и была украшением: меню
  трея клавиш не слушает вовсе, работает настоящий хоткей, глобальный. На маке
  ветка не включается: NSMenuItem рисует `⌘⇧C` сам, а табуляция в заголовке
  была бы литеральной. Обе ветки под `cfg`, и на Linux собирается только вторая
  — Windows-ветку приходится проверять отдельно, подставным `cfg`; поведением
  её здесь не поймать вовсе.

- **Меню `^K` знает виды строк поимённо, и общая ветка — только для настоящих
  сессий.** `availableActions` (`frontend-src/session-actions.js`) ветвится по
  `kind` до всего остального, и веток теперь четыре: `project`, `zellij`,
  `snapshot`, `snapshot-session`. Причина одна на все: общая ветка читает
  работу агента — запись агента, pid, живость, ссылку на PR, — а у строки, где
  этого нет, она рисует не пустоту, а обещание. Заголовку снимка так доставалась
  «Session info», открывавшая карточку сессии по строке, в которой сессии нет.

  Заголовок снимка получает один пункт — восстановление, — и это **исключение
  из правила «открытие висит на Enter, в меню его нет»**. Оплачено пустотой:
  другого дела у заголовка не бывает, а пустое меню на строке, у которой
  действие есть, читается как поломка. Строке внутри снимка того же пункта не
  досталось, и это не забывчивость: меню у неё непустое (каталог настоящий, за
  него тянут действия папки и `New session`), то есть цена исключения не
  уплачена. Пустым её меню всё же бывает — у строки без каталога; такое меню
  `openMenu` не открывает вовсе, по тому же правилу.

  Сторожа два, и второй важнее первого. «Меню решено для каждого вида строки»
  гоняет одну строку, несущую всё сразу, по всем видам и сверяет со списком:
  новый вид, заведённый потом, свалился бы в общую ветку молча. «Каждый
  встроенный пункт меню обработан в `runAction`» — текстовый, и ловит он самый
  тихий отказ из возможных: пункт, попавший в список и не разобранный в
  `sessions.html`, проходит проверку применимости и выходит ни с чем. Ни
  ошибки, ни следа — нажатие просто не делает ничего.

- **Буква встроенного действия не должна забирать у поиска буфер обмена.**
  Прямые клавиши действий гасят событие (`preventDefault` в ветке `plainCtrl`),
  а поле поиска в пикере сфокусировано всегда: буква, совпавшая с правкой
  текста, отбирает её насовсем. `seen` поэтому висит на `^D`, а не на
  напрашивавшейся `^V` («viewed») — вставляют в поиск как раз то, что теперь
  ищется, начало id сессии. Сторож — `test/action-hotkey.test.js`, список
  `c v x z`.

  Буквы ярлыков режимов в этот список не входят намеренно: они клавишу тоже
  отнимают, но сознательно. `^P` открывает проекты, `^L` — свои живые сессии,
  `^H` — историю, `^S` — снимки; `/r` клавиши не получил вовсе, к чужим
  сессиям отдельно ходят реже. Все четыре обязаны стоять в `RESERVED_CODES`
  — иначе встроенная ветка съедала бы событие у настроенного человеком
  действия, и оно молчало бы. Действие `pr` из-за этого переехало с `^P` на
  `^G` (мнемоника своя — GitHub, куда оно и ведёт), а `^A` вернулся полю
  поиска: «выделить всё» в строке поиска снова работает.

  Цена `^H` известна и принята человеком: на macOS это системная
  emacs-привязка «удалить символ слева» в текстовом поле, а прямые клавиши
  гасят событие через `preventDefault`. Backspace и Delete работают, теряется
  только она.

- **Проектный хоткей решения не принимает — он его пересылает.** Нажатие уходит
  просьбой `{action:"terminal", cwd}` в `<base>/windows/claude-session-open`, а
  «поднять последнее окно этого каталога или завести новую сессию» решает
  `openClaudeProject` у windows11-manager. (Под `projectHotkeyAction: new`
  просьба уходит другая, `terminal-new` с посчитанным здесь именем, — то есть
  решение снимается вовсе, а не принимается на месте; см. правило про две
  просьбы ниже.) Решать это здесь нельзя по двум
  причинам: список у скрытого пикера отстаёт до восьми минут (бэкофф в
  `poller.rs`), а при выключённом фоновом опросе не обновляется вовсе; и
  профиль Windows Terminal по каталогу знает только менеджер —
  собранная здесь команда `wt.exe` его теряет. Шлёт просьбу Rust, а не
  страница: у скрытого окна WebView2 умеет усыплять её целиком, а хоткей
  нажимают ровно тогда, когда пикер скрыт. Страница остаётся запасной дорогой
  на случай ненастроенного брокера — там она поднимает новую сессию, как
  раньше.

- **Нулевой `windowPid` больше не про грамоту, но проверку в `canFocus`
  оставили.** Раньше это был адресат `AllowSetForegroundWindow`, и без адресата
  подъём был бы молчащим отказом; теперь грамота безымянная, а поле осталось
  признаком живого трекера — свой pid в файл окон кладёт он сам. Проверка в
  `canFocus` от этого не изменилась: ноль значит «файла нет, он чужой или
  протух», и Enter в этом случае честнее открыть терминал у себя. Проектный
  хоткей отменял на нулевом pid только грамоту, но не просьбу, — теперь
  отменять нечего, и `tracker_pid_from` из `project_hotkeys.rs` убран вместе с
  этой развилкой.

- **Терминал по каталогу открывает менеджер, а пикер — только там, где
  менеджера нет.** Просьб две: `{action:"terminal", cwd}` и
  `{action:"terminal-new", cwd, name}`, обе в
  `<base>/windows/claude-session-open`. Разница одна: `terminal` сначала ищет
  открытое окно этого каталога, `terminal-new` не ищет вовсе. `^N` и пункт
  «New session» шлют вторую всегда; Enter на строке проекта и проектный
  хоткей — ту, которую назвал конфиг (правило ниже). Транспорт у обоих
  решает `chooseProjectOpenAction` (`open-transport.js`) — та же
  `chooseOpenTransport`, что и у Enter на строке сессии: менеджера просят
  только на машине трекера и при настроенном брокере, иначе остаётся местная
  `newSession`, и профиль там теряется по-честному — на такой машине
  `claudeWt.projects` не существует.

- **Какую из двух просьб послать, решает настройка, а не место в коде.** Ключей
  два — `projectOpenAction` (Enter и клик на строке проекта, умолчание `new`) и
  `projectHotkeyAction` (проектная клавиша, умолчание `focus`), — значения у
  обоих `new` | `focus`. Умолчания разные потому, что поводы разные: строку
  проекта выбирают глазами, уже открыв пикер, и просят ею начать работу —
  вернуться в идущую есть чем и без того, у неё своя строка в списке; клавишу
  жмут вслепую, чтобы вернуться туда, где работа идёт. Названы умолчания у
  самих нажатий, а не в таблице: та отвечает на вопрос «что бывает», а не «что
  по умолчанию у этого входа», — то же правило, что у `TRAY_CLICK_ACTIONS`.

  Таблица `PROJECT_OPEN_ACTIONS` одна на всё: разбор обоих значений, обе
  развилки и список в окне настроек; вторая её половина — в `settings-form.js`,
  сторож (`test/project-open-actions.test.js`) сверяет их **вместе с
  подписями**. Разбор при этом всё же двойной — `config_choice` в Rust и
  `choice` в `config-shape.js`, — и иначе нельзя: `projectOpenAction` читает
  страница (Enter жмут при показанном окне), `projectHotkeyAction` — Rust
  (клавишу жмут при скрытом, где WebView2 усыпляет страницу целиком).

  На странице развилка стоит **до** выбора транспорта и на `new` зовёт готовую
  `newSessionHere`: там уже написаны имя, занятие имени, гашение и откат на
  местную дорогу, а второй экземпляр этого разошёлся бы с первым — ровно та
  мина, на которой подорвался `newSession` с самодельным argv терминала. На
  машине без менеджера значение не решает ничего: местная `newSession` всегда
  новая, поднимать там нечем, и об этом сказано в подписи поля.

  **Ветка `new` у хоткея потребовала третьего порта в Rust.** Имя обязано
  считаться на нашей стороне: менеджер списка занятых не ведёт и взял бы
  basename каталога — то самое имя, которое уже носит открытая сессия, — а два
  окна с одним заголовком трекер привяжет к одному слоту. Отсюда
  `src-tauri/src/session_name.rs` рядом с `terminal_name` и `place_order`, и
  держится он так же: общая фикстура `test/fixtures/session-name.json` и два
  сторожа над ней. Поведением расхождение не поймать вовсе — просьба уходит,
  брокер подтверждает, окно открывается, просто имя другое.

  Занятые имена Rust берёт из снимка поллера, и одного его мало: у скрытого
  окна такт уходит в бэкофф до восьми минут, то есть ответ ещё не знает о
  сессии, заведённой прошлым нажатием. Дыру закрывает своя память выданных
  имён (`session_name::issue`), и живут они дольше, чем на странице:
  `BACKGROUND_MAX + 60 с` против минуты у `issuedNames` — там `^N` жмут при
  открытом окне, где опрос идёт раз в секунду. Памяти этой две, и они не
  общие: `^N` и хоткей по одному каталогу в одну минуту могут дать одно имя
  дважды. Случай узкий (пикер при хоткее скрыт, при `^N` показан), а платой за
  его закрытие была бы дорога данных в усыплённую страницу — та самая, ради
  ухода от которой всё это и живёт в Rust.

  Пустое имя (путь с `;`, каталог без basename) откатывает хоткей на прежнюю
  просьбу `terminal` **со строкой в журнал**: `open_new` с пустым именем —
  тело, которое врёт о том, что знает, а промолчать нельзя, потому что ответа
  у публикации нет.

- **Выбранный в пикере терминал главнее дефолта менеджера, и уезжает он именем
  в теле просьбы.** На машине с менеджером терминал открывает не пикер, и поле
  `terminal` из `config.yaml` там не читается вовсе — то есть выбранный в
  настройках WezTerm молча превращался в Windows Terminal, потому что `wt` стоит
  дефолтом в `claudeWt.terminal` менеджера. Настройку пикера человек видит, а
  конфиг менеджера — нет, поэтому побеждает первая. Имя едет во **всех трёх**
  просьбах, кончающихся терминалом (`open`, `open_project`, `open_new` в
  `src-tauri/src/mqtt.rs`): Enter на сессии, Enter на строке проекта — та же
  дорога у проектного хоткея — и `^N`. Забыть любую значило бы, что выбор
  действует через раз; все три сняты живьём подпиской на топик и несут имя.

  Словарь имён общий с реестром `claudeWt.terminals` у windows11-manager —
  `wt`, `wezterm`, `kitty`, `ghostty`, `iterm2`, — и системы в имени нет
  намеренно: WezTerm на маке и на Windows зовётся одинаково, а что за именем
  стоит, знает только принимающая сторона. Поле необязательное: пустое,
  отсутствующее и незнакомое менеджер читает как «бери свой дефолт», поэтому
  порядок выкатки не важен ни в одну сторону.

  **Имя считает Rust, а не страница** (`terminal_name` в `mqtt.rs`): ту же
  просьбу шлёт `project_hotkeys.rs`, а хоткей нажимают ровно тогда, когда пикер
  скрыт и webview усыплён. Своего ключа в конфиге у пресета нет (см. правило про
  `matchPreset` выше), поэтому имя считается от полей — и потому в Rust лежит
  копия таблицы из `frontend-src/terminal-presets.js`. Сверяет их текстовый
  сторож `test/terminal-name.test.js`; поведением такое не поймать вовсе:
  разошедшееся имя менеджер не узнает и молча возьмёт свой терминал.

  Ключ в Rust — **имя файла без каталога**, а не путь целиком и не путь с
  аргументами, и это мягче, чем `matchPreset`. Разница намеренная: там вопрос
  «пресет или Custom», и дописанный руками флаг обязан честно дать Custom;
  здесь вопрос «какой это терминал», и на него ни флаг, ни каталог не влияют —
  у msi, portable-распаковки и scoop путь разный, а терминал один. Неточная
  запись в таблице одна, `osascript` → `iterm2`: AppleScript сам по себе
  терминала не называет, но другого признака у этого пресета нет, а цена ошибки
  сегодня нулевая — просьбы об открытии сессии на маке не принимает никто.

- **Экран для нового окна называет точка курсора, а ставит окно трекер.**
  Ключ `openOnActiveDisplay` в `config.yaml`, галка на вкладке **Window** сразу
  под `showOnActiveDisplay`. Галки соседние, но не половинки одной: та про окно
  списка, эта про окно терминала, и связывать их нельзя — вопросы разные, и
  постоянное место у списка при подвижном у терминала это нормальное желание.
  Сторож — «галки не трогают друг друга» в `main.rs`, потому что связать их
  потом легко, а увидеть это можно было бы только глазами и только на машине с
  двумя мониторами.

  В теле просьбы едет **точка** (`cursor: {x, y}`, `put_cursor` в `mqtt.rs`), а
  не номер экрана: у windows11-manager нумераций мониторов три сразу — своя в
  конфиге, hMonitor и FancyZones, — и общий словарь на два репозитория
  разошёлся бы молча, окно встало бы не туда, а ответа у публикации нет. Точку
  же он переводит в монитор сам (`findMonitorByPoint`), тем же кодом, каким
  делает это для своих раскладок. Целыми пикселями и с округлением, а не
  усечением: экран слева от главного даёт отрицательную точку.

  Читает курсор Rust (`cursor_hint` в `main.rs`), а не страница, и по той же
  причине, что имя терминала и порядок плитки: ту же просьбу шлёт проектный
  хоткей, а его жмут ровно тогда, когда пикер скрыт и webview усыплён. На
  главный поток за курсором не ходят намеренно — `run_on_main_thread` из потока
  поллера это тот самый ход, на котором приложение уже вставало насмерть
  (правило про плагин хоткеев выше).

  **Своей машине — да, чужой — нет,** и различает это единственный аргумент,
  который команда не пересылает, а которым решает: `sameMachine` у
  `open_session_mqtt`. У этого входа два повода (`openViaManager`: Enter здесь
  и пункт «Open on \<host\>» оттуда), и во втором курсор мака уехал бы
  Windows-менеджеру координатой чужого стола. Считает признак та же
  `chooseOpenTransport`, что выбирает транспорт, — второе правило про то же
  самое разошлось бы с первым. Отсутствие ключа читается как «не своя»: забытый
  аргумент обязан оговорку выключать. У `open_project_mqtt` и `new_session_mqtt`
  оговорки нет и не нужно — `chooseProjectOpenAction` отдаёт ветку менеджера
  только на машине самого менеджера.

  Отсутствие ключа `cursor` целиком значит «ставь как ставил»: так выглядит и
  выключенная галка, и пикер прежней версии, — и приёмник обязан вести себя
  одинаково в обоих случаях. Поднятого окна правило не касается вовсе: галка про
  новые окна, а переезд уже открытого — другой вопрос, и его не задавали.

  **Поставить окно мало — его надо ещё и удержать.** На той стороне за
  свежепоставленное окно берутся двое, и оба про просьбу не знают: расстановщик
  новых окон применяет правило из `config.windows`, подобранное по заголовку или
  пути, а демон трекера при первой привязке окна к знакомой сессии тащит его в
  **запомненные** границы и на запомненный стол — то есть туда, где сессия жила
  вчера. Поэтому поставленное по курсору окно менеджер помечает как закрытое от
  автоматики (`src/no-autoplace.js` там же), а демон, встретив пометку,
  переписывает слот сегодняшним местом вместо переноса. Пометка живёт файлом,
  а не переменной: процессы разные — служба MQTT и `claude-wt watch`.

  Поводов у пометки три, и третий добавлен потому, что без него галка отменяла
  бы сама себя: неглавный экран, прямая просьба (`noAutoplace`, правило ниже) и
  **перебитая память о месте** — у окна был слот, и курсор его только что
  заменил. Оговорка про главный экран написана про окна, у которых своего места
  ещё нет; у окна со слотом спор другой, и решался он не в пользу человека —
  окно вставало куда просили и через пару тиков демона уезжало обратно.

  **Знакомую сессию менеджер поднимает восстановлением, и курсор туда доезжает
  тоже.** Дорог у постановки по курсору три — новая сессия, `resume` и
  восстановление из слота, — а правило у них одно (`cursorRule` в
  `windows11-manager/src/claude-wt/cursor-place.js`). Второго быть не может:
  разойдись они, галка работала бы по-разному в зависимости от того, помнит ли
  трекер эту сессию, — то есть через раз и необъяснимо; ровно так она себя и
  вела, пока восстановление курсора не получало вовсе. Курсор при этом отменяет
  и **стол**: окно, уехавшее следом на запомненный рабочий стол, утащило бы
  туда и человека. Восстановление пачкой (старт машины, `^S`) курсора не
  получает — там окон много, и один экран на всех был бы решением за человека.

  **На маке галка не делает ничего, и это сказано в её подписи.** Терминал там
  открывает сам пикер (`spawn_detached`), а двигать чужое окно он не умеет;
  трекер бы смог, но `macos-windows-manager` не принимает просьб об открытии
  вовсе (`openSession: false`), не знает идентичности экранов (`Display` там —
  голый прямоугольник) и курсора не читает. Маковская половина — задача в
  `# future`, и она не поле в теле, а новый протокол.

- **Ctrl на строке списка отменяет расстановку у одного открытия, а галка — у
  всех.** Ctrl+Enter и Ctrl+клик шлют в теле два ключа сразу: точку курсора —
  не спрашивая `openOnActiveDisplay`, — и `noAutoplace: true`, по которому
  менеджер помечает окно закрытым от автоматики независимо от того, главный
  экран или нет (`placeByCursor` в windows11-manager, до правки помечавшая
  только неглавный). Разница вопросов и есть причина двух ключей: галка
  отвечает на «как открывать всегда», модификатор — на «как открыть вот эту»,
  и выводить второе из первого значило бы, что человек, не поставивший галку,
  просьбы задать не может вовсе.

  Флаг без курсора не уезжает (`placement` в `main.rs`): пометку приёмник
  ставит на той же дороге, какой ставит окно по курсору, и «не двигай» без
  «поставь сюда» молча не сделало бы ничего. Отказ курсора называется в
  журнале — ответа у публикации нет, и промолчав, мы отдали бы человеку
  просьбу, выглядящую сработавшей.

  Мерка модификатора одна на клавишу и на мышь — `noAutoplaceWanted` в
  `open-transport.js`, Ctrl или Cmd без Shift и Alt: Shift занят
  переключением отметки «просмотрено», и промах по нему не должен молча
  становиться просьбой о другом открытии. Ключ едет всеми тремя просьбами,
  кончающимися терминалом (`open`, `open_project`, `open_new`) — забудь одну,
  и модификатор работал бы через раз: строка сессии слушалась бы, а строка
  проекта молчала. У проектного хоткея его нет и быть не может: клавишу жмут
  вслепую при скрытом пикере, спросить «куда ты смотришь» там не у кого.

  На macOS ветка живёт только на Cmd: Ctrl+клик система превращает в
  `contextmenu`, и откроется меню `^K`. Терять нечего — менеджера на маке нет
  вовсе, а без него окна никто и не расставляет.

  **Выкатывать в порядке «сперва менеджер, потом пикер».** Ключ, которого
  приёмник ещё не знает, он пропускает молча: окно откроется под курсором и
  тут же уедет в слот, а выглядеть это будет не отказом, а обычным открытием.

- **Имя новой сессии считает пикер, а не менеджер.** `uniqueSessionName` знает
  занятые имена (живые сессии плюс выданные за последнюю минуту), а менеджер
  такого списка не ведёт и взял бы basename каталога — то самое имя, которое
  занято открытой сессией. Два окна с одним заголовком трекер привязал бы к
  одной сессии. Поэтому в `terminal-new` имя едет в теле и на той стороне
  главнее каталога (`sessionNameFor` в `project-helpers.js`), а после удачной
  отправки занимается в `issuedNames` — иначе два быстрых `^N` дали бы одно имя
  дважды.

- **Адрес просьбы называет трекер, а не конфиг пикера.** Трекеров теперь
  несколько, у каждого свой префикс топиков, и просьба о подъёме или об
  открытии сессии обязана уйти на топик именно той машины, где стоит строка,
  — не на `<config.base>` пикера, тот отвечает только за машину, на которой
  пикер настраивали руками. Адрес приезжает полем `mqttBase`: у записи окна —
  как топик для подъёма, у записи машины — как топик для открытия сессии
  (`mqttBaseFor()` и `openManager()` в `frontend-src/session-windows.js`).
  Рассматривались и отвергнуты два других устройства. Сегмент машины в самом
  топике не годится: у windows11-manager `commandFromTopic` отбрасывает
  хвост, содержащий косую черту, — это защита от собственного эха при
  подписке на `#`, — и сегмент машины сломал бы разбор у соседа. Поле `host`
  в теле просьбы тоже не годится: оно потребовало бы правок в
  windows11-manager и асимметричной обратной совместимости — новому пикеру
  пришлось бы помнить, что старый менеджер поля не поймёт. Отсюда решение без
  правок соседа: у каждой машины свой базовый топик, и называет его она сама.
  Строка адреса приезжает из файла, написанного на чужой машине, и потому в
  `src-tauri/src/mqtt.rs` просеивается белым списком (`resolve_base`), а не
  кавычится — `#` и `+` в MQTT подстановочные знаки, публикация по такому
  топику ушла бы мимо всех. Отказ просеивания откатывает на
  `<config.base>/windows`, а не роняет просьбу: старый трекер адреса не
  называет вовсе, и на этой ветке пикер обязан вести себя как прежде.

- **`openSession` — отдельное поле, а не вывод из `focus`.** Способности
  разные: `focus` — умеет ли трекер поднимать уже открытое окно, `openSession`
  — берётся ли менеджер этой машины открывать сессии и терминалы вовсе. Мак
  пишет `focus: true` (окна там поднимает сам трекер через Accessibility) и
  `openSession: false` (терминалы там открывает сам пикер, и открывает верно
  — менеджера на маке нет). Выведи пикер второе поле из первого, упавший
  Windows-трекер оставил бы живым только мак — и пикер назначил бы менеджером
  его, хотя мак просьбу об открытии терминала принять не может: Enter
  замолчал бы, а молчащий Enter хуже открытого терминала. Живёт поле только в
  записи машины (`windowHosts`), а не окна (`windows`): у строки проекта окна нет
  вовсе, а спросить «кто откроет терминал» нужно и про неё — `openManager()`
  берёт поле оттуда, а не из записи окна. Отсутствие поля читается как
  «берётся» — то же правило, что у `canFocus`: windows11-manager этого поля
  не пишет и не должен, и правкой его не тронули.

- **Секции собирает одна `buildSections`, а раскладок у них две.**
  Список — и узкий, и широкий — это одни и те же секции: по секции на группу
  `groupSessions`, плюс `Projects` и `Snapshots`. Собирает их
  `buildSections` (`frontend-src/picker-sections.js`), и от раскладки
  (`layout: 'narrow' | 'wide'`) зависят ровно две вещи: номер колонки и
  умолчание свёрнутости. Больше нигде раскладка ничего не
  решает, и второй сборки нет намеренно: она разошлась бы с первой на первой
  же правке — узкий список уже собирался тремя своими ветками
  (`renderSessions`/`renderProjects`/`renderSnapshots`), и режимы `/p` и `/s`
  подменяли в нём весь список вместо того, чтобы оставить одну секцию.
  Разметка строки одна на оба режима (`sessionItem`, `projectItem`,
  `snapshotItem`), карточка — это CSS под `#list.blocks`, а не вторая
  разметка. `^F` переключает флаг `fullscreen`: `#list` получает класс
  `blocks`, а страница берёт вторую половинку `collapsed`.

  **Ключ секции стабилен, а счёт живёт в `count`, а не в заголовке.**
  `groupSessions` даёт группе `key` (`live`, `remote:<host>`, `past`,
  `past:<N>`, `zellij`) и `label` без числа; счёт приписывает
  `sectionHeaderText` при отрисовке. Раньше ключ считался от заголовка
  (`g:Active sessions - 3`) — то есть менялся каждый раз, когда сессия
  засыпала: сегодня это стоило лишней пересборки каркаса, а с приходом
  свёрнутости стоило бы и её — секция разворачивалась бы сама собой.

  **Пять префиксов, и таблица у них одна** (`PREFIXES` в `picker-mode.js`):
  `/l` свои живые, `/r` чужие, `/h` история, `/p` проекты, `/s` снимки. Разбор,
  снятие и вставка ходят по одному и тому же списку — иначе `^L` на строке с
  чужим префиксом приписал бы свой поверх. Хвост `(\s+|$)` у каждой записи
  обязателен: без него `/lib` уводил бы в `local`, а `/home` — в `history`.
  Префикс оставляет на экране одну секцию и **разворачивает** её независимо от
  `ui.json`: иначе `/h` при свёрнутой по умолчанию истории показал бы один
  заголовок, то есть ровно ничего. Отката в поиск по сессиям у `/l`, `/r` и
  `/h` нет намеренно — пустая история это факт, а не непонятая команда, и
  подмена списка молча врала бы про причину; вместо неё три подписи
  (`No sessions on this machine.` и соседи). Откат есть только у `/s`, и он не
  про пустоту, а про способность: восстанавливать снимок чужой машины нечем,
  и живёт он в `shownModeAndQuery`.

  **Раз режим живёт в строке, выход из режима — это Esc, стирающий строку.**
  `onEscape` в `sessions.html`: непустая строка очищается, и только на пустой
  уходит `hide_picker`. Гасил бы Esc окно сразу — самая привычная клавиша
  отмены уводила бы из пикера вовсе, а вернуться к обычному списку можно было
  бы только стиранием руками. Очистка одношаговая, вместе с префиксом: выход
  из `/p foo` тремя нажатиями читался бы как заедание клавиши, и справочник
  обещает человеку два. Зовётся оттуда та же `onSearchInput`, что и при правке
  руками, — без неё `active` и `selectionReset` остались бы от прежнего
  запроса, и выбор повис бы на строке, которой в новом списке нет. На
  свежепоказанном окне строка пуста всегда (`beginShow`), так что первый же
  Esc после открытия по-прежнему закрывает пикер.

  **`/` возвращает фокус в поиск, и только когда его там нет.** Обработчик
  клавиш висит на `document`, поэтому клавиши работают всегда, а набранный
  текст уходит туда, где фокус, — а клик по строке списка, по заголовку секции
  или по галке статуслайна уводит его с поля. Набор после этого проваливается в
  никуда, без единого признака, что что-то не так. Проверка
  `document.activeElement !== search` обязательна: `/` начинает все пять
  префиксов, и перехватывай ветка его безусловно — набрать `/p` стало бы нечем
  вовсе. Та же цена, за которую `seen` уехал с `^V` на `^D`, и та же причина,
  по которой справочник открывает F1, а не `?`. Символ в строку при этом не
  попадает: `/` здесь команда, а не ввод, — иначе нажатие поверх набранного
  «foo» дало бы «foo/». Стоит ветка **после** ранних выходов трёх оверлеев: у
  них свои клавиши, и строки поиска на экране нет вовсе. Причину — потерю
  фокуса на клике — эта правка не трогает: возврат фокуса после клика имеет
  свою цену (галка перестала бы переключаться пробелом), и решать это надо
  отдельно.

  **Чужие живые сессии склеиваются обратно в один блок — в обеих раскладках.**
  Делит их по машинам `activeGroups` (группа на каждый `windowHost`), а
  `buildSections` собирает обратно. В широкой причина — колонка: блок её
  занимает целиком, и пять трекеров дали бы пять узких колонок на то, что
  человек читает как одно «не здесь».

  В узкой склейки сначала не было, и рассуждение было такое: строки идут
  сверху вниз, лишний заголовок ничего не стоит, а имя машины в нём полезно.
  Оказалось, что стоит, и не заголовок, а ключ. `remote:<host>` живёт ровно
  столько, сколько машина видна; в `order` он не попадает, пока панель не
  перетащили; а после первого перетаскивания чего угодно другого панель без
  места уезжает **в конец** узкого списка — под историю, проекты и снимки, то
  есть с глаз. На живой машине так и вышло: чужих панелей на экране не было
  вовсе, а в окне настроек лежали две мёртвые строки `Remote: <host>` — по
  одной на машину. Постоянный ключ `remote` этим не болеет, а имена машин
  никуда не делись: они подзаголовки внутри блока.

  Склейка узнаёт чужую группу по её пометке
  `group.remote`, а не по заголовку: заголовок носит имя машины — данные с той
  стороны, — и разбор текста сделал бы это имя форматом, который нельзя менять.
  По той же причине и историю опознаёт пометка `group.past`, а не заголовок:
  раньше её узнавали по строке `Not running`, и правка формулировки молча
  увела бы её из своей колонки и выключила сворачивание. Заголовок склеенного
  блока — `Active remote sessions`, счёт приписывает `sectionHeaderText`, ключ
  — постоянный `remote`: по ключу помнится и отрисовка блока, и свёрнутость, и
  считайся он от имён машин, уснувшая на соседней машине сессия пересобирала бы
  колонку целиком.

  **Порядок чужих машин — по свежести, а не по алфавиту.** Ключ тот же,
  которым меряется свежесть строк внутри группы (`recentKey`, минуты), а не
  новый: второй разошёлся бы с первым. По той же причине и `buildProjectList`
  сортирует не сам, а зовёт `compareSessions(a, b, 'recent')`: полей у строки
  проекта ровно те три, которых она просит (`label`, `id`, `lastActivity` —
  названы как у сессии как раз затем), а две копии округления разошлись бы на
  первой же правке. Режим там всегда `recent`, а не выбранный `^O`: ни
  стоимости, ни времени запуска агента у проекта нет, и в прочих режимах
  `missingLast` утопил бы весь список одинаково. Минуты нужны и сами по себе — на
  секундах две почти одинаково свежие машины менялись бы местами от опроса к
  опросу, а список перерисовывается раз в секунду. На равном ключе машины
  разводятся по имени: другого устойчивого порядка у имён нет, а устойчивый
  обязателен. Видно это в обеих раскладках: в узкой это порядок секций, в
  широкой — порядок подзаголовков внутри склеенной.

  **Раскладка широкого режима — три колонки по умолчанию, до пяти
  перетаскиванием, и умолчание в ней задано смыслом строк, а не их числом.**
  Слева свои живые сессии, посередине чужие и под ними
  проекты, справа история и под ней снимки. Номер колонки ставит секции
  `buildSections` — по тому же признаку, по которому блок собран
  (`group.remote`, `group.past`), — и он же задаёт порядок блоков: колонка за
  колонкой, сверху вниз внутри колонки. Порядок этот и есть порядок чтения, а
  по нему ходят `←/→` (`moveBetweenBlocks`): разъедься он с видимым, стрелка
  уводила бы не туда, куда смотрит глаз. Тело блока страница ищет по ключу
  (`blockBodies`), а не по номеру узла: блоки лежат внутри колонок, и порядок
  узлов в `#list` с порядком блоков не совпадает.

  **Смысл строк — умолчание, а не закон: человек волен перенести секцию куда
  угодно.** Порядок и колонка, назначенные перетаскиванием заголовка, живут в
  `order` из `ui.json` и ложатся поверх этого умолчания (`applyWideOrder` и
  `applyNarrowOrder` в `picker-sections.js`). Названная в файле секция едет в
  названную колонку, **не** названная остаётся в своей по смыслу — иначе одно
  перетаскивание сгоняло бы весь список в первую колонку. Порядок результата
  при этом остаётся порядком чтения: колонка за колонкой, сверху вниз, — то
  есть `←/→` ходят по нему по-прежнему, и сторожит это тест, сверяющий, что
  список секций идёт по неубыванию номера колонки.

  Верхний уровень — flex-строка из flex-колонок, и сеткой это не делается.
  Главному списку отдана вся высота, то есть надо охватить все ряды, а
  `grid-row: 1 / -1` считает `-1` по **явной** сетке, которой здесь нет вовсе:
  ряды неявные, размеченные по содержимому, и охватывать нечего. Во
  flex-колонке полная высота достаётся растяжением, сама собой. Пустая колонка
  не рисуется — она забрала бы у соседей долю ширины ради пустоты; ширину
  задаёт `flex`, а не доля от их числа, поэтому на `/p` и `/s` единственная
  колонка занимает экран целиком.

  **Своя живая панель показывается всегда — даже с нулём сессий, — и это
  следствие правила про пустую колонку.** Ей отдана первая колонка, и на
  машине без единой своей живой сессии та исчезала целиком: три назначенных
  колонки давали на экране две, и выглядело это потерянной настройкой, а не
  отсутствием сессий. Поймано на маке, где своих сессий обычно и нет вовсе.
  Заводит панель `buildSections`, а не `groupSessions`: та рассказывает, что
  приехало, и выдумывать группу, которой в данных нет, ей не по чину, — а
  «показывать ли пустое» это решение про показ. Оговорки три, и все три
  намеренные: только в режиме без префикса (под `/l` про пустоту прямо говорит
  подпись `No sessions on this machine.`), только на пустом запросе (секция без
  совпадений исчезает у всех одинаково) и не поверх `hidden` — «убери» сказано
  намеренно. Пустота названа подписью `block-subhead`, а не строкой списка: у
  той нет ни `data-index`, ни класса `row`, иначе выбор вставал бы на строку,
  которую нечем открыть. Заголовок при этом считается по тому же правилу, что
  и у непустой панели (`Active sessions` в одиночку, `Active local sessions`
  при чужих машинах): разойдись эти имена, панель называлась бы по-разному в
  зависимости от того, пуста она или нет.

  Внутри колонки с двумя блоками высота делится **не** по содержимому.
  `flex: 0 1 auto` здесь неверен: ужимает flex пропорционально размеру, и
  длинный сосед съедает короткого — измерено, снимкам под шестьюдесятью
  строками истории оставалось десять пикселей, то есть ничего. Отсюда
  `flex: 1 1 0` (доля поровну), а нижнему блоку колонки вдобавок разрешено
  быть по содержимому, но не выше половины
  (`:last-child:not(:only-child)` → `flex: 0 1 auto; max-height: 50%`):
  короткий показан целиком и без пустоты, а остаток достаётся верхнему — он в
  обеих колонках и есть длинный. `:not(:only-child)` обязателен: без него
  одинокий блок упирается в тот же потолок и занимает половину колонки впустую.

  **Вёрстку широкого режима мало померить в Chromium — надо и в WebKit.**
  Здесь стоял `max-height: max-content`, и в Chromium он считался верно, а в
  WebKit (это WKWebView, на котором пикер живёт на маке) блок с ним схлопывался
  в один заголовок: колонки чужих сессий, проектов, истории и снимков выглядели
  пустыми, при том что в узком списке всё было на месте. Поймано это было
  только человеком на живом макбуке. Оба движка есть чем проверить не выходя из
  разработки: Chromium — из кэша puppeteer по CDP, WebKit — `WebKit2` из
  `python3-gi` (`gi.require_version('WebKit2', '4.1')`) в `Gtk.OffscreenWindow`
  под `xvfb-run`. Стенд собирается из настоящего `<style>` страницы и настоящей
  разметки строк; проверять надо все раскладки — полную, короткую, одну колонку
  (`/p`) и две.

  Высоту блоку задаёт колонка, а не процент: `max-height: 100%` неразрешима
  там, где высота области сама зависит от содержимого, и движку положено
  читать такой процент как `none`. Блок вырос бы под все свои строки,
  `.block-rows` стало бы нечему переполняться, а переросший блок молча срезался
  бы внешним `overflow: hidden` — на экране длинный блок без единой полосы
  прокрутки, ровно то, ради ухода от чего блоки и заведены. Отсюда же снят
  `align-items: start`: он запрещал бы именно то растяжение, которым высота и
  держится.

  **Заголовок секции — обычная строка списка, и свёрнутость помнится по
  раскладкам.** Строкой (`kind: 'section'`, класс `.row.section`,
  `data-index`), а не подписью: свернуть секцию иначе нечем. Раньше здесь была
  отдельная строка-переключатель, показывавшаяся только у уже свёрнутой
  секции, — развернуть было чем, свернуть обратно нечем; теперь свёрнутая и
  развёрнутая формы это одна и та же строка, и вид `block-toggle` исчез вместе
  с развилкой. Enter на нём не открывает ничего, а правит `collapsed` и зовёт
  `saveUi`.

  **За заголовок же секцию и таскают, и перетаскивание это своё, на
  pointer-событиях.** HTML5 drag-and-drop в этом окне на Windows не работает:
  у вебвью Tauri `dragDropEnabled` по умолчанию `true`, и системный обработчик
  файлового перетаскивания съедает события страницы — в `tauri-utils` это
  записано прямо в doc-комментарии поля. Тащат именно за заголовок, потому что
  строки списка заняты кликом, открывающим сессию.

  Три вещи, за которые здесь заплачено, и все три ломаются молча:

  - **Такт придерживается на время перетаскивания.** Подача тикает раз в
    секунду, `planListSync` правит изменившиеся элементы — перетаскиваемый узел
    подменился бы под указателем прямо в движении, а в широкой раскладке вдобавок
    пересобрался бы `blocksShape`, то есть все контейнеры. `applyState`
    складывает ответ в `heldState` и выходит, `endDrag` применяет
    придержанное. Забудь второе — список замер бы навсегда.
  - **Клик приходит следом за `pointerup`**, и без `suppressClick` перенос
    заодно сворачивал бы перенесённую секцию. Порог в несколько пикселей
    (`DRAG_THRESHOLD`) обязателен по обратной причине: без него клик по
    заголовку становился бы переносом на ноль позиций, и свернуть секцию мышью
    стало бы нечем.
  - **Пустая колонка на время перетаскивания дорисовывается** (`addDropZones`,
    класс `drop-zone`). Обычно её нет вовсе — она забрала бы у соседей долю
    ширины ради пустоты, — но тогда секцию, ушедшую из колонки последней,
    вернуть было бы некуда: колонки нет в DOM, и указателю не во что попасть.
    Дорисовывается она **узлами**, а не перерисовкой списка: перерисовка
    заменила бы узел, на котором висит захват указателя, и перетаскивание
    оборвалось бы в момент начала. Селектор правила обязан начинаться с
    `#list` — базовое правило колонки прижато идентификатором и по весу
    выигрывает у двух классов.

  Перетаскивать можно только там, где секции — постоянный список: при пустом
  запросе и без префикса. Отдельной проверки на это не нужно, и её нет —
  признак тот же `foldable`, а при нём заголовок и так перестаёт быть строкой,
  то есть `.row.section` в DOM просто не находится. Порядок при этом
  записывается **по видимому списку**: место секции, которой сейчас нет на
  экране (лёг трекер — нет и его секции), в файле не сохраняется, и вернувшаяся
  машина встаёт в конец — по тому же правилу, по которому туда встаёт всё
  неназванное.

  Заголовок — обычная строка, и первой строкой списка он бывает всегда, а
  `active = 0` ставится и при каждом показе окна, и на каждую правку запроса.
  Поэтому сброс выбора уводит его на первую строку, которая **не** заголовок
  (`selectionReset` в `sessions.html`): иначе Enter сразу после открытия окна
  сворачивал бы верхнюю секцию вместо того, чтобы открыть верхнюю сессию.
  Наведённый стрелками или кликом выбор при этом не трогается — свернуть
  первую секцию с клавиатуры было бы нечем. И `^K` на заголовке не открывает
  меню вовсе: ни id, ни имени у него нет, меню вышло бы озаглавленным словом
  «undefined».

  **Непустой запрос разворачивает всё, и это сильнее памяти о свёрнутости.**
  Свёрнутая под запросом секция показывает вместо найденного одну строку с его
  счётом — а искали не счёт. Умолчание в узком списке сворачивает историю,
  проекты и снимки, то есть три секции из пяти, и поиск по слову, которое
  встречается везде, упирался бы в три закрытые двери подряд. Причина та же, по
  которой разворачивает префикс.

  Отсюда `foldable` (`buildSections`): свернуть можно только ту секцию, чья
  свёрнутость не назначена сверху, то есть при пустом запросе и без префикса. В
  остальных случаях заголовок — **подпись, а не строка**: ни `data-index`, ни
  класса `row`, и в `rows` он не попадает вовсе, как заголовок группы до всей
  этой затеи. Оставь его строкой — и Enter на нём молчал бы: записанное
  `collapsed: true` тут же затиралось бы обратно назначением сверху, а молчащий
  переключатель хуже отсутствующего. Побочно это и лучше на ощупь: под запросом
  стрелки ходят прямо по найденному, не спотыкаясь о заголовки.

  Умолчание живёт в коде (`defaultCollapsed`), отступление человека — в
  `ui.json`, и половинки у него свои на каждую раскладку
  (`collapsed: {narrow, wide}`). Умолчания у раскладок разные и по разным
  причинам: в узком списке история оттесняет вниз то, что работает сейчас, а
  проекты и снимки — справочники, за которыми приходят намеренно, поэтому все
  три приходят свёрнутыми; в широком у каждой своя колонка, и оттеснять там
  некого. Один список на обе значил бы, что свёрнутая в узком история
  опустошает колонку в широком. Отсутствие ключа в карте читается как «как по
  умолчанию», а не «развёрнута»: так умолчание можно менять, не переписывая
  людям `ui.json`.

  **Чужие машины названы подзаголовками внутри склеенного блока.** Склейка
  убрала заголовки групп, а вопрос «на какой машине» остался — ради него
  деление и заводили. Подзаголовок (`kind: 'block-subhead'`) лежит в тех же
  `rows`, что и сессии, но в `rows` страницы **не** попадает: это подпись, а не
  строка списка, у неё нет ни `data-index`, ни класса `row`, и ни стрелки, ни
  клик её не видят — ровно как заголовок группы в узком списке. Отсюда правило
  для `renderWide`: сколько строк было до блока, считается **до** сборки его
  элементов, а не вычитанием их числа. Арифметика «элементов ровно столько же,
  сколько строк» на подзаголовке врёт, и номера блоков разъехались бы со
  строками — стрелки сломались бы, а клик нет.

  Карточкой становится не любая строка внутри блока, а только та, что несёт
  класс `session` (`#list.blocks .row.session`): голый `.row` носят и строка
  проекта, и снимок, и заголовок секции, и зелийная псевдосессия
  (`.row.zellij`), а карточка — оформление под запрос с ответом, которых у
  них нет. Маркер положительный, а не цепочка `:not(...)`: новый вид строки,
  заведённый потом, по умолчанию останется строкой, а не подхватит карточку
  по ошибке.

  Состояние отрисовки при переключении сбрасывается в обе стороны: `planListSync`
  сравнивает новые строки со снимком прошлой раскладки и правил бы не те
  элементы. Своё состояние на блок (`renderedBlocks`), а не одно на список, —
  иначе изменение в одном блоке пересобирало бы все.

  Режим и запрос, которые показаны на самом деле, вычисляет одна функция на
  обе раскладки — `shownModeAndQuery()`, а не `render()` по месту: широкая
  ветка не может взять сырой `mode` как есть — `buildSections` на `snapshots`
  без трекера не отдаёт ни одной секции, и вместо отката в обычный поиск по
  сессиям человек получил бы пустой экран без единого слова о причине. Второй
  такой же откат, написанный отдельно в узкой и широкой ветке, разошёлся бы с
  первым на первой же правке — они уже разъезжались ровно здесь.

  `KeyF` обязан стоять в `RESERVED_CODES` (`action-hotkey.js`): без этого
  встроенная ветка съедала бы `Ctrl+F` у настроенного человеком действия, и оно
  молчало бы — ровно та ошибка, за которую уже заплачено списком `c v x z`.

  `←/→` в этом режиме уходят в навигацию по блокам, но только когда каретка на
  краю запроса и ничего не выделено: поле поиска сфокусировано всегда, и отнять
  у него стрелки насовсем значило бы лишить человека правки запроса.

  **Входов в широкий режим два — `^F` и кнопка `⛶` в статуслайне, — и работа у
  них одна `toggleFullscreen`.** Вторая копия `set_picker_size` + `saveUi`
  разъехалась бы с первой, а увидеть это можно было бы только глазами. Кнопку
  красит `paintToggles`, а не обработчик клика: режим переключается ещё и из
  окна настроек (событие `ui-changed`), и покрашенная по клику кнопка врала бы
  после чужой правки. Поэтому же `toggleFullscreen` зовёт `paintToggles` явно:
  `render` его не зовёт, а с дороги от настроек туда доходит `regroup`.

  Кнопки статуслайна держатся на классе `.icon-button`, а `margin-left: auto`
  стоит ровно у одной — первой в ряду. Здесь была цепочка из двух правил
  (отступ у `?` и его гашение у шестерёнки **соседним** селектором), и третья
  кнопка, вставшая между ними, разорвала бы её молча: шестерёнка отжалась бы
  вправо, а между ней и новой кнопкой встала бы дыра во всю ширину. Сторож —
  «вправо ряд прижимает ровно одна кнопка» в `test/keys-modal.test.js`.
  `:first-of-type` тут не годится: он считает по типу элемента, а первым
  `span` в статуслайне идёт переключатель сортировки.

  Размер окна меняет Rust (`set_picker_size`), а не страница: у окна нет
  декораций, и `window.resizeTo` на нём не работает. Узкий размер обязан
  совпадать с `tauri.conf.json` — сторожит тест
  `narrow_size_matches_the_window_config`. Широкий зажимается по экрану
  (`fit_to_screen`): 1400×900 на тринадцатидюймовом маке закрывают его целиком,
  а окно без декораций и drag-region мышью не подвинуть.

  **Оба размера можно заменить долей экрана, и доля зажим обходит.** Ключ
  `pickerSize` в `config.yaml` — по стороне на каждую раскладку, вкладка
  **Window** в окне настроек. Ноль (и отсутствие ключа) значит «встроенный
  размер», и ноль этот не «пусто»: удалять ключи `merge_patch` не умеет, он
  только вставляет, — то есть возврат с 80% на `Default` иначе нечем было бы
  записать. Считает всё `wanted_size` в `main.rs`, чистая и отдельная от
  команды по той же причине, что `fit_to_screen`: монитора в тестах нет.

  `SCREEN_FILL` доле не применяется намеренно. Зажим защищает **абсолютное**
  число от маленького экрана; доля в экран влезает по построению, и зажми мы
  её, выбранные человеком 95% молча стали бы 90% — пункт списка, обещающий не
  то, что делает. Экран неизвестен — доли не считаются вовсе: `NaN * 0.8`
  уронил бы окно в точку.

  Проценты, а не пиксели и не множитель встроенного размера: вопрос у человека
  «сколько сессий влезет», а не «во сколько раз больше», и ответ на него свой
  на каждом экране. Границ у доли две — `1..=100`, — и проверок тоже две
  (`scale_axis` в Rust ставит размер, `normalizePickerSize` показывает выбор);
  разойтись им нельзя, и сторож сверяет диапазон по тексту `main.rs`.

  **Смену размера в конфиге применяет `apply_config`, а ставит её ближайший
  показ.** Пикер в этот момент скрыт — он гасит себя перед открытием
  настроек, — а скрытому окну размер не ставится вовсе (см. ниже); помечать
  просьбу отложенной при этом больше не нужно: геометрию `show_picker` считает
  на каждом показе, по свежим долям из того же состояния. Перепросить
  со страницы по событию `config-changed` нельзя по той же причине, по какой
  опрос живёт в Rust: у скрытого окна WebView2 умеет усыплять её целиком, и
  просьба замолчала бы ровно в том случае, ради которого затевалась.

  **Скрытому окну размер не ставится вовсе, но геометрию считают именно для
  него — до `show()`.** Окно создаётся скрытым (`visible: false`), а страница
  просит размер при каждой своей загрузке, то есть по окну, которого ещё нет
  на экране. `set_size` по такому окну на macOS отрабатывает, и отрабатывает
  плохо: origin у NSWindow в левом нижнем углу, окно остаётся у прежнего угла
  и растёт вправо и вниз, а `center()` — это `NSWindow.center()`, и считает он
  от экрана, которого у выведенного из показа окна нет. На маке это и увидели:
  узкое окно в углу, широкое за правым краем. Отсюда `SizeRequest` в
  `main.rs`: `set_picker_size` ставит размер только по показанному окну, а по
  скрытому лишь запоминает названный режим.

  Ставит геометрию `show_picker` — **на каждом показе и до `show()`**, а не
  только по отложенной просьбе, как было сперва. Причин две, и обе новые.
  Монитор теперь называет приложение, а не окно (`target_monitor`, правило
  ниже), то есть слепота скрытого окна счёту больше не мешает; а окно на
  каждом показе обязано ещё и приехать на нужный экран — с галкой «Show on
  active display» тот меняется без всякой просьбы о размере. Прежний довод
  против («второй показ подряд — лишний перескок на глазах») умер вместе с
  причиной: до `show()` человек видит уже вставшее на место окно. Все пути
  показа идут через `show_picker` (оба хоткея, оба пункта трея и клик по
  иконке — через `toggle_window`), второй ветки показа заводить нельзя.
  Страница за этим следить не может — у скрытого окна webview усыпляют
  целиком, и «перепросить размер по событию `picker-shown`» замолчало бы ровно
  в том случае, ради которого затевалось.

  **На каком мониторе открывать пикер, решает `target_monitor`, и спрашивает
  он приложение, а не окно.** Ключ `showOnActiveDisplay` в `config.yaml`,
  галка на вкладке **Window**: выключена (умолчание) — `primary_monitor`,
  включена — экран под курсором (`cursor_position` → `monitor_from_point`).
  Умолчание именно такое, потому что постоянное место окна само по себе
  полезно: рука ведёт глаз туда, где список появится. Хоткей при этом жмут с
  клавиатуры, а спрашивается мышь — но второго признака «активного» экрана без
  платформенного кода нет: передним окном пришлось бы звать
  `GetForegroundWindow` на Windows и AX на macOS, две ветки под `cfg`, ни одна
  из которых не собирается на машине разработки.

  У приложения, а не у окна, — условие всей затеи: считают до `show()`, а у
  скрытого окна экрана нет (на macOS `current_monitor` это
  `ns_window.screen()`, у невыведенного окна `nil`), тогда как
  `primary_monitor` и `monitor_from_point` про окно не спрашивают ничего.
  Откат на `current_monitor` окна остался последним ходом: не назвался ни
  курсор, ни главный монитор — считаем по тому экрану, где окно уже стоит,
  ровно как пикер вёл себя до появления галки.

  Подложка едет следом сама и без второго правила: монитор она берёт у самого
  окна пикера (`scrim::monitor_rect`), а `apply_scrim` зовётся **после**
  `show()` — то есть по окну, которое уже стоит там, куда его поставили.
  Порядок в `show_picker` от этого обязателен: геометрия → `show()` →
  подложка.

  **Режим помнится в `ui.json` третьим полем верхнего уровня — рядом с `sort` и
  `toggles`, — и окно настроек обязано вернуть это поле нетронутым.**
  Полей теперь пять (см. правило про `ui.json` выше); `uiStateToSave`
  принимает режим третьим аргументом; `settings.html` звал её
  двумя, и первое же сохранение вкладки UI гасило запомненный `^F`. Обратный
  ход тот же: страница пикера читает `ui.json` при загрузке и по событию
  `ui-changed` и просит у Rust размер **безусловно, в обе стороны** — `if
  (fullscreen)` умел только расширять раму и на гонке (настройки перечитывают
  `ui.json` между `^F` и записью `saveUi`) оставлял узкую раскладку в широкой
  раме.

- **Источников состояния бывает два, и адрес действия называет строка.**
  `sshHost` — удалённый агрегатор, `localSource: true` — местный `ccfzf`,
  запускаемый процессом, без ssh (`ssh localhost` требовал бы sshd и своего
  ключа — на маке Remote Login выключен, на Windows сервера нет вовсе). Список
  источников считает `sources_from` в `state_source.rs`, опрашивает их
  `poll_once` в `poller.rs`, а ответы сливает `merge_states` — **в документ
  прежней формы**: страница живёт полями `lastState`, и два документа стоили бы
  не десяти правок, а ста.

  Дедуп в слиянии идёт по `id` (у проектов — `path`, у зелийных — `name`, у
  машин — `host`), первый источник побеждает, окна двойника складываются.
  Отдельной проверки «а не та ли это машина» нет намеренно: пикер на машине
  агрегатора получит от обоих источников один и тот же список целиком, и дедуп
  делает этот случай безвредным сам.

  Окна двойника склеиваются сравнением записи целиком, своего ключа у окна
  нет. Значит одно и то же физическое окно, приехавшее от двух источников с
  разошедшимся `lastSeen` или `focusedAt`, ляжет двумя записями — то есть
  двумя карточками. Сегодня это недостижимо: местный источник окон не отдаёт
  вовсе, привязка окна местного claude — отдельная задача в соседних
  репозиториях. Чинить это придётся вместе с ней, и чинить дедупом по `host`
  и `pid`, а не сравнением записи.

  Метка источника едет полем `source` у каждой строки и оттуда же берётся
  адресом действия — открытия, новой сессии, комментария. `CONFIG.sshHost`
  адресом больше не является: местная сессия открылась бы на удалённой машине,
  где её нет. Транспорт выбирает `commandParts` в `open-strategy.js`, и это
  единственное место, где команда встречается с дорогой, — по той же причине,
  по какой `terminalArgv` единственное место, где она встречается с терминалом.

  `sshHost`, буквально равный `local`, зарезервирован: обратный разбор
  (`Source::from_label`) принял бы его за местный источник.

  Отказ одного источника не гасит второй: список показывается по ответившим, а
  отказавшие называются в статуслайне поимённо. Молчаливое выпадение половины
  списка читалось бы как «сессий нет», а не как «спросить не удалось».

  Проверка ненастроенности теперь одна — пустой список источников. Прежних
  было две (`check_ssh_host` и `sshHostMissing()`), и второе правило про то же
  самое молчало бы, разойдясь с первым.

- **Местный источник на Windows читает реестр сессий, а не процессы.** Разбор
  процессов там не годится: рабочего каталога `Win32_Process` не отдаёт вовсе,
  а именно на cwd держится `fresh_ids` — единственная дорога для сессии,
  запущенной голым `claude`, без id в argv. Зато Claude Code сам ведёт
  `~/.claude/sessions/<pid>.json`: файл на процесс, и в нём уже есть и id, и
  каталог. Разбор белым списком, как у файла окон, — `registry_records` в
  агрегаторе.

  **Записи в реестре мёртвые — норма: за собой его никто не чистит.** Поэтому
  живость спрашивается отдельно и **двумя** половинами сразу: pid существует
  **и** время создания процесса совпало с `procStart` записи. Одной мало —
  pid'ы переиспользуются, и чужой процесс оживил бы вчерашнюю сессию. Время
  берётся через `ctypes` (`OpenProcess` + `GetProcessTimes`), а не
  подпроцессом: спрашиваются только те несколько pid, которые назвал реестр.
  `entrypoint` в реестре есть, но не читается — его источник транскрипт, и
  второго у одного факта быть не должно.

  **Обёртку пикер там не зовёт**: `bash` на Windows — это пускач WSL, он
  съедает обратные слэши пути (`local: exit code 127`), и даже с починенным
  путём читал бы `~/.claude` самой WSL, то есть список вышел бы не про ту
  машину. Поэтому `unpack` кладёт вторым файлом сам python-блок, вырезанный по
  меткам `PYEOF`, а `resolve` зовёт `python` с ним; ветка PATH там пропускается
  целиком — найденный в PATH `ccfzf` это тот же bash-скрипт. Пути себе режим
  считает сам (`state_defaults`, алиас `--state`): второй экземпляр тех же
  умолчаний в Rust разошёлся бы с этим молча, а расхождение выглядело бы пустым
  списком сессий.

  **Две мелочи здесь стоили живой выкатки, и обе молчаливые.** Программу в PATH
  на Windows ищут **с расширением**: файла `python` там нет вовсе, есть
  `python.exe`, и `on_path` по голому имени не находил ничего — `resolve`
  отказывал словами «neither python nor python3 is on PATH» на машине, где стоят
  обе. И ответ пишется **в UTF-8** независимо от системы (`reconfigure` у
  импортов агрегатора): при перенаправленном stdout кодировку python берёт от
  кодовой страницы (cp1251 на этой машине), и первая же стрелка в заголовке
  сессии роняет вывод посередине — читателю достаётся не отказ, а оборванный
  JSON. Обе видны только на Windows, обе выглядели бы прежней поломкой местного
  источника.

  **Состояния агента у этих строк нет, и это не поломка.** Хуков на той машине
  не стоит (`~/.claude/claude-wt/` не существует), поэтому точка состояния,
  сводка, деньги и доля контекста приезжать неоткуда — правая группа у строки
  пустая. Фоновых форков ветка не собирает по той же причине: признака
  `bg-pty-host`, по которому форк узнают на Linux, здесь нет, а форк, взятый за
  обычную сессию, отобрал бы у родителя его же окно.

  **Enter на местной строке идёт без шелла.** `/bin/sh` там нет вовсе, а
  `$SHELL -ic` написан ради интерактивного rc, которого там тоже нет: команда
  уходит голым хвостом argv, а каталог ставит запуск процесса (`spawn_detached`
  с `cwd`). Так не приходится ни собирать `cd`, ни кавычить путь, ни бояться
  `;`, который Windows Terminal делит на панели.

  **Каталог местной строки не переводится ни на одной системе** —
  `mapRowPath` в `path-map.js`. `mapPath` отдаёт `null` пути, не начинающемуся
  с удалённого префикса, и вместе с ним из меню молча пропадали бы все действия
  с папкой, `Open plan` и `Open spec`. Видно это стало на Windows, где местная
  строка несёт путь с буквой диска, но беда общая: на Linux с настроенным
  `pathMap` местная строка переводилась через удалённый префикс так же неверно.

## Иконки и хоткеи

- `src-tauri/icons/icon.ico` обязателен: без него `tauri-build` не собирает
  Windows-ресурс и падает до компиляции.
- **Руками в `src-tauri/icons/` правится только `favicon.png`.** Остальные семь
  файлов — вывод `python3 scripts/make-icons.py`, и правка любого из них
  переживёт ровно до следующего запуска скрипта.
- Умолчание хоткея — `Cmd+Shift+C` (на Windows `Win+Shift+C`). `Win+Shift+T`
  система держит за собой: `RegisterHotKey` отвечает «already registered».
- Отказ регистрации хоткея не фатален — пишет в stderr и не мешает запуску:
  окно поднимается из трея.
- `HOME` на Windows не выставлен; `load_config` и `seen.json` знают про
  запасной `USERPROFILE`.
