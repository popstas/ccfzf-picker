# ccfzf-picker

Пикер сессий Claude Code на удалённой машине. Список берётся из `ccfzf --state`
по ssh, окно и хоткеи — Tauri 2. Начинать с [README.md](README.md).

## Сборка и тесты

```
npm test                      # фронтенд, node --test, без зависимостей
cd src-tauri && cargo test    # оболочка
```

`vendor/ccfzf` — сабмодуль: `local_ccfzf.rs` вшивает его `include_str!`-ом
в бинарь, и без `git clone --recurse-submodules` (или `git submodule update
--init` в уже склонированном каталоге) сборка не доходит до этой строчки —
падает весь крейт, а не только местный источник.

`node --test test/` на этих версиях Node не работает — только `npm test`.

## Выкатка

Собирает и перезапускает пикер на целевой машине `data/scripts/deploy-win.sh`
(Windows; соседний `deploy-mac.sh` — то же для маков). Каталог `data/` под
`.gitignore`: скрипты знают имена хостов и пути конкретной установки, а не
проекта, — и потому же остальное про них написано в них самих.

```
./data/scripts/deploy-win.sh              # обновить, собрать, перезапустить
./data/scripts/deploy-win.sh --no-build   # только перезапустить собранное
./data/scripts/deploy-win.sh --no-launch  # собрать, но не запускать
```

**Закончив задачу — выкатывать на все три машины, не дожидаясь просьбы.** Пикер
живёт значком в трее на каждой из них, и невыкаченная правка там просто не
видна; половина задач проекта и доказывается только живой проверкой — терминалы
на маке, перетаскивание секций, глифы в системных шрифтах, штамп сборки. Скрипта
два, машин три, и пускать их надо **параллельно и в фоне**: Windows собирается
около трёх с половиной минут, маки — около одной.

```
BRANCH=<ветка> ./data/scripts/deploy-win.sh
BRANCH=<ветка> ./data/scripts/deploy-mac.sh --all
```

Ветку называть явно: умолчание у скриптов `master`, и с ветки под ревью уехал бы
чужой код. Выкатывать **после пуша** — скрипт первым делом делает `git pull` на
целевой машине (правило ниже), то есть незапушенное не уедет вовсе. После
выкатки сказать, чего на машинах ещё нет: коммит, легший после запуска скрипта,
на экране не окажется.

Первым шагом скрипт делает `git pull` на целевой машине: выкатывается
запушенное, а не то, что лежит в рабочем каталоге. Собирает он `cargo build
--release`, а не `cargo tauri build` из README: `bundle.targets` в
`tauri.conf.json` — `["app"]`, это формат macOS, на Windows результат работы
сам `.exe`. Мимо tauri-cli не отрабатывает `beforeBuildCommand`, поэтому
`scripts/prepare-frontend.js` там зовётся отдельным шагом — без него в бинарь
вшилась бы прошлая статика.

Разложенную им статику cargo замечает сам: пути `frontend/` попадают в
dep-info крейта (`target/*/ccfzf-picker.d`, все 29 файлов), и правка страницы
крейт пересобирает. А вот сборочный скрипт про неё не знал: входы у него
объявлены явно, и каталог фронтенда лежит вне пакета. Отсюда штамп сборки в
трее показывал прошлую выкатку — сам `build.rs` не перезапускался. Чинит это
одна строка `cargo:rerun-if-changed=../frontend` в `src-tauri/build.rs`,
сторож — `build_script_watches_the_frontend`; поймать это поведением нельзя,
cargo решает про `build.rs` до того, как хоть что-то наше начнёт выполняться.

**Профиль `release` собран под выкатку, а не под витрину.** Стояли `lto = true`
и `codegen-units = 1`, и пересборка после правки одной строки занимала 208 с —
из них почти всё fat-LTO по дереву из 323 зависимостей в один поток. Правка
файла фронтенда стоила ровно столько же (214 с): статика вшивается на
компиляции, то есть обе дороги ведут в полную перекомпиляцию крейта. Замеры
(i5-12600K, 16 потоков) и цена в размере бинаря — таблицей в
`src-tauri/Cargo.toml` рядом с самим профилем; работу делает `incremental`,
итог — **37 с**. Оптимизации всей программы пикер не окупает: он спит и раз в
секунду правит различающиеся строки в DOM.

Три рычага проверены и отвергнуты, и каждый стоил бы настройки:

- **линкер `rust-lld` вместо `link.exe`** — 37,6 с против 37,2 с. Линковка
  узким местом не была; ради этого нуля пришлось бы завести
  `.cargo/config.toml` с путём внутрь каталога тулчейна, то есть привязать
  сборку к версии rustup;
- **`strip = "debuginfo"`** — 38,7 с. PDB на 7,6 МБ пишется при каждой
  линковке, но времени не стоит;
- **общий `target` на несколько соседних проектов** — ноль. Затея выглядела
  верной: у пикера с windows11-manager 224 крейта совпадают по имени, профили
  после этих правок одинаковы, и напрашивался вывод, что второй проект
  доберёт готовое. Замерено прямо: windows11-manager собран в пустой общий
  каталог (222,4 с, 518 юнитов), следом туда же пикер — **491 юнит**; он же в
  свой одноразовый каталог — **те же 491**. Переиспользован ноль юнитов,
  время совпало в пределах шума (321,9 с против 329,2 с), место сложилось
  ровно (1,8 + 1,4 = 3,2 ГБ). Совпадение имени и версии крейта ничего не
  значит: юнит опознаётся хэшем, а в него входит унификация фич, своя у
  каждого дерева зависимостей. Платой была бы сериализация — cargo берёт на
  каталог эксклюзивный лок, и две сборки перестали бы идти параллельно.

**`LNK1104` на `deps\ccfzf_picker.exe` — след стенда, а не беда деплоя.**
`release\ccfzf-picker.exe` и `release\deps\ccfzf_picker.exe` — жёсткие ссылки
на один образ (`fsutil hardlink list` показывает оба имени), и на этом легко
решить, что `deploy-win.sh` освобождает только одно имя и потому обязан падать.
Проверено воспроизведением всей последовательности деплоя на работающем
пикере: не падает. Удаление **не последнего** имени NTFS разрешает и для
отображённого образа — имён остаётся два (`*.old.exe` и `deps\`), cargo сносит
второе и кладёт своё. Отказ бывает ровно тогда, когда имя у образа осталось
одно; у деплоя такого не бывает, а у самодельного стенда — бывает.

## Релиз

**Выкатка и релиз — две разные дороги, и общего у них ничего.** `deploy-*.sh`
кладут `cargo build --release` на три рабочие машины и никаких артефактов не
делают; релиз собирает `.github/workflows/release.yml` по тегу `v*` — четыре
работы: установщик NSIS под Windows, `.app` под macOS в zip, релиз с заметками
git-cliff и обновление homebrew-каски.

Ставить тег после пуша: workflow висит на теге, а не на ветке. Версия правится
руками в трёх файлах (`package.json`, `src-tauri/tauri.conf.json`,
`src-tauri/Cargo.toml`), и согласие держат двое — `test/version-sync.test.js` на
каждом прогоне и `scripts/check-version.js` первым шагом обеих сборок в CI, до
компиляции. Цена ошибки известна по соседнему windows11-manager: там образец
тега разошёлся с тем, что ставилось, и три релиза вышли без единого `.exe` —
молча, потому что не сработавший workflow в релизе ничем себя не проявляет.

**Сабмодуль назван ssh-адресом, и в CI это чинится не правкой `.gitmodules`.**
`vendor/ccfzf` вшивается `include_str!`-ом, без него не компилируется весь
крейт, а ssh-ключа у бегунка нет. Перед чекаутом стоит
`git config --global url."https://github.com/".insteadOf "git@github.com:"` —
адрес в файле остаётся прежним, потому что пуш в сабмодуль идёт по ssh.

**Рычаги размера живут в workflow, а не в `[profile.release]`.** Профиль собран
под скорость выкатки (таблица замеров — в самом `Cargo.toml`), а у релиза
вопрос обратный: ждёт машина GitHub, а весит скачиваемое. Своего `--profile` у
`tauri build` нет — проверено по справочнику CLI v2, — поэтому релизная сборка
перекрывает профиль переменными `CARGO_PROFILE_RELEASE_*` (fat-LTO, один
codegen-unit, без incremental, `strip`, `opt-level = "z"`). Верни их в
`Cargo.toml` — и каждая выкатка подорожает втрое, молча: скрипт деплоя времени
не считает. Сторожит это тот же `test/version-sync.test.js`.

Замерено на popstas-pc (i5-12600K, 16 потоков) на версии 0.9.0, тем же
`tauri build`, каким собирает workflow:

```
профилем выкатки (incremental, без LTO)          .exe  14,7 МБ
релизным профилем (fat-LTO, cgu=1, strip, z)     .exe   8,7 МБ
установщик NSIS                                        2,7 МБ
```

Времена сравнивать в лоб нельзя: 37 с из таблицы в `Cargo.toml` — это
пересборка после правки одной строки, а релизная сборка идёт с нуля и заняла
3 мин 44 с. Платит за неё машина GitHub, а не человек, — ради чего рычаги и
разведены по двум местам.

Установщик — NSIS и `installMode: currentUser`: пикер это значок в трее одного
человека, UAC ему не нужен. WebView2 остаётся в режиме `downloadBootstrapper`
(умолчание); соседний `offlineInstaller` добавил бы к установщику около 130 МБ.

**Маковская сборка — arm64 и без подписи, и плата за это видна человеку.**
Developer ID нет, universal удвоил бы вес ровно в той задаче, где вес и
оптимизируется. Gatekeeper на неподписанном приложении говорит «повреждено», а
не «не подписано», — то есть выглядит это поломкой сборки. Поэтому
`--no-quarantine` назван трижды: в README, в описании релиза и в `caveats`
каски.

Каска живёт в общем публичном тапе `popstas/homebrew-apps` рядом с касками
остальных маковских приложений,
версию и `sha256` в ней правит `sed` из работы `update-homebrew`. Токен для
этого — секрет `HOMEBREW_TAP_TOKEN` (PAT с правом записи в tap):
`GITHUB_TOKEN` в чужой репозиторий не пускают, и без секрета работа падает на
чекауте — красно и вслух, релиз при этом уже собран.

## Тема

- **Цвет в стилях называется токеном, а не литералом.** Палитра обеих страниц
  живёт одним файлом — `frontend-src/theme.css`, — и подключается `<link>`-ом
  и в `sessions.html`, и в `settings.html`. До неё шкалы были разные: пикерная
  (#1e1f22, #25262a, #31343a) и маковская у настроек (#1c1c1e, #232326,
  #3a3a3e), — два набора об одном и том же, которым разойтись мешало только
  то, что их никто не трогал. Сведены в один.

  Тёмная стоит на голом `:root` и остаётся умолчанием даже там, где JS не
  отработал вовсе. Светлая написана дважды — под `prefers-color-scheme` и под
  `:root[data-theme="light"]`, — и половинам этим расходиться нельзя: одна и та
  же светлая тема выглядела бы по-разному в зависимости от того, выбрана она
  человеком или взята у системы. Сторожа — в `test/theme.test.js`: обе половины
  сверяются целиком, у каждого тёмного токена спрашивается светлая пара, а в
  `<style>` обеих страниц запрещены сырые цвета. Последнее не придирка: цвет,
  дописанный литералом, в тёмной теме верен, а на светлой пропадает с глаз —
  и увидеть это можно только на той машине, где пикер стоит.

- **`system` — это снятый атрибут, а не третье его значение.** Настройка
  `theme` в `config.yaml` знает три слова, а `data-theme` на `<html>` — два:
  `dark` и `light`. При `system` атрибута нет вовсе, и светлую половину
  включает медиазапрос — то есть первая же отрисовка страницы верна, до
  всякого JS. Поставь страница `data-theme="system"` — и ни одно правило
  палитры не совпало бы, окно осталось бы тёмным на светлой системе.

  Умолчание — `system`, и знают его трое: `config-shape.js` (Enter и список
  жмут при показанном окне), поле формы в `settings-form.js` и `config_choice`
  в `main.rs`. Третий тут не от жадности — см. правило ниже.

- **Окно настроек получает тему до загрузки, и ставит её Rust.** Оно
  создаётся сразу видимым, поэтому при `theme: light` человек увидел бы тёмную
  вспышку: конфиг страница спрашивает уже после загрузки. Отсюда
  `theme_script` в `main.rs` — `initialization_script` с одной строкой
  `window.__THEME__`, — а головной скрипт обеих страниц ставит по ней атрибут
  синхронно. Значение уезжает в исходный текст страницы, поэтому просеивается
  белым списком (`config_choice` по таблице `THEMES`), а не подставляется как
  есть; `system` скрипта не получает вовсе. Пикеру это не нужно (его окно
  создано скрытым и грузится задолго до показа), но список слов у них общий, и
  сверяет все три `test/theme.test.js` вместе с подписями.

- **Знак GitHub красится по теме, потому что каскад внутрь `<img>` не
  попадает.** Заливка вшита в `data:`-URI (`GITHUB_FILL` в
  `frontend-src/action-icons.js`), `currentColor` там не работает, и одна
  заливка на обе темы означала бы исчезнувший знак на светлой. Разрешает
  `system` в одно из двух слов страница (`resolvedTheme` в `sessions.html`) —
  палитре это не нужно, у неё медиазапрос, — а пересобирает картинку
  `loadActionIcons`, та же дорога, какой значки перечитываются на
  `config-changed`.

## Язык

**Всё, что видит человек, — по-английски; всё, что видит разработчик, — по-русски.**
Подписи, кнопки, подсказки, сообщения об ошибках, пункты меню трея, заголовки
окон и шапка, которую окно настроек пишет человеку в `config.yaml`, — английские.
Комментарии, doc-комментарии, названия тестов и сообщения в `assert` —
русские: они объясняют «почему», и объяснение это писано на языке, на котором
о нём договаривались. Тест, сверяющийся с видимой строкой, правится вместе с
ней — иначе перевод ломает сторожа, а не проверяемое им правило.

## Правила, за которые уже заплачено

Правил накопилось семь десятков, и каждое записано ценой отладки: почти все
ломаются молча — команда уходит, брокер подтверждает, окно открывается, а
сделано не то. Четыре из них всегда при себе: они решают, соберётся ли команда
вообще, и забытые портят не ту задачу, над которой работаешь. Остальные
разложены по подсистемам в `docs/rules/` — **открывай названный файл, взявшись
за его тему**, до правки, а не после.

- **`;` в удалённой команде не ставить** — для Windows Terminal это разделитель
  панелей, и команда развалится на панели вместо выполнения. Стратегия
  `takeover` в `frontend-src/open-strategy.js` склеивает команду через `; `; она
  выключена (`caps.takeover: false`), но при включении это первое, что сломается.

- **`ssh host cmd` — неинтерактивный шелл.** zsh читает только `.zshenv`,
  `.zshrc` не читает. Форма `inDir` в `frontend-src/open-strategy.js`:
  `exec $SHELL -ic 'cd -- <cwd> && <cmd>'`. Через неё обязаны идти **все**
  удалённые запуски агента — и `resume`, и хвост `takeover`, и проектные хоткеи
  в `sessions.html`. Без неё не отрабатывает хук `chpwd`, который ставит
  `project=` в `OTEL_RESOURCE_ATTRIBUTES`, и агент пишет телеметрию без имени
  проекта.

- **`cd` стоит внутри интерактивного шелла**, после чтения rc: иначе rc, сам
  куда-то переходящий, увёл бы каталог обратно. Кавычки при этом навешиваются
  дважды (`q` внутри `q`) — разбирать будут два шелла подряд.

- **Имена машин в репозиторий не возвращать.** Хост берётся из
  `~/.config/ccfzf-picker/config.yaml`, умолчания у него нет.
  `test/no-private-data.test.js` это проверяет; список конкретных слов — в
  `data/private-patterns.txt`, каталог под `.gitignore`.

  Правило не безоговорочное: санкционированное исключение есть, и живёт оно в
  `BINARY_OK` того же теста — `assets/fullscreen.png`, снимок окна для
  README. Комментарий рядом называет цену: имена машин, домашний путь, полный
  список проектов и содержимое сессий текстом — всё это на снимке видно, и
  проверке нечем ни прочитать картинку, ни отредактировать её. Решение
  опубликовать снимок принято владельцем сознательно; второму такому файлу
  появляться в репозитории не следует, не замазав на нём те же классы данных.

Указатель — не пересказ: правило живёт в своём файле целиком, и решать по
строке таблицы нельзя. Заводя новое правило, клади его в тот же файл, что и
соседей по подсистеме, и правь здесь счёт.

## Иконки и хоткеи

- `src-tauri/icons/icon.ico` обязателен: без него `tauri-build` не собирает
  Windows-ресурс и падает до компиляции.
- **Руками в `src-tauri/icons/` правится только `favicon.png`.** Остальные семь
  файлов — вывод `python3 scripts/make-icons.py`, и правка любого из них
  переживёт ровно до следующего запуска скрипта.
- Умолчание хоткея — `Cmd+Shift+C` (на Windows `Win+Shift+C`). `Win+Shift+T`
  система держит за собой: `RegisterHotKey` отвечает «already registered».
- Отказ регистрации хоткея не фатален — пишет в stderr и не мешает запуску:
  окно поднимается из трея.
- `HOME` на Windows не выставлен; `load_config` и `seen.json` знают про
  запасной `USERPROFILE`.
