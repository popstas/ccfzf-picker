# ccfzf-picker

Пикер сессий Claude Code на удалённой машине. Список берётся из `ccfzf --state`
по ssh, окно и хоткеи — Tauri 2. Начинать с [README.md](README.md).

## Сборка и тесты

```
npm test                      # фронтенд, node --test, без зависимостей
cd src-tauri && cargo test    # оболочка
```

`node --test test/` на этих версиях Node не работает — только `npm test`.

## Выкатка

Собирает и перезапускает пикер на целевой машине `data/scripts/deploy-win.sh`
(Windows; соседний `deploy-mac.sh` — то же для маков). Каталог `data/` под
`.gitignore`: скрипты знают имена хостов и пути конкретной установки, а не
проекта, — и потому же остальное про них написано в них самих.

```
./data/scripts/deploy-win.sh              # обновить, собрать, перезапустить
./data/scripts/deploy-win.sh --no-build   # только перезапустить собранное
./data/scripts/deploy-win.sh --no-launch  # собрать, но не запускать
```

Первым шагом скрипт делает `git pull` на целевой машине: выкатывается
запушенное, а не то, что лежит в рабочем каталоге. Собирает он `cargo build
--release`, а не `cargo tauri build` из README: `bundle.targets` в
`tauri.conf.json` — `["app"]`, это формат macOS, на Windows результат работы
сам `.exe`. Мимо tauri-cli не отрабатывает `beforeBuildCommand`, поэтому
`scripts/prepare-frontend.js` там зовётся отдельным шагом — без него в бинарь
вшилась бы прошлая статика.

## Язык

**Всё, что видит человек, — по-английски; всё, что видит разработчик, — по-русски.**
Подписи, кнопки, подсказки, сообщения об ошибках, пункты меню трея, заголовки
окон и шапка, которую окно настроек пишет человеку в `config.yaml`, — английские.
Комментарии, doc-комментарии, названия тестов и сообщения в `assert` —
русские: они объясняют «почему», и объяснение это писано на языке, на котором
о нём договаривались. Тест, сверяющийся с видимой строкой, правится вместе с
ней — иначе перевод ломает сторожа, а не проверяемое им правило.

## Правила, за которые уже заплачено

- **`;` в удалённой команде не ставить** — для Windows Terminal это разделитель
  панелей, и команда развалится на панели вместо выполнения. Стратегия
  `takeover` в `frontend-src/open-strategy.js` склеивает команду через `; `; она
  выключена (`caps.takeover: false`), но при включении это первое, что сломается.

- **`ssh host cmd` — неинтерактивный шелл.** zsh читает только `.zshenv`,
  `.zshrc` не читает. Форма `inDir` в `frontend-src/open-strategy.js`:
  `exec $SHELL -ic 'cd -- <cwd> && <cmd>'`. Через неё обязаны идти **все**
  удалённые запуски агента — и `resume`, и хвост `takeover`, и проектные хоткеи
  в `sessions.html`. Без неё не отрабатывает хук `chpwd`, который ставит
  `project=` в `OTEL_RESOURCE_ATTRIBUTES`, и агент пишет телеметрию без имени
  проекта.

- **`cd` стоит внутри интерактивного шелла**, после чтения rc: иначе rc, сам
  куда-то переходящий, увёл бы каталог обратно. Кавычки при этом навешиваются
  дважды (`q` внутри `q`) — разбирать будут два шелла подряд.

- **Список не перерисовывается целиком.** Подача тикает раз в секунду; запись в
  DOM идёт через `syncList()` и `frontend-src/picker-list-sync.js`, которые
  правят только отличающиеся строки. `list.innerHTML = html` на каждый тик
  ронял скролл и гасил hover.

- **Про окна пикер не спрашивает никого — они приезжают в ответе агрегатора.**
  `ccfzf --state` читает у себя файл, который кладёт рядом оконный трекер с той
  машины, где сессии видны на экране, и добавляет каждой сессии поле `window`, а
  ответу — `windowHost` и `windowPid`. Своего http-клиента у пикера нет и не
  должно появиться: сервер на той стороне вешал демона через две-три минуты
  после старта (разбор — в репозитории windows11-manager). Устаревший файл агрегатор
  отбрасывает сам, старше двух минут.

- **Передний план на Windows выдаётся, а не берётся.** `SetForegroundWindow`
  система разрешает только тому, кто передним планом уже владеет либо получил
  последнее событие ввода. Никто из исполнителей наших просьб не таков: они
  слушают брокера. Право передаёт сам пикер, `allow_any_foreground` в
  `src-tauri/src/main.rs`, и **до** публикации, пока нажатие ещё наше.

  Право уходит всем (`ASFW_ANY`), а не названному pid, и это исправление.
  Названный pid был один — `windowPid` из ответа агрегатора, — но кладёт его в
  файл трекера демон `claude-wt watch`, а окна поднимает и терминал запускает
  служба MQTT: с переезда claude-wt из windows-mqtt в windows11-manager это два
  разных дочерних процесса трея, и грамота уходила не тому. Третьего исполнителя
  — только что запущенный `wt.exe` — по pid не назвать вовсе: в момент выдачи
  его ещё нет, а именно его отказ выглядел свернувшимся окном нового терминала.

  Гашение пикера — тоже ход за передний план, поэтому оно идёт **до** просьбы во
  всех четырёх ветках, кончающихся окном (`focusSession`, `openProjectRow`,
  `newSessionHere`, `openViaManager`); сторож — `test/hide-before-request.test.js`.
  Цена известна и уплачена: отказ публикации человек увидит не сразу, а когда
  откроет пикер снова.

  Чего грамота не решает: уже открытое окно менеджер поднимает и без неё —
  `bringToTop()` в node-window-manager подцепляет свой ввод к потоку переднего
  окна (`AttachThreadInput`), а такой подъём Windows не запрещает. Поэтому окно
  новой сессии на той стороне поднимают явно (`focusSpawnedWindow` в
  `windows11-manager/src/claude-wt/project.js`), выждав расстановку: грамота
  живёт до следующего ввода человека, а окно приезжает секундами позже.

- **Поднимать ли окно, решает совпадение имён машин — по каждой строке
  отдельно.** Трекеров теперь может быть несколько, и «чья это машина»
  перестало быть свойством всего ответа: `windowOf()` в
  `frontend-src/session-windows.js` берёт `host` из записи окна именно этой
  строки, а на старом агрегаторе (там окно одно на весь ответ) подставляет
  верхние поля `windowHost`/`windowPid`. `canFocusRow()` сравнивает этот
  `host` с `windowHost` конфига — тем же именем, что человек пишет в
  `config.yaml`. На маке агрегатор рассказывает и про окна Windows-машины:
  пометка ▣ там полезна, а ветка `focus` не включается — подъём окна на чужом
  экране ничего не дал бы человеку, а Enter лишился бы привычного открытия
  терминала. Пустое поле в конфиге значит «фокуса не бывает», и это
  умолчание.

- **Отметок «просмотрено» две, и складываются они по максимуму.** Своя —
  `seen.json`, её ставит открытие сессии из списка; на маке она единственная.
  Чужая приезжает полем `focusedAt` внутри `window` — оконный трекер видит
  переход взгляда на окно, а пикер про это не знает ниоткуда. Отсюда и обратный
  ход: «Mark unread» отматывает обе, местную в `seen.json` и трекерную
  публикацией в `<base>/windows/claude-session-unread`. Только местная у сессии
  с открытым окном не значит ничего — следующий опрос вернёт «просмотрено».
  Шлётся она независимо от `canFocus`: тот про подъём окна, а отметка приезжает
  в список на любой машине.

- **Настроенный `mqtt` — условие выполнимости фокуса, а не второе решение.**
  Просьба о подъёме уходит единственным способом, публикацией в MQTT. Топик
  при этом не свой: адрес называет трекер строки (поле `mqttBase`), а
  `<config.base>/windows/claude-focus` — только запасной ход, на который
  `resolve_base` в `src-tauri/src/mqtt.rs` откатывается, когда трекер адреса
  не назвал (подробности — в правиле про адрес просьбы ниже). Без брокера
  ветку `focus` предлагать нельзя: Enter молча не сработал бы, а это хуже,
  чем открыть терминал.

- **Развилку Enter решает `chooseEnterAction`, а не условия по месту.**
  `frontend-src/open-transport.js`, три проверки в одном порядке: уже открытое
  окно поднимает `focusSession` — подъём, а не открытие (гасят пикер до
  публикации и выдают право на передний план теперь все ветки одинаково);
  просьба к windows11-manager уходит лишь у
  строк с настоящим id сессии (`SESSION_ID_ROW_KINDS`) и только у тех, по
  которым менеджер сможет сработать — либо трекер знает сессию (поле `window`,
  то есть её id найдётся среди слотов), либо известен каталог проекта (поле
  `cwd`, и по нему открывается терминал с профилем из `claudeWt.projects`);
  всё остальное открывается локально, как до появления ветки менеджера.
  Каталог едет в теле просьбы (`open_session_mqtt` → ключ `cwd`) — без него
  менеджер на незнакомый id отвечает `unknown session` в свой лог, а пикеру
  про это не узнать ниоткуда: ответа у публикации нет.

- **Снимки раскладки приезжают в ответе агрегатора, а не по запросу.** Список
  снимков в windows-mqtt отвечал через `mqtt.sendEvent()` — это запись в stdout
  своему Tauri-процессу, и стороннему читателю там взяться неоткуда. Дорога
  та же, что у окон: демон кладёт снимки в файл трекера, `ccfzf --state` их
  отдаёт. Заводить ради списка подписку в пикере значило бы держать
  соединение и ждать — ровно того, чего эта схема избегает.

  Трекеров, умеющих снимать раскладку, теперь два (windows11-manager и
  macos-windows-manager), и владельца снимку приписывает агрегатор, а не сам
  трекер: в своём файле трекер и так публикует только свои снимки, а вопрос
  «чей это снимок» встаёт лишь на слиянии, когда агрегатор складывает файлы
  разных машин в один список. Та же развилка уже решена для окон
  (`windowOf()`, правило про совпадение имён машин выше) — снимку она досталась
  тем же способом: `host` и `mqttBase` источника каждой записи проставляет
  `read_window_sources` в агрегаторе `ccfzf`, а пикер их только читает —
  `snapshotBase()` в `frontend-src/picker-snapshots.js` достаёт `mqttBase` из
  уже готовой записи.
  `^S` отбирает из ответа только снимки своей машины (`snapshotsHere`) — снимок
  соседней восстановить на своём экране всё равно нечего.

  Восстановление ветвится не по `host` снимка, а по способности его
  машины `openSession` (`openManager` в `frontend-src/session-windows.js`,
  развилку решает `snapshotOwner` в `sessions.html`). Мак эту способность не
  объявляет: менеджера, который умел бы открыть терминал по MQTT-просьбе, там
  нет, и снимок с `host: mac-host` восстанавливается не просьбой, а тем же
  путём, каким пикер открывает сессию из списка сам — по одной, `resume` по
  id (место запомнено за идентификатором сессии, а не за именем окна), с
  паузой между поднятиями: два терминала, вставшие разом, ни один трекер не
  различит — заголовок у обоих ещё не устоялся, а привязка идёт по нему.
  Расставляет поднятые окна по местам сам трекер той машины, обычным
  механизмом расстановки — про восстановление как таковое он не знает и
  знать не обязан. Прямое сравнение `host` снимка с `windowHost` конфига эту
  развилку не заменит: так не отличить мак без менеджера от Windows-машины с
  ним, и Enter уехал бы в топик, который никто не слушает, молча, потому что у
  публикации нет ответа.

  На машине с менеджером просьба по-прежнему уходит ему — публикацией
  `claude-snapshot-restore`, но адрес называет уже не `managerBase()`, а сам
  снимок: у `mqttBase` в его записи то же происхождение, что у одноимённого
  поля записи окна, и то же правило — своя база у каждой машины.
  `managerBase()` жива и не тронута: ею по-прежнему пользуются три другие
  просьбы к менеджеру (открыть проект, завести сессию, открыть через пункт
  меню), у которых снимка нет и адрес неоткуда взять, кроме как у текущей
  машины-менеджера. `<config.base>/windows/claude-snapshot-restore` — запасной
  ход на случай пустого `mqttBase` у снимка (старый агрегатор его не
  проставляет), а не основной адрес.

- **Тело просьбы о восстановлении разбирается на той стороне двумя видами.**
  С панели openHASP прилетает сырая строка или пустота, от пикера — объект
  `{id, sessionIds}`. `parseRestorePayload` в windows-mqtt знает оба; без
  разбора JSON id снимка уезжал в `restoreSnapshot` литералом `{"id":"…"}`, и
  ошибки на такой вход нет — есть пустой результат.

- **Действия открытия папки запускаются без шелла — и это разница, а не
  мелочь.** `spawn_detached` зовёт `Command::new(file).args(args)`, элементы
  `argv` уходят аргументами процесса: кавычить и экранировать нечего, `q` из
  `open-strategy.js` тут не нужна и только испортила бы путь. Правило `q`
  действует ровно там, где команда идёт через `ssh` в чужой шелл.

- **`{localPathSlash}` не для красоты.** `cmd /c start` съедает обратные слэши
  и папку не открывает — проверено ещё в windows-mqtt
  (`src/picker/session-open-helpers.js`). Прямой
  запуск `explorer.exe` там же не сработал вовсе. Единственная форма, которая
  открывает папку, — `cmd /c start "" <путь прямыми слэшами>`.

- **Имена машин в репозиторий не возвращать.** Хост берётся из
  `~/.config/ccfzf-picker/config.yaml`, умолчания у него нет.
  `test/no-private-data.test.js` это проверяет; список конкретных слов — в
  `data/private-patterns.txt`, каталог под `.gitignore`.

- **Опрос живёт в Rust, а не на странице.** У скрытого окна webview тормозит
  таймеры, а WebView2 у свёрнутого умеет усыплять страницу целиком: фон на
  `setInterval` замолчал бы, и узнать об этом было бы неоткуда. Такт считает
  `next_delay` в `src-tauri/src/poller.rs` — секунда на показанном окне,
  1→2→4→8 минут на скрытом. Фон нужен не только ради тёплого списка:
  `ccfzf --state` переписывает свой дамп, а с того дампа живут экспорт в Home
  Assistant и панель openHASP — закрытый пикер, переставший спрашивать,
  останавливает и панель.

- **Отпечаток состояния считается без времени.** `generated` наверху ответа и
  `age` у каждой сессии считаются от «сейчас» и отличаются на каждом опросе:
  сравнивая ответ целиком, бэкофф не включился бы никогда, а выглядело бы это
  как работающая функция. `fingerprint` в `poller.rs` их выбрасывает.

- **Галка в списке имеет две оси, и старую форму `ui.json` надо понимать.**
  `list` — показывать ли колонку (это и значила плоская галка), `statusline` —
  выносить ли галку в строку внизу. `normalizeUiState` поднимает булево
  значение в `list`: не поняв старый файл, первый же запуск после обновления
  сбросил бы человеку все колонки, и выглядело бы это потерей настроек.

- **`config.yaml` после первого сохранения из окна настроек ведёт окно.**
  Перезапись через `serde_yaml` теряет комментарии — а они и есть
  документация. Смягчение одно и разовое: `config.yaml.bak` перед первой
  перезаписью и шапка-предупреждение в новом файле. Патч сливается по ключам
  (`config_file::merge_patch`), иначе окно стирало бы `actions`, про которые не
  знает, и `mqtt.password`, который не показывает.

- **Окно создаётся только из `async`-команды.** Синхронную команду Tauri
  выполняет в потоке цикла событий, а webview на Windows дозревает через этот
  же цикл: `open_settings` без `async` возвращал Ok, окно появлялось, и
  страница в нём не загружалась никогда — белый прямоугольник с рамкой.
  Отладить это тяжелее, чем звучит: то же окно, открытое из `setup` (тоже
  главный поток, но до входа в цикл), рисуется правильно, и разница видна
  только в настоящем пути «пикер → шестерёнка». То же правило и у второго входа
  в настройки — пункта в меню трея: `on_menu_event` крутится в том же потоке,
  и вызов `open_settings` оттуда на месте вернул бы тот же белый прямоугольник.
  Поэтому он уходит в `tauri::async_runtime::spawn`; сторожит это тест
  `tray_opens_settings_off_the_event_loop`, сверяющийся с формой обработчика —
  поведением это не поймать, `build()` отвечает `Ok` в обоих случаях.

- **Плагин хоткеев ходит через главный поток — звать его под мьютексом
  нельзя.** `unregister` и `on_shortcut` в `tauri-plugin-global-shortcut` идут
  через `run_main_thread!`: кладут задачу в цикл событий и блокируются на
  ответе. Пока регистрация жила только в `setup`/`apply_config`, это
  исполнялось inline и не стоило ничего; теперь список вешает поток поллера
  (`project_hotkeys::apply`), и переход настоящий. Держи он при этом свой
  мьютекс, приложение вставало бы насмерть двумя путями сразу: поллер ждёт
  главный поток, а тот ждёт мьютекс в команде `project_hotkeys_taken` — она
  поэтому `async`; и путь короче — `apply_config` зовёт `reapply` прямо с
  главного потока. Отсюда форма `apply_once`: под замком только обмен
  списками, работа с плагином — снаружи. Двух `apply` внахлёст разводит не
  второй мьютекс, а заявка (`claim`/`finish`): ждать опоздавшему нельзя ровно
  по той же причине, по какой нельзя держать замок.

- **Галка-фильтр в статуслайне зовёт `regroup`, а не `render`.** Отбор строк
  живёт в `regroup()`, `render()` рисует уже отобранное. С одним только
  `render` фильтр (`onlyWindow`, `showAll`) срабатывал бы к следующему ответу
  агрегатора — а тот может не прийти вовсе: на скрытом окне такт уходит в
  минуты, а неизменившееся состояние отсекается по отпечатку. Выглядит это
  мёртвым чекбоксом. Какая галка фильтр, решает `FILTER_KEYS`, считанный из
  `TOGGLE_CHECKS`: вторым списком он молча разошёлся бы с первым.

- **`showAll` перекрывает `onlyLive`, а не заменяет его.** Конфиг задаёт, с чем
  пикер открывается, галка — отступление от настройки, и отступление
  запоминается в `ui.json`, как и все остальные. Обратной галки «только живые»
  нет намеренно: включённый `onlyLive` и есть умолчание, а вторая галка поверх
  настройки читалась бы как второй фильтр.

- **Пикер гасится перед открытием настроек.** Он `alwaysOnTop` и центрирован,
  окно настроек центрируется тоже и выходит меньше — то есть ложится ровно под
  него и закрывается целиком: не прочитать и не нажать крестик. К `hideOnBlur`
  это отношения не имеет, тот про потерю фокуса; здесь пикер уходит по своей же
  команде, и до создания окна, пока фокус ещё наш.

- **Проектные хоткеи приезжают ответом агрегатора, а не из конфига.** Список
  живёт в `claudeWt.projects` у windows11-manager, демон кладёт его в файл
  трекера, `ccfzf --state` отдаёт полем `hotkey` у строки проекта. Признак
  свежести у них общий с окнами — `windowHost`: пуст (трекер лежит или файл
  протух) — регистрации не трогаем вовсе, непуст и совпал с конфигом — список
  полон и заменяет прежний, даже пустой. Своего таймера у хоткеев нет
  намеренно: второй признак свежести разошёлся бы с первым на первой же правке.
  Вешает клавиши `project_hotkeys.rs` из поллера, а не страница: у скрытого
  окна WebView2 умеет усыплять её целиком, и клавиши вставали бы только при
  открытом пикере. До первого ответа висит список из `hotkeys.json`.

- **Отказ регистрации проектного хоткея обязан быть виден.** Раньше он стоил
  строки в stderr, и `Ctrl+F11`, отобранный соседом по системе (им оказался
  windows-mqtt, регистрировавший те же клавиши из того же конфига менеджера),
  выглядел как сломанный конфиг: расследование заняло полдня. Теперь занятая
  комбинация уходит наверх событием `project-hotkeys`, гаснет в колонке `hk` и
  называется в статуслайне.

- **Умолчание второго глобального хоткея живёт в Rust, а в `config-shape.js`
  пусто.** Глобальных хоткея два: `hotkey` показывает пикер, `projectsHotkey`
  открывает его сразу в режиме проектов. У первого умолчание одно на обе
  системы — `SUPER` и есть Cmd на маке и Win на Windows. У второго объединять
  нечего: комбинации выбраны разные, `Win+Shift+F10` против
  `Option+Cmd+Shift+C`, — поэтому в `main.rs` развилка по `target_os`, а окно
  настроек умолчания не знает вовсе. Запиши оно комбинацию строкой —
  и, сохранившись на другой системе, увезло бы в `config.yaml` чужую клавишу.
  Отсюда правило: пустое поле (и отсутствие ключа) значит «взять встроенное»,
  а не «выключить», и `projects_hotkey` в `main.rs` глотает пустую строку без
  жалобы в stderr, в отличие от испорченной.

  Второй хоткей окно **переключает**, как и первый: повторное нажатие его
  гасит. Сначала он был сделан показывающим — рассуждение было, что нажатый на
  уже открытом пикере он должен сменить режим, а не погасить окно, — и это
  оказалось неверно на живом пикере: от любого хоткея пикера ждут переключения,
  и второй, ведущий себя иначе, читается как поломка. Отсюда общая
  `toggle_window` с флагом и общий дребезг `LastToggle`: два хоткея подряд не
  открывают окно дважды. Сам режим живёт префиксом `/a ` в строке поиска,
  поэтому Rust окно только показывает, а правку строки делает страница по
  событию `picker-projects` — `showProjects()` в `sessions.html`, общая с `^A`.

- **Буква встроенного действия не должна забирать у поиска буфер обмена.**
  Прямые клавиши действий гасят событие (`preventDefault` в ветке `plainCtrl`),
  а поле поиска в пикере сфокусировано всегда: буква, совпавшая с правкой
  текста, отбирает её насовсем. `seen` поэтому висит на `^D`, а не на
  напрашивавшейся `^V` («viewed») — вставляют в поиск как раз то, что теперь
  ищется, начало id сессии. Сторож — `test/action-hotkey.test.js`, список
  `c v x z`. `^A` в него не входит намеренно: он отдан ярлыку `/a` сознательно,
  и цена записана в `docs/TODO.md`.

- **Проектный хоткей решения не принимает — он его пересылает.** Нажатие уходит
  просьбой `{action:"terminal", cwd}` в `<base>/windows/claude-session-open`, а
  «поднять последнее окно этого каталога или завести новую сессию» решает
  `openClaudeProject` у windows11-manager. Решать это здесь нельзя по двум
  причинам: список у скрытого пикера отстаёт до восьми минут (бэкофф в
  `poller.rs`), а при выключённом фоновом опросе не обновляется вовсе; и
  профиль Windows Terminal по каталогу знает только менеджер —
  собранная здесь команда `wt.exe` его теряет. Шлёт просьбу Rust, а не
  страница: у скрытого окна WebView2 умеет усыплять её целиком, а хоткей
  нажимают ровно тогда, когда пикер скрыт. Страница остаётся запасной дорогой
  на случай ненастроенного брокера — там она поднимает новую сессию, как
  раньше.

- **Нулевой `windowPid` больше не про грамоту, но проверку в `canFocus`
  оставили.** Раньше это был адресат `AllowSetForegroundWindow`, и без адресата
  подъём был бы молчащим отказом; теперь грамота безымянная, а поле осталось
  признаком живого трекера — свой pid в файл окон кладёт он сам. Проверка в
  `canFocus` от этого не изменилась: ноль значит «файла нет, он чужой или
  протух», и Enter в этом случае честнее открыть терминал у себя. Проектный
  хоткей отменял на нулевом pid только грамоту, но не просьбу, — теперь
  отменять нечего, и `tracker_pid_from` из `project_hotkeys.rs` убран вместе с
  этой развилкой.

- **Терминал по каталогу открывает менеджер, а пикер — только там, где
  менеджера нет.** Enter на строке проекта шлёт `{action:"terminal", cwd}`,
  `^N` и пункт «New session» — `{action:"terminal-new", cwd, name}`; оба в
  `<base>/windows/claude-session-open`. Разница одна: `terminal` сначала ищет
  открытое окно этого каталога, `terminal-new` не ищет вовсе. Транспорт у обоих
  решает `chooseProjectOpenAction` (`open-transport.js`) — та же
  `chooseOpenTransport`, что и у Enter на строке сессии: менеджера просят
  только на машине трекера и при настроенном брокере, иначе остаётся местная
  `newSession`, и профиль там теряется по-честному — на такой машине
  `claudeWt.projects` не существует.

- **Имя новой сессии считает пикер, а не менеджер.** `uniqueSessionName` знает
  занятые имена (живые сессии плюс выданные за последнюю минуту), а менеджер
  такого списка не ведёт и взял бы basename каталога — то самое имя, которое
  занято открытой сессией. Два окна с одним заголовком трекер привязал бы к
  одной сессии. Поэтому в `terminal-new` имя едет в теле и на той стороне
  главнее каталога (`sessionNameFor` в `project-helpers.js`), а после удачной
  отправки занимается в `issuedNames` — иначе два быстрых `^N` дали бы одно имя
  дважды.

- **Адрес просьбы называет трекер, а не конфиг пикера.** Трекеров теперь
  несколько, у каждого свой префикс топиков, и просьба о подъёме или об
  открытии сессии обязана уйти на топик именно той машины, где стоит строка,
  — не на `<config.base>` пикера, тот отвечает только за машину, на которой
  пикер настраивали руками. Адрес приезжает полем `mqttBase`: у записи окна —
  как топик для подъёма, у записи машины — как топик для открытия сессии
  (`mqttBaseFor()` и `openManager()` в `frontend-src/session-windows.js`).
  Рассматривались и отвергнуты два других устройства. Сегмент машины в самом
  топике не годится: у windows11-manager `commandFromTopic` отбрасывает
  хвост, содержащий косую черту, — это защита от собственного эха при
  подписке на `#`, — и сегмент машины сломал бы разбор у соседа. Поле `host`
  в теле просьбы тоже не годится: оно потребовало бы правок в
  windows11-manager и асимметричной обратной совместимости — новому пикеру
  пришлось бы помнить, что старый менеджер поля не поймёт. Отсюда решение без
  правок соседа: у каждой машины свой базовый топик, и называет его она сама.
  Строка адреса приезжает из файла, написанного на чужой машине, и потому в
  `src-tauri/src/mqtt.rs` просеивается белым списком (`resolve_base`), а не
  кавычится — `#` и `+` в MQTT подстановочные знаки, публикация по такому
  топику ушла бы мимо всех. Отказ просеивания откатывает на
  `<config.base>/windows`, а не роняет просьбу: старый трекер адреса не
  называет вовсе, и на этой ветке пикер обязан вести себя как прежде.

- **`openSession` — отдельное поле, а не вывод из `focus`.** Способности
  разные: `focus` — умеет ли трекер поднимать уже открытое окно, `openSession`
  — берётся ли менеджер этой машины открывать сессии и терминалы вовсе. Мак
  пишет `focus: true` (окна там поднимает сам трекер через Accessibility) и
  `openSession: false` (терминалы там открывает сам пикер, и открывает верно
  — менеджера на маке нет). Выведи пикер второе поле из первого, упавший
  Windows-трекер оставил бы живым только мак — и пикер назначил бы менеджером
  его, хотя мак просьбу об открытии терминала принять не может: Enter
  замолчал бы, а молчащий Enter хуже открытого терминала. Живёт поле только в
  записи машины (`hosts`), а не окна (`windows`): у строки проекта окна нет
  вовсе, а спросить «кто откроет терминал» нужно и про неё — `openManager()`
  берёт поле оттуда, а не из записи окна. Отсутствие поля читается как
  «берётся» — то же правило, что у `canFocus`: windows11-manager этого поля
  не пишет и не должен, и правкой его не тронули.

- **Широкий режим — вторая раскладка того же списка, а не второй список.**
  `^F` переключает флаг `fullscreen`: `#list` получает класс `blocks` и хранит
  не строки, а блоки — по блоку на группу `groupSessions`, плюс `Projects` и
  `Snapshots`. Своего правила группировки у режима нет намеренно: второе
  разошлось бы с первым на первой же правке. Разметка строки одна на оба режима
  (`sessionItem`, `projectItem`, `snapshotItem`), карточка — это CSS под
  `#list.blocks`, а не вторая разметка.

  **Исключение одно, и оно про раскладку, а не про группировку: чужие живые
  сессии склеиваются обратно в один блок.** Узкий список делит их по машинам
  (группа на каждый `windowHost`, см. `activeGroups`), а здесь блок занимает
  колонку — пять трекеров дали бы пять узких колонок на то, что человек читает
  как одно «не здесь». В узком списке строки идут сверху вниз, и лишний
  заголовок там ничего не стоит. Склейка узнаёт чужую группу по её пометке
  `group.remote`, а не по заголовку: заголовок носит имя машины — данные с той
  стороны, — и разбор текста сделал бы это имя форматом, который нельзя менять.
  По той же причине и историю опознаёт пометка `group.past`, а не заголовок:
  раньше её узнавали по строке `Not running`, и правка формулировки молча
  увела бы её из своей колонки и выключила сворачивание. Заголовок склеенного
  блока — `Active remote sessions`
  со счётом, ключ — постоянный `g:remote`: по ключу помнится отрисовка блока, и
  считайся он от имён машин, уснувшая на соседней машине сессия пересобирала бы
  колонку целиком.

  **Раскладка широкого режима — три колонки, и она задана смыслом строк, а не
  их числом.** Слева свои живые сессии, посередине чужие и под ними проекты,
  справа история и под ней снимки. Номер колонки ставит блоку `buildBlocks` —
  по тому же признаку, по которому блок собран (`group.remote`, `group.past`),
  — и он же задаёт порядок блоков: колонка за колонкой, сверху вниз внутри
  колонки. Порядок этот и есть порядок чтения, а по нему ходят `←/→`
  (`moveBetweenBlocks`): разъедься он с видимым, стрелка уводила бы не туда,
  куда смотрит глаз. Тело блока страница ищет по ключу (`blockBodies`), а не по
  номеру узла: блоки лежат внутри колонок, и порядок узлов в `#list` с
  порядком блоков не совпадает.

  Верхний уровень — flex-строка из flex-колонок, и сеткой это не делается.
  Главному списку отдана вся высота, то есть надо охватить все ряды, а
  `grid-row: 1 / -1` считает `-1` по **явной** сетке, которой здесь нет вовсе:
  ряды неявные, размеченные по содержимому, и охватывать нечего. Во
  flex-колонке полная высота достаётся растяжением, сама собой. Пустая колонка
  не рисуется — она забрала бы у соседей долю ширины ради пустоты; ширину
  задаёт `flex`, а не доля от трёх, поэтому на `/a` и `/s` единственная
  колонка занимает экран целиком.

  Внутри колонки с двумя блоками высота делится **не** по содержимому.
  `flex: 0 1 auto` здесь неверен: ужимает flex пропорционально размеру, и
  длинный сосед съедает короткого — измерено, снимкам под шестьюдесятью
  строками истории оставалось десять пикселей, то есть ничего. Отсюда
  `flex: 1 1 0` (доля поровну) плюс `max-height: max-content` (блок не выше
  своего содержимого): упёршийся в потолок блок flex замораживает, а остаток
  отдаёт соседу. Измерено на 1400×900: история 420 со своей полосой, снимки
  212 целиком и без пустоты; на коротких списках не скроллится ничего, на
  одной колонке она занимает всю ширину, на двух — по половине; общего скролла
  страницы и переполнения `#list` нет ни в одном случае.

  Высоту блоку задаёт колонка, а не процент: `max-height: 100%` неразрешима
  там, где высота области сама зависит от содержимого, и движку положено
  читать такой процент как `none`. Блок вырос бы под все свои строки,
  `.block-rows` стало бы нечему переполняться, а переросший блок молча срезался
  бы внешним `overflow: hidden` — на экране длинный блок без единой полосы
  прокрутки, ровно то, ради ухода от чего блоки и заведены. Отсюда же снят
  `align-items: start`: он запрещал бы именно то растяжение, которым высота и
  держится.

  **История приходит развёрнутой.** Сворачивалась она затем, чтобы «что было
  раньше» не оттесняло вниз «что работает сейчас», — со своей колонкой она
  никого не оттесняет, и умолчание перевернулось вместе с причиной. Механизм
  цел и работает от обратного списка: `opts.collapsed` называет свёрнутые
  блоки (страница держит его в `collapsedBlocks`), Enter на строке-переключателе
  убирает оттуда ключ. Свернуть можно по-прежнему только историю (признак
  `past`), а входа в сворачивание сейчас нет ни одного — это записано долгом в
  `docs/TODO.md`.

  **Чужие машины названы подзаголовками внутри склеенного блока.** Склейка
  убрала заголовки групп, а вопрос «на какой машине» остался — ради него
  деление и заводили. Подзаголовок (`kind: 'block-subhead'`) лежит в тех же
  `rows`, что и сессии, но в `rows` страницы **не** попадает: это подпись, а не
  строка списка, у неё нет ни `data-index`, ни класса `row`, и ни стрелки, ни
  клик её не видят — ровно как заголовок группы в узком списке. Отсюда правило
  для `renderBlocks`: сколько строк было до блока, считается **до** сборки его
  элементов, а не вычитанием их числа. Арифметика «элементов ровно столько же,
  сколько строк» на подзаголовке врёт, и номера блоков разъехались бы со
  строками — стрелки сломались бы, а клик нет.

  Карточкой становится не любая строка внутри блока, а только та, что несёт
  класс `session` (`#list.blocks .row.session`): голый `.row` носят и строка
  проекта, и снимок, и свёрнутый блок недавних, и зелийная псевдосессия
  (`.row.zellij`), а карточка — оформление под запрос с ответом, которых у
  них нет. Маркер положительный, а не цепочка `:not(...)`: новый вид строки,
  заведённый потом, по умолчанию останется строкой, а не подхватит карточку
  по ошибке.

  Состояние отрисовки при переключении сбрасывается в обе стороны: `planListSync`
  сравнивает новые строки со снимком прошлой раскладки и правил бы не те
  элементы. Своё состояние на блок (`renderedBlocks`), а не одно на список, —
  иначе изменение в одном блоке пересобирало бы все.

  Режим и запрос, которые показаны на самом деле, вычисляет одна функция на
  обе раскладки — `shownModeAndQuery()`, а не `render()` по месту: широкая
  ветка не может взять сырой `mode` как есть — `buildBlocks` на `snapshots` без
  трекера не отдаёт ни одного блока, и вместо отката в обычный поиск по
  сессиям человек получил бы пустой экран без единого слова о причине. Второй
  такой же откат, написанный отдельно в узкой и широкой ветке, разошёлся бы с
  первым на первой же правке — они уже разъезжались ровно здесь.

  `KeyF` обязан стоять в `RESERVED_CODES` (`action-hotkey.js`): без этого
  встроенная ветка съедала бы `Ctrl+F` у настроенного человеком действия, и оно
  молчало бы — ровно та ошибка, за которую уже заплачено списком `c v x z`.

  `←/→` в этом режиме уходят в навигацию по блокам, но только когда каретка на
  краю запроса и ничего не выделено: поле поиска сфокусировано всегда, и отнять
  у него стрелки насовсем значило бы лишить человека правки запроса.

  Размер окна меняет Rust (`set_picker_size`), а не страница: у окна нет
  декораций, и `window.resizeTo` на нём не работает. Узкий размер обязан
  совпадать с `tauri.conf.json` — сторожит тест
  `narrow_size_matches_the_window_config`. Широкий зажимается по экрану
  (`fit_to_screen`): 1400×900 на тринадцатидюймовом маке закрывают его целиком,
  а окно без декораций и drag-region мышью не подвинуть.

  **Скрытому окну размер не ставится вовсе — просьба ждёт показа.** Окно
  создаётся скрытым (`visible: false`), а страница просит размер при каждой
  своей загрузке, то есть по окну, которого ещё нет на экране. На macOS
  `center()` — это `NSWindow.center()`, и считает он от экрана, на котором
  окно стоит; у выведенного из показа окна экрана нет, а `set_size` при этом
  отрабатывает — origin у NSWindow в левом нижнем углу, и окно остаётся у
  прежнего угла и растёт вправо и вниз. На маке это и увидели: узкое окно в
  углу, широкое за правым краем. Отсюда `SizeRequest` в `main.rs`:
  `set_picker_size` записывает названный режим и ставит размер только по
  показанному окну, а `show_picker` применяет отложенное сразу после `show()`
  — центровать надо окно, у которого уже есть экран. Все пути показа идут
  через `show_picker` (оба хоткея, оба пункта трея и клик по иконке — через
  `toggle_window`), второй ветки показа заводить нельзя. Применённое
  перестаёт быть отложенным: показ без новой просьбы окна не трогает, иначе
  человек видел бы перескок на каждом открытии. Страница за этим следить не
  может — у скрытого окна webview усыпляют целиком, и «перепросить размер по
  событию `picker-shown`» замолчало бы ровно в том случае, ради которого
  затевалось.

  **Режим помнится в `ui.json` третьим полем верхнего уровня — рядом с `sort` и
  `toggles`, — и окно настроек обязано вернуть это поле нетронутым.**
  `uiStateToSave` принимает его третьим аргументом; `settings.html` звал её
  двумя, и первое же сохранение вкладки UI гасило запомненный `^F`. Обратный
  ход тот же: страница пикера читает `ui.json` при загрузке и по событию
  `ui-changed` и просит у Rust размер **безусловно, в обе стороны** — `if
  (fullscreen)` умел только расширять раму и на гонке (настройки перечитывают
  `ui.json` между `^F` и записью `saveUi`) оставлял узкую раскладку в широкой
  раме.

## Иконки и хоткеи

- `src-tauri/icons/icon.ico` обязателен: без него `tauri-build` не собирает
  Windows-ресурс и падает до компиляции.
- **Руками в `src-tauri/icons/` правится только `favicon.png`.** Остальные семь
  файлов — вывод `python3 scripts/make-icons.py`, и правка любого из них
  переживёт ровно до следующего запуска скрипта.
- Умолчание хоткея — `Cmd+Shift+C` (на Windows `Win+Shift+C`). `Win+Shift+T`
  система держит за собой: `RegisterHotKey` отвечает «already registered».
- Отказ регистрации хоткея не фатален — пишет в stderr и не мешает запуску:
  окно поднимается из трея.
- `HOME` на Windows не выставлен; `load_config` и `seen.json` знают про
  запасной `USERPROFILE`.
